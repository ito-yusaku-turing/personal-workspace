GitHub の Pull Request をレビューする。引数: $ARGUMENTS

**目的は、人間が「何を指摘するか」を決めるための材料を揃えること**。指摘を投稿するのは人間であり、このコマンドは GitHub に何も書き込まない。

## 引数

- PR の指定（必須）: URL（`https://github.com/<owner>/<repo>/pull/<N>`）か `<owner>/<repo>#<N>`。番号だけのときは、どのリポジトリか確認する（作業ディレクトリは personal-workspace なので、番号だけでは決まらない）。
- レビューの深さ（任意）: `low` `medium` `high` `xhigh`。省略したら `high`。**`max` と `ultra` は、引数で明示されたときだけ**使う（コストが大きい）。
- 残りの文字列は「見てほしい観点」として、レビューと判断材料の両方で重視する。

## 参照するもの

- `docker/container-bin/doctor.sh --porcelain` — `gh-auth` が `ok` でなければ、PR を取得できない。`missing` なら `docker/bin/setup/github.sh gh-login` を案内して終える。`declined` なら、差分と本文を貼ってもらえればそれで進めると伝えて終える。
- **対象リポジトリの AGENTS.md / CLAUDE.md**（`/usr/app/<repo>` にマウントされていれば）— コーディング規約・設計方針・禁止事項を、レビューの基準に加える。マウントされていなければ、PR の head の同名ファイルを `gh api` で読む。

## 手順

1. **PR を取得する**。
   ```bash
   gh pr view <PR> --json number,title,url,author,body,baseRefName,headRefName,headRefOid,isDraft,state,additions,deletions,changedFiles,files,commits,labels,closingIssuesReferences
   gh pr diff <PR>
   gh pr view <PR> --comments   # 既存の議論。すでに指摘済みのことを二重に挙げないため
   ```
   本文から Issue や別 PR が参照されていれば、背景の把握に必要な範囲で読む。

2. **周辺のコードを読めるようにする**。差分だけでは、呼び出し元・データの流れ・既存の同じパターンが分からない。
   - 対象リポジトリが `/usr/app/<repo>` にマウントされていれば、そこで `git fetch origin pull/<N>/head` し、`git show FETCH_HEAD:<path>` や `git grep <pattern> FETCH_HEAD` で読む。
   - **マウント先の作業ツリーは変えない**（`gh pr checkout`・`git switch`・`git stash` などはしない。人間の作業中の変更があり得る）。作業ツリーが必要なら、scratchpad に `git worktree add --detach <scratchpad>/pr-<N> FETCH_HEAD` で作り、終わったら `git worktree remove` で消す。
   - マウントされていなければ、`gh api repos/<owner>/<repo>/contents/<path>?ref=<headRefOid>` で必要なファイルだけ読む。

3. **変更内容を整理する**（出力の「1. 変更内容の整理」）。PR 本文は、書き手の頭の順に書かれていて読みにくいことがある。本文・コミット・差分・関連 Issue から、次の見出しに組み直す。本文の言い回しを写すのではなく、読み手が最初に知りたい順に書く。
   - **概要**: 何をする PR か、1〜3 文で
   - **背景・目的**: なぜ必要か。本文に書かれていなければ「本文に記載なし」とし、差分から推測したことは推測と明記する
   - **変更点**: 変更の単位ごとに箇条書き。ファイルの羅列ではなく、振る舞いの変化で書く（主なファイルは括弧で添える）
   - **影響範囲**: 利用者から見える変化、DB・API・設定・依存関係の変更、移行やデプロイ順の要否
   - **本文と実装の対応**: 本文が述べていることを 1 件ずつ挙げ、差分のどこで実装されているかを対応づける。次の 3 つを区別して示す
     - 本文どおりに実装されている
     - 本文にあるが、実装が見当たらない・本文と食い違う
     - 実装にあるが、本文に書かれていない（ついでの変更・意図の分からない変更）

4. **コードレビューを行う**。Claude Code の `code-review` スキルを、Skill ツールで呼ぶ。
   - 引数は `<深さ> <PR の URL>`。`--comment` と `--fix` は付けない（GitHub への投稿も、作業ツリーの変更もしない）。
   - スキルが PR を解決できない（別リポジトリで動かない等）ときは、手順 2 で用意した worktree を対象に呼ぶか、それも無理なら同じ観点（正しさのバグ、規約違反、単純化の余地）で自分でレビューする。どちらで行ったかを出力に書く。
   - スキルの結果に加えて、**手順 3 の「本文と実装の対応」で見つかった食い違い**と、**対象リポジトリの AGENTS.md / CLAUDE.md の規約に反する点**も指摘事項に含める。
   - 既存のコメントで指摘済みのものは、指摘事項から外し、「既出」として一言だけ触れる。

5. **指摘ごとに判断材料を集める**（出力の「3. 指摘ごとの判断材料」）。推測で埋めず、コードを読んで確かめる。確かめられなかった項目は「未確認」と書き、何を見れば確かめられるかを添える。
   - **発生条件**: どの入力・状態・操作の順序・環境で起きるか。再現手順を具体的に
   - **発生頻度の見積もり**: 呼び出し元の数、その経路が通常の操作で通るか、条件を満たすデータがどれくらいありそうか、などの根拠とともに「常に／よくある操作で起きる／まれ／理論上のみ」のどれか
   - **起きたときの影響**: データの破損・消失、セキュリティ、誤った表示、性能、開発者体験のどれか。影響を受ける人の範囲
   - **気づきやすさ・戻しやすさ**: エラーとして表に出るか、黙って誤るか。起きた後に直せるか
   - **PR が持ち込んだものか**: この PR で新たに生じたのか、既存のコードに前からあるのか（`git show <base>:<path>` で確かめる）。既存なら、この PR で直すべきかは別の判断になる
   - **直すコスト**: 修正の大きさの目安と、直し方の案
   - **推奨**: 「この PR で直してもらう」「指摘はするがマージは妨げない（nit・提案）」「別 Issue にする」「指摘しない」のどれか。理由を 1 行で。最終判断は人間がするので、推奨の確信度（高・中・低）も添える

6. **出力する**（下の形式）。worktree を作っていれば消す。

## 出力の形式

ターミナルに次の構成で出す。指摘が無ければ 3 は「指摘なし」とし、レビューで見た範囲を書く。

```markdown
# <PR タイトル>（<URL>）

<作成者> / <base> ← <head> / +<additions> −<deletions>、<changedFiles> ファイル / <Draft なら Draft>

## 1. 変更内容の整理
### 概要
### 背景・目的
### 変更点
### 影響範囲
### 本文と実装の対応

## 2. レビュー結果
- 方法: code-review スキル（深さ: <深さ>）／自分でレビュー
- 総評: <マージしてよさそうか、大きな懸念はあるか。2〜3 文>
- 指摘の一覧（重い順）:
  1. [<推奨>] <要約> — `<path>:<line>`
  2. ...
- 既出（コメントで指摘済み）: ...

## 3. 指摘ごとの判断材料
### 指摘 1: <要約>
- 箇所: `<path>:<line>`
- 内容:
- 発生条件:
- 発生頻度: <常に／よくある／まれ／理論上のみ> — <根拠>
- 影響:
- 気づきやすさ・戻しやすさ:
- PR が持ち込んだものか:
- 直すコスト・直し方の案:
- 推奨: <この PR で直す／nit・提案／別 Issue／指摘しない>（確信度: <高・中・低>）— <理由>

## 4. 確認していないこと
（読めなかったファイル、動かしていないテスト、未確認のまま残った項目）
```

- 人間がそのまま PR に貼れるよう、各指摘の「内容」は、書き手に向けた文として読めるように書く。
- ほかのリポジトリの PR・Issue は、番号だけでなくフル URL のリンクで書く。

## やらないこと

- GitHub への書き込み（コメント・レビューの投稿、approve / request changes、ラベルの変更）。人間に頼まれたら、そのときに内容を示して確認してから行う
- マウントしたリポジトリの作業ツリー・ブランチの変更
- PR のブランチへの commit・push
