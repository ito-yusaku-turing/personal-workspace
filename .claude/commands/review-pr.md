GitHub の Pull Request をレビューする。引数: $ARGUMENTS

**目的は、人間が「何を指摘するか」を決めるための材料を揃えること**。指摘を投稿するのは人間であり、このコマンドは GitHub に何も書き込まない。

## 入力の想定

- 入力は **1 つ以上の PR の URL** だけ。形は `https://github.com/turingmotors/<repo>/pull/<番号>`。
- 組織は **`turingmotors` に固定**。
- 対象は **Open の PR**（Draft を含む）。
- 複数の URL があるときは、**互いに関係している PR**（同じ機能を複数のリポジトリにまたがって実装している、PR を積み重ねている、など）。

入力ミスがあるものとして扱う。**想定から外れたものは、レビューを始める前にすべて洗い出し、まとめて 1 回で確認する**（1 件ずつ止めない）。確認は AskUserQuestion で行う。問題ごとに、何が想定外か、どう直せそうか（「`turingmotor` は `turingmotors` の誤りでは？」など）を添える。手順 1〜3 の確認は、できるだけ 1 回にまとめる。

## 手順

### 1. 入力を検証する（取得の前）

引数を空白・改行・カンマ・読点で区切り、1 つずつ判定する。前後の `<>` `()` 「」・句読点は取り除いてから判定する。

| 判定 | 例 | 扱い |
|---|---|---|
| 正しい URL | `https://github.com/turingmotors/cdk-apps/pull/2253` | そのまま使う |
| PR の URL に余分な部分が付いている | 末尾の `/files` `/commits` `/commits/<sha>` `/checks`、`?…` `#…`、末尾の `/`、`http://`、`www.` | **PR の URL に直して続ける**。直したことを最初の出力で示す（ブラウザからのコピーでよく起きるため、確認はしない） |
| **組織が `turingmotors` 以外** | `github.com/turingmotor/…`、`github.com/someone/…` | **エラー**。その URL は対象にしない。綴りの近い誤りなら正しい候補を示す |
| 引数が空 | | **エラー**。使い方（`/review-pr <PR の URL> ...`）を示して終える |
| PR でない GitHub の URL | `/issues/<番号>`、`/compare/…`、`/tree/…`、リポジトリのトップ | 警告して確認 |
| URL でないもの | `#2253`、`cdk-apps#2253`、`2253`、説明の文章 | 警告して確認。推測できる URL があれば示す |
| 壊れた URL | `https://` が 2 つ連結されている、番号が数字でない、`github.com` 以外のホスト | 警告して確認。連結なら分割した候補を示す |
| 重複 | 同じ PR が 2 回（直した後で同じになるものを含む） | 警告して確認（別の PR を貼るつもりだった可能性がある） |
| 件数が多い | 6 件以上 | 警告して確認（時間とコストが大きい） |

- **エラーが 1 件でもあれば、残りの入力が正しくてもレビューは始めない**。エラーの内容を示し、正しい URL で打ち直してもらう。
- 警告だけなら、問題ごとに「直した候補で続ける／その URL を外して続ける／中止する」を確認する。

### 2. PR を取得し、状態を検証する

セットアップ状態を見る（`docker/container-bin/doctor.sh --porcelain`）。`gh-auth` が `ok` でなければ取得できない。`missing` なら `docker/bin/setup/github.sh gh-login` を案内し、`declined` なら差分と本文を貼ってもらえればそれで進めると伝えて終える。

各 PR を取得する。

```bash
gh pr view <URL> --json number,title,url,author,body,state,isDraft,mergedAt,closedAt,baseRefName,headRefName,headRefOid,headRepositoryOwner,isCrossRepository,createdAt,additions,deletions,changedFiles,files,commits,labels,closingIssuesReferences,statusCheckRollup
```

**読む量を見積もる**。`files` から、次のファイルを「読まないもの」として除いた変更行数とファイル数を出す。除いたものは出力に書く。

- lock ファイル（`package-lock.json` `pnpm-lock.yaml` `yarn.lock` `uv.lock` `poetry.lock` `Cargo.lock` `go.sum` など）
- 生成物（`dist/` `build/` `*.min.js`、スナップショット、`.gitattributes` で `linguist-generated` のもの、ファイル冒頭に生成物と書かれたもの）
- DB のマイグレーションは生成されたものでも**除かない**（振る舞いを変えるため）

次のものは想定外として扱う。手順 1 と同じく、**全件を取得し終えてから、まとめて 1 回で確認する**。

| 判定 | 扱い |
|---|---|
| PR が存在しない・読めない（404・権限なし） | エラー。番号やリポジトリ名の誤りの可能性を示す |
| 返ってきた `url` の組織が `turingmotors` でない（リポジトリの移管でリダイレクトされた等） | エラー |
| `state` が `MERGED` | 警告して確認（マージ後のレビューは想定していない） |
| `state` が `CLOSED` | 警告して確認 |
| フォークからの PR（`isCrossRepository` が true） | 警告して確認 |
| 除いた後でも大きい（PR 1 件で変更 1,000 行超、または 50 ファイル超） | 警告して確認。レビューの精度が落ちることと、分割を提案する材料になることを伝え、「続ける／中止する」を選んでもらう |
| Draft | 続ける。出力に Draft と書く |

### 3. 複数の PR の関係を確かめる（2 件以上のとき）

PR の組ごとに、次の手がかりを探す。

- 本文・コミットメッセージが、もう一方の PR の URL・番号・ブランチ名に触れている
- 同じ Issue を参照している（`closingIssuesReferences`、本文中の Issue の URL）、または同じチケット番号・同じ外部資料の URL を含む
- 積み重ねの関係（一方の `baseRefName` が、もう一方の `headRefName`）
- 同じリポジトリで、変更したファイルが重なる
- リポジトリをまたいで、一方が定義するもの（API・型・設定のキー・環境変数・テーブル名など）を、もう一方が使っている
- ブランチ名やタイトルに共通する固有の語（チケット番号・機能名）。作成者が同じで、作成日時が近い

手がかりでつながる PR をまとめ、グループに分ける。**グループが 2 つ以上に分かれたら警告して確認する**。どの PR とどの PR がつながらなかったか、見つかった手がかりを示し、「関係があるものとして一緒にレビューする／PR ごとに別々にレビューする／中止する」を選んでもらう。作成者が同じで日時が近い、だけの PR は、つながったとみなさない（弱い手がかりとして示すにとどめる）。

関係がある場合は、関係の種類（積み重ね・リポジトリをまたぐ実装・同じ Issue の分担など）と、**マージ・デプロイの順序**（あれば）を把握しておく。

### 4. 周辺の情報を集める

差分だけでは、呼び出し元・データの流れ・既存の同じパターンが分からない。PR ごとに次を行う。

- `gh pr diff <URL>` と `gh pr view <URL> --comments`（既存の議論。指摘済みのことを二重に挙げないため）。本文から Issue や別 PR が参照されていれば、背景の把握に必要な範囲で読む。
- **CI の結果**: `gh pr checks <URL>`。落ちているチェックがあれば、`gh run view <run-id> --log-failed` で原因を見る。
- **前回のレビュー**: 自分（`gh api user -q .login`）が過去にこの PR をレビューしているか、`gh api repos/turingmotors/<repo>/pulls/<N>/reviews` と `.../pulls/<N>/comments` で調べる。あれば「再レビュー」として扱う（手順 6）。
- 対象リポジトリの AGENTS.md / CLAUDE.md を読み、規約・設計方針・禁止事項をレビューの基準に加える。
- リポジトリが `/usr/app/<repo>` にマウントされていれば、そこで `git fetch origin pull/<N>/head` し、`git show FETCH_HEAD:<path>` や `git grep <pattern> FETCH_HEAD` で読む。
  - **マウント先の作業ツリーは変えない**（`gh pr checkout`・`git switch`・`git stash` などはしない。人間の作業中の変更があり得る）。作業ツリーが必要なら、scratchpad に `git worktree add --detach <scratchpad>/pr-<repo>-<N> FETCH_HEAD` で作り、終わったら `git worktree remove` で消す。
- マウントされていなければ、`gh api repos/turingmotors/<repo>/contents/<path>?ref=<headRefOid>` で必要なファイルだけ読む。

### 5. 変更内容を整理する

PR 本文は、書き手の頭の順に書かれていて読みにくいことがある。本文・コミット・差分・関連 Issue から、次の見出しに組み直す。本文の言い回しを写すのではなく、読み手が最初に知りたい順に書く。

- **概要**: 何をする PR か、1〜3 文で
- **背景・目的**: なぜ必要か。本文に書かれていなければ「本文に記載なし」とし、差分から推測したことは推測と明記する
- **変更点**: 変更の単位ごとに箇条書き。ファイルの羅列ではなく、振る舞いの変化で書く（主なファイルは括弧で添える）
- **影響範囲**: 利用者から見える変化、DB・API・設定・依存関係の変更、移行やデプロイ順の要否。AWS・Databricks の既存のリソースに関わる変更は、必要に応じて実環境の状態を裏どりする（「AWS・Databricks での裏どり」）
- **本文と実装の対応**: 本文が述べていることを 1 件ずつ挙げ、差分のどこで実装されているかを対応づける。次の 3 つを区別する
  - 本文どおりに実装されている
  - 本文にあるが、実装が見当たらない・本文と食い違う
  - 実装にあるが、本文に書かれていない（ついでの変更・意図の分からない変更）

関係のある複数の PR は、**先に全体の整理**（全体で何を実現するか、PR の分担、マージ・デプロイの順序）を書き、続けて PR ごとの整理を書く。

### 6. コードレビューを行う

PR ごとに、Claude Code の `code-review` スキルを Skill ツールで呼ぶ。

- 引数は `high <PR の URL>`。`--comment` と `--fix` は付けない（GitHub への投稿も、作業ツリーの変更もしない）。`max` と `ultra` は使わない。
- スキルが PR を解決できない（別リポジトリで動かない等）ときは、手順 4 で作った worktree を対象に呼ぶ。それも無理なら同じ観点（正しさのバグ、規約違反、単純化の余地）で自分でレビューする。どちらで行ったかを出力に書く。
- **スキルの結果の受け取り方**: スキルが結果を専用のツール（ReportFindings など）で報告し、テキストに出さないことがある。その場合も、報告された指摘をこのコマンドの指摘の材料として受け取り、手順 7 以降の形式で出し直す。スキルの報告で手順を終えず、手順 7・8 まで続ける。

スキルの結果に加えて、次も見て指摘事項に含める。

- **CI**: 落ちているチェックは、ほかの指摘より先に挙げる。PR の変更が原因か、既存の不安定なテストや基盤の問題かを、ログから見分けて書く。
- **テスト**: 振る舞いを変えた箇所ごとに、それを確かめるテストが追加・更新されているか。無ければ「テストが無い」を指摘とし、どの条件のテストがあるとよいかを添える。リファクタリングで既存のテストが変わっていないなら、それは良い材料として書く。
- **セキュリティ**: PR が IAM・ポリシー・ロール、認証・認可、秘密情報の扱い、ネットワークの公開範囲、外部からの入力の検証のどれかに触れるとき（`identity` や `cdk-apps` の権限まわりは常に該当）は、`security-review` スキルも呼ぶ。スキルは作業中のブランチを対象にするため、手順 4 の worktree で使えなければ、同じ観点（権限が必要以上に広がっていないか、認証を迂回できないか、秘密が漏れないか、入力を信用していないか）で自分で見る。
- 手順 5 の「本文と実装の対応」で見つかった食い違い。
- 対象リポジトリの AGENTS.md / CLAUDE.md の規約に反する点。
- 関係のある複数の PR では、**PR の間の食い違い**（一方が定義し、もう一方が使うものの名前・型・値が合っているか。片方だけが先にマージ・デプロイされたときに壊れないか）。

既存のコメントで指摘済みのものは、指摘事項から外し、「既出」として一言だけ触れる。

**再レビューのとき**（手順 4 で自分の過去のレビューが見つかったとき）は、次も行う。

- 最後のレビューの `commit_id` から `headRefOid` までの差分（`git diff <commit_id> FETCH_HEAD`）を「前回以降の変更」として重点的に見る。force push で `commit_id` に届かないときは、その旨を書いて全体を見直す。
- 自分の過去の指摘を 1 件ずつ挙げ、「対応された／対応されていない／返信で説明された（妥当か）」を判定する。
- 全体の整理（手順 5）は短くし、前回からの変化を中心に書く。

### 7. 指摘ごとに判断材料を集める

推測で埋めず、コードを読んで確かめる。必要なら AWS・Databricks で実環境を裏どりする（下の「AWS・Databricks での裏どり」）。確かめられなかった項目は「未確認」と書き、何を見れば確かめられるかを添える。

まず、指摘を 2 つに分ける。

- **詳しく書く指摘**: 推奨が「この PR で直してもらう」「別 Issue にする」になりそうなもの、または判断が分かれそうなもの。下の全項目を書く。
- **短く書く指摘**: 明らかな nit（命名・書き方・小さな単純化）や、すぐ「指摘しない」と判断できるもの。1 行で、推奨と理由だけを書く。

詳しく書く指摘の項目:

- **発生条件**: どの入力・状態・操作の順序・環境で起きるか。再現手順を具体的に
- **発生頻度の見積もり**: 呼び出し元の数、その経路が通常の操作で通るか、条件を満たすデータがどれくらいありそうか、などの根拠とともに「常に／よくある操作で起きる／まれ／理論上のみ」のどれか。実環境で確かめた根拠は、そうと分かるように書く（「AWS で確認: …」）
- **起きたときの影響**: データの破損・消失、セキュリティ、誤った表示、性能、開発者体験のどれか。影響を受ける人の範囲
- **気づきやすさ・戻しやすさ**: エラーとして表に出るか、黙って誤るか。起きた後に直せるか
- **PR が持ち込んだものか**: この PR で新たに生じたのか、既存のコードに前からあるのか（`git show <base>:<path>` で確かめる）。既存なら、この PR で直すべきかは別の判断になる
- **直すコスト**: 修正の大きさの目安と、直し方の案
- **推奨**: 「この PR で直してもらう」「指摘はするがマージは妨げない（nit・提案）」「別 Issue にする」「指摘しない」のどれか。理由を 1 行で。最終判断は人間がするので、推奨の確信度（高・中・低）も添える

### 8. 出力する

下の形式で出す。worktree を作っていれば消す。

## AWS・Databricks での裏どり

このコマンドの中では、**判断材料を確かめるための読み取り**を、確認せずに行ってよい。例: コードが前提にしているリソースが実在するか、設定（バージョニング・暗号化・ポリシー・ジョブの設定など）が実際にどうなっているか、対象のデータがどれくらいあるか。レビューの材料に関係しない調べものはしない。

### AWS

- **プロファイルは `readonly`（ReadOnly ロール）だけを使う**。コマンドには毎回 `--profile readonly` を付ける。`full` `dev-secrets` など、ほかのプロファイルは使わない（`readonly` で読めなくても切り替えない）。
- 最初に `aws sts get-caller-identity --profile readonly` で、ReadOnly ロールで入れることを確かめる。
- 使ってよいのは、状態を変えない操作だけ（`describe-*` `get-*` `list-*` `head-*`、`aws s3 ls`）。
- 読み取りでも次はしない: 秘密の中身を読む操作（`secretsmanager get-secret-value`、`ssm get-parameter(s) --with-decryption`、`kms decrypt`）。また、データそのものの取得（`s3 cp` `s3api get-object`、DynamoDB の `scan` / `query` など）は、事前に承認を得る。
- SSO の期限が切れていたら（`Token has expired`、`The SSO session associated with this profile has expired` など）、**手を止めて**、人間にログインし直してもらう（例: `! aws sso login --sso-session turing --use-device-code`）。自分ではログインしない。済んだと言われたら確かめ直して続ける。裏どりなしで進めてよいと言われたら、その項目を「未確認」にして続ける。

### Databricks

- `~/.databrickscfg` の `DEFAULT` プロファイルを使う。最初に `databricks current-user me` で入れることを確かめる。
- 使ってよいのは、状態を変えない操作だけ（`get` `list` 系。例: `jobs get` `jobs list` `jobs list-runs` `clusters get` `workspace list` `workspace export` `catalogs` / `schemas` / `tables` の `get` `list`）。
- 次はしない: ジョブの実行・取り消し、クラスタやウェアハウスの起動・停止、設定やファイルの変更・削除。SQL の実行（SELECT を含む）はウェアハウスを動かし、データも読むので、事前に承認を得る。
- **トークンの期限が切れていたら**（`invalid_grant`、`refresh token is invalid`、`401` など）、**手を止めて**、人間に再アクティベートを依頼する。エラーの内容を示し、自分ではログインしない。済んだと言われたら `databricks current-user me` で確かめ直して続ける。裏どりなしで進めてよいと言われたら、その項目を「未確認」にして続ける。

### 事前に承認を得る場合

次のどれかに当たるときは、実行の前に「何を・何回くらい・なぜ」を示して承認を得る。

- 1 回のレビューで、AWS と Databricks を合わせて **20 回を超えそう**なとき
- リソースを 1 件ずつループで叩く、全件をページングで取り切るなど、回数が読めないとき
- 課金や負荷が大きい操作（Athena・CloudWatch Logs Insights のクエリ、Databricks の SQL、大きなバケットの `s3 ls --recursive`）
- 上で「事前に承認」としたもの（データそのものの取得など）

### 書き方

- 判断材料には、何を叩いて何が分かったかを要約して書く（「AWS で確認: `<bucket>` はバージョニングが有効」）。叩いたコマンドは「4. 確認していないこと」の前に一覧で残す。
- アカウント ID・ARN・内部のホスト名・データの中身は、人間が PR に貼る「内容」の文には入れない（PR は多くの人が見る）。判断材料の側にだけ書く。

## 2. レビュー結果
- 方法: code-review スキル／自分でレビュー（security-review を併用したかも書く）

「PR ごとに別々にレビューする」が選ばれたときは、単体の形式を PR の数だけ続けて出す。

- 人間がそのまま PR に貼れるよう、各指摘の「内容」は、書き手に向けた文として読めるように書く。
- PR・Issue は、番号だけでなくフル URL のリンクで書く。

## やらないこと

- GitHub への書き込み（コメント・レビューの投稿、approve / request changes、ラベルの変更）。人間に頼まれたら、そのときに内容を示して確認してから行う
- マウントしたリポジトリの作業ツリー・ブランチの変更
- PR のブランチへの commit・push
- AWS・Databricks の状態を変える操作。読み取りでも、上の「AWS・Databricks での裏どり」の範囲を超えるもの
