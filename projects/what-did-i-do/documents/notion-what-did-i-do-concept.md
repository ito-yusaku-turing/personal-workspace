# システム操作の通知と見張りの構想（今日なにしたかわかる君・大事なもの見張る君）

作成: 2026-10-26 ／ 伊藤

自分がシステムに対して行った重要な操作を、自分で把握できるようにする仕組みの構想です。人でない主体（アプリ・CI・Databricks のロールなど）の操作は、別の仕組みで見張ります。S3 の原本バケットの削除の検知（今日なに消したかわかる君）を作る中で出てきた考えを、一般化しました。

**要点**

- 仕組みを 4 つの部品に分けます。「事実の層」「今日なにしたかわかる君」「今日なに消したかわかる君」「大事なもの見張る君」です。
- **今日なにしたかわかる君**は、自分の主体による重要な操作を、本人に定期的に知らせます。Slack の通知は、この目的に絞ります。
- **大事なもの見張る君**は、人でない主体の「いつもと違う」を LLM で拾い、MLOps チームに知らせます。
- **今日なに消したかわかる君**は、原本バケットの戻せない削除などを、LLM を使わず規則で**必ず**知らせます。ほかの部品の判断で、この通知を消すことはできません。
- LLM には、ログを集計・整理してから渡します。費用は月 $30 前後の見込みで、生のログを渡す場合の 100 分の 1 以下です。プロンプトインジェクションへの備えにもなります。

## 1. 背景

S3 の原本バケット（消えると作り直せないデータを置くバケット）の守りを、段階的に固めてきました。

- バージョニング: ふつうの削除・上書きを戻せるようにした。
- バケットポリシー: 古い版の削除と守りを外す操作を、例外の主体だけに限った（12 本すべて、2026-10-26）。
- 削除の記録: S3 のイベントと CloudTrail を集める仕組みと、検証用のバケット（カナリア）を本番に置いた（[cdk-apps#2267](https://github.com/turingmotors/cdk-apps/pull/2267)、2026-10-26）。

削除の記録の次は、毎時の報告を作る予定でした。設計を進めるうちに、次のことが見えてきました。

- 「誰が・何を・いつ」を集めて本人に知らせる仕組みは、削除に限らず、IAM の変更や本番の設定の変更にも使える。
- 一方で、削除を消した主体の多くは人ではない（アプリのロール、Databricks のロール、ライフサイクルなど）。人への通知とは、目的も届け先も違う。

そこで、全体の構想を立て直しました。

## 2. 目的と範囲

- **Slack の通知は、「自分の主体による重要な操作を、定期的に本人に知らせる」ことに絞ります。** 振り返りのためです。あわせて、認証情報が盗まれたときに、本人が「身に覚えのない操作」に気づけるようにします。
- **人でない主体は、別の仕組みで見張ります。** LLM で異常を拾い、MLOps チームに知らせます。
- **決まった重大な操作は、規則で必ず知らせます。** LLM の判断は確率的で、見逃しがありうるためです。

## 3. 部品の構成

| 部品 | 呼び名 | 中身 | 届け先 |
|---|---|---|---|
| 1. 事実の層 | （共通の部品） | CloudTrail・S3 のイベント・Inventory などを集め、共通の形の記録にそろえる | — |
| 2. 人の通知 | **今日なにしたかわかる君** | 自分の主体による重要な操作を、定期的に知らせる | 本人（DM） |
| 3. 必ずの通知 | **今日なに消したかわかる君** | 原本バケットの戻せない削除などを、規則で必ず拾う | 本人＋MLOps チーム |
| 4. 見張り | **大事なもの見張る君** | 人でない主体・対応表に無い主体の異常を、LLM で拾う | MLOps チーム |

### 3.1 事実の層

- 原本バケットの削除の記録のために作った「集める部分」（S3 のイベント → EventBridge → Firehose、CloudTrail のトレイル、S3 Inventory → ログのバケット）が、その最初です。作り直しは要りません。
- 1 件の記録には、次の項目を持たせます。
  - 誰が（主体と、分かれば本人）
  - いつ・どのシステムで・何に・何をしたか
  - 重要度・戻せるか
  - 元の記録へのリンク
- 主体と本人の対応表（SSO のメールアドレス、ロールの担当者）も、ここに持ちます。

### 3.2 今日なにしたかわかる君（人の通知）

- 対象は、自分の主体の操作だけです。
- 「重要な操作」に絞ります。最初は、IAM・権限、バケットポリシー、データの削除、本番の設定くらいから始めます。普段から繰り返している操作は省きます。量が多いと読まれなくなり、身に覚えのない操作にも気づけなくなるためです。
- 1 件ごとに「戻せるか」を添え、戻せない操作が目立つようにします。
- 届け先は本人への DM です。個人の操作をチャンネルに出すと、監視されているように感じる人がいるためです。

### 3.3 今日なに消したかわかる君（必ずの通知）

- 取りこぼさないことを前提にします。決まった重大な操作は、LLM を通さず規則で拾い、必ず知らせます。
  - 原本バケット 12 本の、戻せない削除（古い版の削除・ライフサイクルによる失効）
  - 守りの設定の変更（バケットポリシー・バージョニング・ライフサイクル）
- 主体が人なら本人にも届け、どの主体でも MLOps チームに届けます。
- 2 と 4 の判断で、この通知を消すことはできません。
- 設計とカナリアでの確認の結果は、別の資料にあります（personal-workspace の `projects/aws-data-protection/workstream/s3-data-protection-2/stage2-hourly-report.md`）。

### 3.4 大事なもの見張る君（見張り）

- 対象は、人でない主体と、対応表に無い主体です。
- LLM で「いつもと違う」を拾います。普段と違う量・時間帯・操作の組み合わせ、初めて見る操作やリソースなどです。規則で書き切れないものを拾う役です。
- 誤報と見逃しを、チームが返せる仕組みを持たせ、判断を育てます。
- LLM の使い方と安全は、5 章にまとめました。

## 4. 主体の振り分け

**原則: 誰の通知にも載らない操作を作らない。** 対応表に無い主体は、すべて大事なもの見張る君に入れます。

| 主体 | 振り分け | 補足 |
|---|---|---|
| SSO の人（対応表にある） | 今日なにしたかわかる君 | 必ずの通知の対象なら、今日なに消したかわかる君にも |
| GitHub Actions の deploy のロール | 大事なもの見張る君 | 起点の人（PR をマージした人）が分かれば、その人の通知にも載せる |
| アプリのロール | 大事なもの見張る君 | |
| Databricks のロール | 大事なもの見張る君 | Databricks の監査ログで本人を引けるなら、将来は人の通知にも |
| 対応表に無い主体（持ち主不明の IAM ユーザーなど） | 大事なもの見張る君 | |
| root・BreakGlass | 今日なに消したかわかる君（常に即時にチームへ） | 使われること自体が異常 |
| ライフサイクルによる失効 | 今日なに消したかわかる君（原本バケットの場合） | |

## 5. LLM の使い方と安全

- **ログは集計・整理してから渡します。** 主体ごとに、操作の種類ごとの件数、エラーの件数、普段（たとえば過去 14 日）との差、初めて見る操作・リソースなどにまとめます。
- **生の文字列は、できるだけ渡しません。** CloudTrail には、操作した側が自由に決められる文字（オブジェクトのキー、ロールのセッション名、User-Agent など）が入ります。攻撃者がそこに指示を書けば、LLM の判断を曲げられるおそれがあります（プロンプトインジェクション）。
- **LLM の判断は、通知を「足す」方向にだけ使います。** 規則で拾った重大な操作を、LLM が「報告不要」にして消すことはできないようにします。
- **実行場所は Amazon Bedrock のリージョン内（us-west-2）にします。** ログを社外に出さないためです。世界中のリージョンに振り分ける推論（Global）は約 10% 安いものの、米国の外で処理されうるので使いません。

## 6. 費用の見積もり（大事なもの見張る君の LLM）

### Bedrock の単価（us-west-2 のリージョン内、100 万トークンあたり。2026-10-26 時点）

| モデル | 入力 | 出力 | キャッシュ読み込み | キャッシュ書き込み |
|---|---|---|---|---|
| Claude Haiku 5.5 | $0.11 | $0.55 | $0.011 | $0.1375 |
| Claude Sonnet 5.5 | $2.20 | $11.00 | $0.11 | $2.75 |
| Claude Opus 5.5 | $4.40 | $22.00 | $0.22 | $5.50 |

- 課金はトークン単位の従量課金です。Anthropic のモデルは AWS Marketplace 経由で請求されます。
- バッチ推論は、On-Demand より 50% 安くなります（結果がすぐには返らないので、毎日の分析向き）。
- 毎回同じ指示文は、プロンプトキャッシュに載せると、2 回目以降の入力が約 10 分の 1 になります。

### 見積もり（月、730 時間）

前提（仮置き）:
- 1 時間に動く人でない主体を 150 とする（実数は未計測）。
- 1 主体の集計を約 500 トークンとする。
- 判断の基準を書いた指示文は約 3,000 トークンとし、キャッシュに載せる。1 回の呼び出しで 20 主体ずつ判定する。

| 案 | 中身 | 月の費用 |
|---|---|---|
| 毎時・Haiku | 毎時、全主体を Haiku で判定 | 約 $8 |
| 毎時・Sonnet | 毎時、全主体を Sonnet で判定 | 約 $160 |
| 毎日・Sonnet | 1 日分の集計（1 主体 2,000 トークン）を Sonnet で深く分析 | 約 $27（バッチなら約 $14） |
| 毎日・Opus | 同上を Opus で | 約 $55（バッチなら約 $27） |
| **推奨** | 毎時は Haiku でふるい分け、怪しいものだけ Sonnet で詳しく見る。毎日は Sonnet のバッチで振り返る | **約 $25〜$30** |
| （参考）生のログを Haiku に渡す | 1 時間 5 万件 × 300 トークン | 約 $1,200 |
| （参考）生のログを Sonnet に渡す | 同上 | 約 $24,000 |

- このほかに、集計の処理（Athena・Lambda・DynamoDB）で数ドル〜十数ドルかかる見込みです。
- 今日なに消したかわかる君は、別に約 $60/月かかります（ほとんどは S3 Inventory）。

## 7. 通知の間隔

1 時間と 1 日の 2 種類を用意します。どの検出にどちらを使うかは、別に決めます。決め方の軸の案は次のとおりです。

- **1 時間:** 戻せないもの、守りを弱めるもの、身に覚えがなければ即座に止めたいもの。
- **1 日:** 戻せるもの、振り返りのためのもの。

## 8. 決まっていないこと

- 通知の間隔の割り当て
- 「重要な操作」の最初の範囲（今日なにしたかわかる君）
- 共通の記録の形の細部
- 主体と本人の対応表の持ち方
- Slack のチャンネルと bot
- 誤報・見逃しの返し方（大事なもの見張る君）
- Bedrock の利用（Marketplace の購読、ログを LLM に渡すこと）が社内のルールで許されるか

## 9. 進め方の案

1. 今日なに消したかわかる君を先に仕上げます。出力を、共通の記録の形にそろえておきます。
2. 今日なにしたかわかる君と大事なもの見張る君は、別のアプリとして作ります。2 つ目の情報源（たとえば IAM の変更）を足すときに、共通の土台を作ります。情報源が 1 つのうちに土台から作ると、作りすぎになりやすいためです。
3. 大事なもの見張る君は、まず毎日の振り返り（Sonnet のバッチ）から始め、誤報と見逃しの具合を見てから毎時のふるい分けを足すのが安全です。
