# システム操作の通知と見張りの構想（今日なにしたかわかる君・大事なもの見張る君）

作成: 2026-10-26 ／ 伊藤

システムに対して行われた重要な操作を、本人やチームが気づけるようにする仕組みの構想です。最終的に、次の 3 つの仕組みを作ります。段階的に作るため、フェーズ 0〜5 に分けました。**フェーズ 0〜1 は伊藤が進めます。フェーズ 2 以降は、チームへの提案です。**

| 仕組み | 何をするか | 届け先 |
|---|---|---|
| 今日なに消したかわかる君 | 原本バケットの戻せない削除などを、必ず知らせる | MLOps チーム＋本人 |
| 今日なにしたかわかる君 | 自分が行った重要な操作を、本人に知らせる | 本人 |
| 大事なもの見張る君 | 人でない主体（アプリ・CI などのロール）の「いつもと違う」を、LLM で拾う | MLOps チーム |

## 1. 背景

S3 の原本バケット（消えると作り直せないデータを置くバケット）の守りを、段階的に固めてきました。

- バージョニング: ふつうの削除・上書きを戻せるようにした。
- バケットポリシー: 古い版の削除と守りを外す操作を、例外の主体だけに限った（12 本すべて、2026-10-26）。
- 削除の記録: 削除を記録する仕組みと、検証用のバケット（カナリア）を本番に置いた（2026-10-26）。

次は削除の報告を作る予定でした。設計を進めるうちに、次の 2 つが見えてきました。

- 「誰が・何を・いつ」を集めて本人に知らせる仕組みは、削除に限らず、IAM の変更や本番の設定の変更にも使える。
- 一方で、削除をした主体の多くは人ではない（アプリのロール、Databricks のロール、ライフサイクルなど）。人への通知とは、目的も届け先も違う。

そこで、全体を 3 つの仕組みに分けて構想し直しました。

## 2. フェーズの全体像

各フェーズの終わりに、それだけで役に立つものが残るように分けています。

| フェーズ | 中身 | LLM | 位置づけ |
|---|---|---|---|
| 0. 事実の層の土台 | 削除を記録する仕組みと、カナリア | なし | 済み |
| 1. 今日なに消したかわかる君 | 原本バケット 12 本の削除を、規則で必ず知らせる | なし | 伊藤が進める |
| 2. 今日なにしたかわかる君（毎日） | 人の重要な操作を、毎日本人に知らせる | なし | **提案** |
| 3. 大事なもの見張る君（毎日） | 人でない主体の異常を、毎日の振り返りで拾う | あり | **提案** |
| 4. 毎時の通知 | 戻せない操作を毎時に知らせる。見張る君も毎時にする | あり | **提案** |
| 5. 情報源を広げる | GitHub・Databricks・Okta の監査ログなど | — | **提案** |

この順にする理由:

- **フェーズ 1 を最初にする。** 要件が固まっていて、守りとして一番大事です。土台（フェーズ 0）もできています。
- **フェーズ 2 では LLM を使わない。** 規則だけで作れます。ここで、記録の形と、主体と本人の対応表を固めます。
- **LLM はフェーズ 3 から使う。** LLM の判断は確かめながら育てる必要があり、Amazon Bedrock の利用には社内の承認も要るためです。
- **毎時はフェーズ 4 から。** 毎日の運用で、量・誤報・費用の感覚をつかんでから毎時にするほうが安全です。

## 3. フェーズ 0: 事実の層の土台（済み）

すべての仕組みが使う「事実の層」の、最初の部分です。2026-10-26 に deploy しました（[cdk-apps#2267](https://github.com/turingmotors/cdk-apps/pull/2267)）。

- **集めるもの:**
  - S3 のイベント（何が消えたか）: EventBridge → Firehose → ログのバケット
  - CloudTrail の記録（誰が消したか）: 専用のトレイル → ログのバケット
  - S3 Inventory（何バイトか）: 毎日 → ログのバケット
- **カナリア:** 原本バケットと同じ条件の検証用のバケットを、本番に常設しました。削除を起こす Lambda で、記録のされ方を確かめられます。今は、監査の対象はカナリアだけです。
- **カナリアで確かめたこと:**
  - S3 のイベントと CloudTrail の記録は、リクエストの ID でつながる。
  - 一括削除も、オブジェクトごとに記録される。
  - 古い版の削除は、守りのバケットポリシーで拒否される。
  - 残り: ライフサイクルによる失効の記録（2026-10-27〜28 に確かめる）。

事実の層では、1 件の記録に次の項目を持たせる予定です。ほかの仕組みも、この形の記録を読みます。

- 誰が（主体と、分かれば本人）
- いつ・どのシステムで・何に・何をしたか
- 重要度・戻せるか
- 元の記録へのリンク

## 4. フェーズ 1: 今日なに消したかわかる君（伊藤が進める）

**目的:** 原本バケットで、戻せない削除や守りを外す操作が起きたら、必ず気づけるようにする。

- **知らせるもの:**
  - 原本バケット 12 本の、戻せない削除（古い版の削除、ライフサイクルによる失効）
  - 原本バケットのふつうの削除（削除マーカー。古い版から戻せる）
  - 守りの設定の変更（バケットポリシー・バージョニング・ライフサイクル）
- **規則で必ず拾います。** LLM の判断は確率的で、見逃しがありうるため使いません。取りこぼさないことが前提です。ほかの仕組みの判断で、この通知を消すことはできません。
- **届け先:** MLOps チームのチャンネル。主体が人なら、本人にもメンションします。
- **作るもの:**
  - トレイルを削除系の操作だけに絞る（12 本に広げると、作成の記録が月 400 万件ほどになるため）
  - 毎時の集計（Lambda・Athena）。単発の削除と一括削除の 2 通りのつなぎ方、まだ届いていない「誰が」の保留、重複の除去を含む
  - Slack への通知
  - 対象をカナリアから原本バケット 12 本に広げる
  - 仕組みが止まったときのアラーム
- **あとから足すもの（1b）:**
  - Inventory による日次の突き合わせ（取りこぼしを拾う最後の網）
  - 本人へのメンション（SSO のメールアドレスから引く）
  - 記録を置くバケットの改ざん対策（Object Lock）
- **前提:** Slack のチャンネルと bot。
- **終わりの条件:** カナリアで定期的に起こす削除が、毎回通知に出ること。2 週間、取りこぼしと誤報が無いこと。
- **費用:** 月約 $60（ほとんどは S3 Inventory）。

---

**ここから先（フェーズ 2〜5）は、チームへの提案です。** 進めるかどうか、進める場合の担当は、チームで決めたいと考えています（10 章）。

## 5. フェーズ 2: 今日なにしたかわかる君（毎日。提案）

**目的:** 自分の主体で行った重要な操作を、本人が翌日に振り返れるようにする。あわせて、認証情報が盗まれたときに、本人が「身に覚えのない操作」に気づけるようにする。

- **対象:** 自分の主体（SSO でログインした人）の操作だけ。人でない主体は、フェーズ 3 の大事なもの見張る君で扱います。
- **知らせるもの:** 重要な操作に絞ります。最初は、IAM・権限、バケットポリシー、データの削除、本番の設定くらいから始めます。普段から繰り返している操作は省きます。量が多いと読まれなくなり、身に覚えのない操作にも気づけなくなるためです。
- **書き方:** 1 件ごとに「戻せるか」を添え、戻せない操作が目立つようにします。
- **届け先:** 本人への DM。個人の操作をチャンネルに出すと、監視されているように感じる人がいるためです。
- **作るもの:**
  - 2 つ目の情報源として、CloudTrail の管理イベントを事実の層に取り込む（既存のトレイルで、追加の費用なし）
  - 主体と本人の対応表
  - 毎日の DM
- **LLM は使いません。** 「重要な操作」は規則の一覧で選びます。
- **終わりの条件:** 試しに受け取る人（たとえば伊藤）が 2 週間受け取り、量と中身が「読み続けられる」と判断できること。そのあと、チームの希望者に広げる。
- **費用:** 数ドル（集計の処理だけ）。

## 6. フェーズ 3: 大事なもの見張る君（毎日。提案）

**目的:** 人でない主体の「いつもと違う」操作を拾い、MLOps チームに知らせる。規則では書き切れない異常を拾う役です。

- **対象:** 人でない主体と、対応表に無い主体（9 章）。
- **拾うもの:** 普段と違う量・時間帯・操作の組み合わせ、初めて見る操作やリソースなど。
- **やり方:** 主体ごとに 1 日分の記録を集計し、普段（たとえば過去 14 日）との差を、LLM（Claude Sonnet）に判断させます。毎日の判断は、安いバッチ推論で行います。
- **最初は影の運用にします。** 通知はせず、判断を記録するだけにして、人が目を通します。誤報の具合を見てから、MLOps チームのチャンネルに出します。
- **誤報・見逃しを、チームが返せる仕組み**を持たせ、判断を育てます。
- **前提:** Bedrock の利用の社内承認（AWS Marketplace の購読、ログを LLM に渡すこと）。
- **終わりの条件:** 影の運用で、チームが「この量・この精度なら通知してよい」と判断できること。
- **費用:** 月約 $14（バッチ推論。見積もりは下）。

### LLM の使い方と安全

- **ログは集計・整理してから渡します。** 主体ごとに、操作の種類ごとの件数、エラーの件数、普段との差、初めて見る操作・リソースなどにまとめます。
- **生の文字列は、できるだけ渡しません。** CloudTrail には、操作した側が自由に決められる文字（オブジェクトのキー、ロールのセッション名など）が入ります。攻撃者がそこに指示を書けば、LLM の判断を曲げられるおそれがあります（プロンプトインジェクション）。
- **LLM の判断は、通知を「足す」方向にだけ使います。** 今日なに消したかわかる君が規則で拾ったものを、LLM が「報告不要」にして消すことはできないようにします。
- **実行場所は Amazon Bedrock のリージョン内（us-west-2）にします。** ログを社外に出さないためです。世界中のリージョンに振り分ける推論（Global）は約 10% 安いものの、米国の外で処理されうるので使いません。

### 費用の見積もり（月、730 時間）

前提（仮置き）:
- 1 時間に動く人でない主体を 150 とする（実数は未計測）。
- 1 主体の 1 時間分の集計を約 500 トークン、1 日分を約 2,000 トークンとする。
- 判断の基準を書いた指示文は約 3,000 トークンとし、キャッシュに載せる。1 回の呼び出しで 20 主体ずつ判定する。

| 案 | 中身 | 月の費用 |
|---|---|---|
| 毎日・Sonnet | 1 日分の集計を Sonnet で分析する（フェーズ 3） | 約 $27（バッチなら約 $14） |
| 毎日・Opus | 同上を Opus で | 約 $55（バッチなら約 $27） |
| 毎時・Haiku | 毎時、全主体を Haiku でふるい分ける（フェーズ 4） | 約 $8 |
| 毎時・Sonnet | 毎時、全主体を Sonnet で判定する | 約 $160 |
| **推奨（フェーズ 4 まで）** | 毎時は Haiku でふるい分け、怪しいものだけ Sonnet で詳しく見る。毎日は Sonnet のバッチで振り返る | **約 $25〜$30** |
| （参考）生のログを Haiku に渡す | 1 時間 5 万件 × 300 トークン | 約 $1,200 |
| （参考）生のログを Sonnet に渡す | 同上 | 約 $24,000 |

- 集計してから渡すと、生のログを渡す場合の 100 分の 1 以下になります。
- このほかに、集計の処理（Athena・Lambda・DynamoDB）で数ドル〜十数ドルかかる見込みです。
- 単価は付録にまとめました。

## 7. フェーズ 4: 毎時の通知（提案）

**目的:** すぐに止めたい操作に、1 日待たずに気づけるようにする。

- **今日なにしたかわかる君:** 戻せない操作・守りを弱める操作を、毎時の通知に移します。
- **大事なもの見張る君:** 毎時、Claude Haiku で全主体をふるい分け、怪しいものだけ Sonnet で詳しく見る仕組みを足します。
- **どの操作を毎時にするか**は、フェーズ 1〜3 の運用の結果を見て決めます。決め方の軸の案は次のとおりです。
  - **1 時間:** 戻せないもの、守りを弱めるもの、身に覚えがなければ即座に止めたいもの。
  - **1 日:** 戻せるもの、振り返りのためのもの。
- **費用:** 大事なもの見張る君の合計で、月約 $25〜$30。

## 8. フェーズ 5: 情報源を広げる（提案）

必要が出たものから足します。

- **GitHub:** deploy の起点の人（PR をマージした人）を、deploy のロールの操作に結びつける。
- **Databricks の監査ログ:** Databricks のロールの操作を、本人に結びつける。
- **Okta:** 認証まわりの重要な操作。
- **即時のアラート（オプション）:** 大量削除などで、即座に強く鳴らす。

## 9. 主体の振り分け（フェーズ 1〜3 に関わる）

**原則: 誰の通知にも載らない操作を作らない。** 対応表に無い主体は、すべて大事なもの見張る君に入れます。

| 主体 | 振り分け | 補足 |
|---|---|---|
| SSO の人（対応表にある） | 今日なにしたかわかる君 | 原本バケットの削除などは、今日なに消したかわかる君にも |
| GitHub Actions の deploy のロール | 大事なもの見張る君 | 起点の人が分かれば、その人の通知にも載せる（フェーズ 5） |
| アプリのロール | 大事なもの見張る君 | |
| Databricks のロール | 大事なもの見張る君 | 本人を引けるようになれば、人の通知にも（フェーズ 5） |
| 対応表に無い主体（持ち主不明の IAM ユーザーなど） | 大事なもの見張る君 | |
| root・BreakGlass | 今日なに消したかわかる君（常に即時にチームへ） | 使われること自体が異常 |
| ライフサイクルによる失効 | 今日なに消したかわかる君（原本バケットの場合） | |

## 10. チームに決めてほしいこと

1. フェーズ 2〜5 に進めてよいか。進める場合の担当。
2. 今日なにしたかわかる君の「重要な操作」の最初の一覧と、本人への DM という届け方でよいか。
3. 大事なもの見張る君の通知先（MLOps チームのチャンネル）と、誤報・見逃しの返し方。
4. Bedrock の利用の申請（誰が・どの範囲で）。承認に時間がかかるかもしれないので、フェーズ 3 に進むなら早めに申請したい。
