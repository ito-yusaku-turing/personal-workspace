# mono-e2e のリポジトリの肥大の解決

- 開始: 2026-11-04
- 状態: **完了（岩政さんに引き継いだ）**（2026-11-11）。本件は岩政さん（MLOps）が引き取った。結論は [../../documents/findings.md](../../documents/findings.md)
- 所属: project:mono-e2e-repo-size

mono-e2e のリポジトリが 2026-10 末から急に重くなり、clone や fetch に時間がかかるようになった。原因を調べ、手元と、ほかの人の clone の両方で重さを解消する。

## 背景・目的

- 2026-11-04 に「ここ一週間くらいで急にサイズが重たくなった」ことに気づき、コミットログから原因を調べた（personal-workspace のセッション。そのときは資料に残していなかったので、2026-11-11 にセッションの記録から書き起こした）。
- 目的は 2 つ。
  - **手元**: 自分の clone を軽くする。
  - **根本**: ほかの人の clone も重くならないようにし、再発を防ぐ。

## 発端の相談（2026-11-11 に共有を受けた）

この workstream は、次の相談を受けて起票した（投稿者・投稿先は未記録）。

> **Task**: 実験用途のクソデカファイルが commit される問題の対策をしたい
>
> 最近 fullcombo の学習用 workspace 以下の肥大化が進んでいて、現在 550MB 程度にまで膨らんでいます。種別に見ると、支配的なのは uv.lock と Python ファイルで、合わせて 360MB 程度あります。残りの大きな割合を占めているのが実験用のリソースです。
>
> 根本的には、ユーザが手動で用意した実験用の（軽量な）リソースをクラスタ非依存の共有物にする方法がないのが問題だと考えられます。そこで、たとえば以下のような解決策がありえます。
>
> - exp resource を管理する仕組みを作って、backend-api 経由で解決できるようにして、それを利用するよう促す
> - クラスタ間で自動 sync される軽量ファイル向けの領域を整備し、そこを利用するよう促す
>
> 短期的には Git LFS を使う方針で緩和しようと思うのですが、中長期的な解決の方向性を MLOps と相談できると嬉しいです。

## 相談の事実確認（2026-11-11）

手元の `origin/main`（2026-11-10 17:50 の `5654fbdf03`）で `projects/fullcombo/workspace` を集計した。

**投稿の数字は正しい。** ただし、それは展開したファイルの合計の話。Git が保存・転送するときの大きさ（圧縮後）で見ると、workspace の分は小さい。

| 項目 | 投稿 | 確認した値 |
|---|---|---|
| workspace の合計 | 550MB 程度 | 573.7MB（≒ 547MiB）、17,811 ファイル。checkout の実体は `du` で 519MB |
| uv.lock と .py | 合わせて 360MB 程度 | .py 192.0MB（6,853 個）＋ uv.lock 173.0MB（1,160 個、平均 149KB）＝ 365MB |
| 残り | 実験用のリソース | .csv 56.5MB、.json 49.0MB、.txt 35.2MB、.png 19.3MB、.gz 11.9MB など |

圧縮後の大きさ（`objectsize:disk`。pack の作り方で多少変わる）:

- 同じ内容のファイルは 1 つにまとめて保存されるので、中身の異なるファイルだけで 399MB。差分圧縮もかかり、**ディスク上では 66MB**。
- uv.lock は 173MB → **4.3MB**、.py は 192MB → **17MB**。実験ごとにほぼ同じものを写しているので、よく縮む。圧縮後に一番大きいのは .png（18.7MB）。
- main の履歴の中で workspace に現れた blob は全部で 584.7MB、ディスク上で 112MB。**main の履歴全体でもディスク上で 338MB**。
- 手元の pack は 2.12GiB。つまり **約 1.8GB は main の外のブランチの分**で、下の「2026-11-04 の調査の結果」の画像のブランチ（1.3GB）がその大半。

ほかに分かったこと:

- **main の workspace に「クソデカ」なファイルは無い**。一番大きいのは `shingo_yokoi/constants/blinker_label_edits/exp_3049_1f1b124a.csv`（12MB）。大きい画像は main にマージされていないブランチにある。
- 1 人の分が大きい: `shingo_yokoi` が 253.5MB（7,973 ファイル）で全体の 44%。
- 増え方（main の木のサイズ）: 2026-08-01 に 0.5MB → 09-01 に 221MB → 10-01 に 471MB → 11-01 に 664MB（最大）→ 11-10 に 574MB（減った）。workspace は 2026-07-09 に作られた。
- mono-e2e は既に Git LFS を使っている（`.gitattributes` で `projects/open-street-map-renderer/tests/fixtures/*.mbtiles` だけ）。

見立て（エージェントの考え。まだ相談者と合わせていない）:

- workspace の肥大は、**checkout の大きさとファイル数**（1.8 万）の問題としては本当にある。しかし、**clone・fetch が重い主な原因ではない**。主な原因は、main にマージされない作業ブランチに積まれた画像。
- Git LFS が向くのは画像や PDF などのバイナリ。uv.lock や .py は LFS に向かない（差分やレビューが見えなくなり、すでによく圧縮されている）。また、LFS は入れた後の commit にしか効かず、履歴に残った分は減らない。

## Devin の調査結果（2026-11-11 に共有を受けた）

相談を受けて Devin が調べた結果。mono-e2e の `origin/main` の `54bb06d`（2026-11-09 11:57）で集計している。リンク先の #dev_mono_e2e のスレッドは、権限が無く読めなかったとのこと。

**推奨アクションは、ユーザーの指示で保留にしている（2026-11-11）。** 採るかどうかはまだ決めていない。

### 現状（実測）

- 合計 554MB・17,391 ファイル。同じ内容の blob をまとめると 384MB。2026-09-01 時点は 149MB、2026-11-01 時点は 636MB。
- uv.lock は 1,133 ファイル・169MB。同じ内容が多く、中身の異なるものは 54MB。
- .py は 186MB。そのうち 143MB は各 exp の `main.py`（1,122 個、平均約 130KB）。学習スクリプトを exp ごとにコピーしているのが主な原因。
- データ系（csv / json / txt / png / gz など）は 170MB（中身の異なるもの 131MB）。1MB を超えるファイルは 35 個・91MB だけで、残りは中小のファイルが大量にある。

### LFS を短期策にするときの注意点

- LFS で減らせるのはデータ系の約 170MB まで。`main.py` のコピーと uv.lock は減らない。
- すでに commit された blob は履歴に残る。「pack は現在 2.1GiB で、履歴を書き換えない限り減らない」としている。
- LFS は mbtiles ですでに使っている（`.gitattributes`）。workspace に広げるなら、各クラスターに git-lfs が入っているか、GitHub LFS の容量と帯域に余裕があるかを先に確かめる。
- `.pre-commit-config.yaml` にはファイルサイズの上限のチェック（`check-added-large-files`）が無い。workspace に限って足せば今後の大きなファイルは止められるが、中小のファイルが大量に増えるのは止められない。

### 中長期策に使えそうな既存の仕組み

- **案 1（exp resource を backend-api で解決する）**: backend-api の `routers/experiments.py` に、Experiment の CRUD と `s3_prefix` がすでにある（`EXPERIMENT_ALLOWED_PROJECTS` の既定値は `fullcombo,wam`）。ここに「resource の URI の一覧」を足す形にできる。
- **案 2（クラスター間で sync される領域）**: fullcombo の `fullcombo.runtime.data_cloud` が、クラスターごとの保存先（AWS S3、GCP GCS、GMO と gaggle の `/data`）を 1 か所で解決している。ここに `exp_resources` のような root を足し、実体の sync は cluster-daemons の ansible-local（各 login ノードで定期実行）に任せる形が考えられる。

### 判断が要る点として挙げた担当者

- どちらの案にするか、sync の主体を backend-api と cluster-daemons のどちらにするかは、チームの設計判断。
- Shuhei Tsukamoto さん: backend-api の experiments router と schema を直近で最も多く変えている（案 1 の観点）。
- Kazuki Odo さん: cluster-daemons の直近のコミットのほとんど（案 2 の観点）。

### Devin の推奨（保留中）

短期:

- pre-commit に `check-added-large-files` を `projects/fullcombo/workspace` に限って足し、上限を 1MB 程度にする（現状で 1MB を超えるのは 35 ファイル・91MB）。
- `main.py` を exp ごとにコピーする運用を見直す（143MB で、最も効く箇所）。共通部分を fullcombo 本体から import できるかは fullcombo 側の判断。
- LFS は全体に広げない。減らせるのはデータ系の最大 170MB だけで、各クラスターへの git-lfs の導入や、GitHub の LFS の容量・帯域の管理という運用の負担が増える。

中長期（案 2 に近い形）:

- 実験用リソースの正本を object storage の 1 か所（例: S3 の `exp_resources/<user>/<exp>/`）に置く。
- `fullcombo.runtime.data_cloud` に resolver を足し、各クラスターでは初回のアクセスで取ってきてローカルにキャッシュする。
- この形なら、新しい sync のデーモンや backend-api のスキーマの追加は要らない。案 1 は、必要になってから Experiment の `s3_prefix` と結び付ければ足りる。
- 未確認の前提: GCP・GMO2・gaggle から同じバケットを読めるか。読めなければ ansible-local での sync（案 2 そのもの）が要る。

やらないほうがよいこと:

- 履歴を書き換えて pack（2.1GiB）を縮める作業は全員の clone に響くので、今回の範囲に含めない。

pre-commit の PR は Devin が作れると申し出ている。

### エージェントの所見（Devin の結果と、上の事実確認を突き合わせて）

- 数字はこちらの集計とほぼ合う。差は集計したコミットの違い（Devin は 11-09 の `54bb06d`、こちらは 11-10 の `5654fbdf03`）。
- **「pack 2.1GiB は履歴を書き換えない限り減らない」は、そのままでは正しくない。** 2.1GiB は全ブランチを取った手元の clone の大きさで、main の履歴全体は圧縮後 338MB しかない。残りの約 1.8GB は main の外のブランチの分なので、**それらのブランチを消せば、履歴を書き換えなくても新しい clone・fetch には届かなくなる**（手元は参照を消して gc すれば減る）。
- Devin の結果は「checkout したときの大きさ」の話が中心で、圧縮後の大きさ（workspace は main で 66MB）と、main の外のブランチの画像（1.3GB）には触れていない。clone・fetch が重い件への対策としては、ブランチの扱い（下の「対策の案」の 2）が抜けている。

## 考察（2026-11-11）

エージェントの考察。根拠は mono-e2e の `origin/main`（2026-11-10）と GitHub の設定（`gh api`、2026-11-11）。推測を含むところは「推測」と書いた。

### 調べて分かった運用ルールの現状

| ルール | 導入 | 中身 |
|---|---|---|
| 実験ごとの workspace（ADR 0002） | 2026-07-08 | `workspace/<user>/exp_XXXX/` ごとに `main.py`・`pyproject.toml`・lock file を持つ。目的は実験の再現性 |
| commit の関所（テンプレートの `.gitignore`） | 2026-07-28 | 新しい exp は `*` で全部を無視する。commit する価値があると思ったら、その行を消す（消すと全部が対象になる） |
| 重複のチェック（`clean_config_lint.py duplicates`） | 2026-11-03 | 150KiB 以上で中身が同じファイルが同じ workspace か `src/` にあれば CI がエラーにする |
| uv.lock を既定で外す（[mono-e2e#7509](https://github.com/turingmotors/mono-e2e/pull/7509)、Devin） | 2026-11-09 | ADR 0002 に「過去の実験の再現を行わなくなった」と注記。**すでに commit 済みの 1,160 個は残っている** |
| 大きいファイルの扱い（skill `fullcombo-clean-config`） | — | 「main に入った大きいファイルは履歴に残り続けるので、merge の前に移す」。エージェント向けの文書にしか書かれていない |
| マージしたブランチの自動削除（GitHub） | — | `delete_branch_on_merge: true` |

ほかに確かめたこと:

- `projects/fullcombo/workspace` に exp は 1,026 個（`main.py` の数）。exp の `.gitignore` は 569 個しか無く、半分ほどはテンプレートを通さずに（コピーなどで）作られている（推測）。
- uv.lock の追加は月に 260〜370 個（2026-08〜10）。
- 1 つの PR が大きい例: [mono-e2e#7469](https://github.com/turingmotors/mono-e2e/pull/7469)（793 ファイル・55 万行の追加）。
- 現場は自分たちでも減らしている: `shingo_yokoi` さんが同じ中身のデータを `constants` にまとめた（[mono-e2e#7254](https://github.com/turingmotors/mono-e2e/pull/7254) で 155 万行、[mono-e2e#7257](https://github.com/turingmotors/mono-e2e/pull/7257) で 20 万行の削除。11/3〜4）。11/1 の 664MB から 11/10 の 574MB に減ったのはこのため。
- GitHub 上のブランチは 1,644 本、開いている PR は 377 件。**開いた PR の無いブランチが 1,200 本以上ある**。自動削除はマージしたときにしか効かないので、閉じた PR やマージしない作業ブランチは残り続ける。
- 原因のブランチは 2026-11-11 時点でも残っている: [mono-e2e#6875](https://github.com/turingmotors/mono-e2e/pull/6875)（OPEN、最終更新 10/30）、[mono-e2e#7061](https://github.com/turingmotors/mono-e2e/pull/7061)（OPEN）、[mono-e2e#6700](https://github.com/turingmotors/mono-e2e/pull/6700)（OPEN）、`feat/fullcombo-back`。GitHub が示すリポジトリのサイズは約 2.2GB。
- `.pre-commit-config.yaml` には fullcombo の項目もファイルサイズの上限も無い。`.gitignore` は `output/` を無視しているが、`results/` は無視していない。

### 1. 現場の運用から読み取れること

- **実験 1 つが 1 ディレクトリで、前の実験をコピーして作る。** `main.py` は 1 個 130〜350KB の学習スクリプト全体で、exp ごとに写している。4 か月で 1,000 個を超えた。再現性のために ADR 0002 で選んだ形で、写すのは設計どおり。
- **実験に使う軽いデータ（ラベルの表・scene の一覧・manifest）も Git に置いている。** クラスターをまたいで共有できる置き場が無いので、Git が共有の置き場の代わりになっている。相談の投稿の見立てと合う。
- **Git に実験の記録を残す文化がある。** 実験を PR にして main に入れている。大きな PR もある。
- **今回の問題のケース（ego mask）では、Git のブランチをファイルの受け渡しに使っていた（推測）。**
  - 2 日で約 40 回、修正版のマスク画像と検収用の PDF を作業ブランチに積んだ。PR には自分で「作業用・マージ対象外」と書いている。
  - 検収する人に見せるため、またはクラスターと手元の間で受け渡すために、Git を使ったと考えられる。結果の画像を共有する正式な置き場が無いことの表れ（推測）。
  - 最終版だけを別の PR（[mono-e2e#7038](https://github.com/turingmotors/mono-e2e/pull/7038)）で squash マージした。作業ブランチは開いたまま残った。本人は、main を汚していないので問題ないと考えている可能性が高い（推測）。**main の外のブランチも全員の clone に入るとは知られていない。**
  - `codex/vehicle-id-mask-probe` のように、エージェントが作ったブランチも同じように残っている。
- **現場は肥大に気づいていて、main の側では自分たちで減らしている**（データの集約、重複のチェック、uv.lock を外す）。ただ、どれも main の checkout の大きさが対象で、ブランチは視野に入っていない。相談の投稿と Devin の調査も同じ。

### 2. 運用ルールの問題（ルールが無いところを含む）

- **ルールが main しか見ていない。** 重複のチェックも skill の注意書きも「main に入れる前」が前提になっている。マージしないブランチに何を積んでも止まらず、残り続ける。今回の 1.3GB はまさにここから入った。
- **ブランチの後始末のルールが無い。** 自動削除はマージのときだけ効く。閉じた PR、マージしない作業ブランチ、PR の無いブランチ（1,200 本以上）の扱いが決まっていない。
- **バイナリ（画像・PDF・結果）を Git に入れないルールが無い。** `.gitignore` は `output/` だけを無視していて、`results/` は無視していない。ファイルサイズの上限は、pre-commit にも GitHub 側にも無い（GitHub の 100MB の上限だけ）。
- **commit の関所が「全部か無しか」になっている。** `*` の行を消すと、中の結果ファイルまで全部が対象になる。実験に要るファイルだけを選ぶ仕組みになっていない。
- **ルールが届く範囲が狭い。** 大きいファイルの注意は、エージェント向けの skill にしか書かれていない。人が読む `workspace/README.md` には無い。テンプレートを通さずに作った exp には、関所の `.gitignore` も無い。
- **ルールを入れたのが最近で、入る前の分が残っている。** uv.lock の除外（11/9）と重複のチェック（11/3）より前に commit した分は、そのまま main にある。
- **前提が変わっている。** ADR 0002 は再現性のために exp ごとに写す形を選んだ。しかし 11/9 の注記で「過去の実験の再現を行わなくなった」とされた。`main.py` を写す運用も見直す余地がある（fullcombo 側の判断）。
- **共有の置き場が無い**（相談の投稿のとおり）。この点はルールより仕組みの問題で、ここが埋まらない限り、Git が置き場の代わりに使われ続ける。

### 3. 解決の方法は明確か

問題が 2 つ混ざっている。分けて考えると、片方は明確で、もう片方は複雑。

**A. clone・fetch が重い（相談の発端の体感）: 原因も解決も明確で、安い。**

- 原因は特定済み（main の外のブランチ、約 1.3GB＋α）。main の履歴全体は圧縮後 338MB。
- 解決は、[mono-e2e#6875](https://github.com/turingmotors/mono-e2e/pull/6875) などを閉じてブランチを消すこと。**履歴を書き換える必要は無い**。新しく clone・fetch する人には届かなくなる。すでに取った人は、参照を消して gc すれば減る。
- 要るのは担当の方（Shuhei Goda さんほか）の同意だけ。
- 再発の防止も比較的はっきりしている。ブランチの後始末のルール（閉じた PR のブランチを消す、古いブランチを定期的に掃除する）と、ブランチにも効くサイズの上限（GitHub の push ruleset のファイルサイズの制限など。この組織のプランで使えるかは未確認）を入れる。

**B. workspace の肥大（相談の投稿の主題）: 複雑。**

- 影響は主に checkout の大きさとファイル数（1.8 万）。圧縮後は 66MB しかないので、clone の重さへの寄与は小さい。急ぎ度は A より低い。
- 原因が設計（exp ごとに写す ADR 0002）と、仕組みが無いこと（共有の置き場）にあるので、ルールを 1 つ足しても解決しない。
- 関わる人が多い。fullcombo 側（`main.py` を写す運用の見直し）、MLOps（置き場）、backend-api（案 1）、cluster-daemons（案 2）。
- 技術的に確かめていない前提がある。GCP・GMO2・gaggle から同じ置き場を読めるか（Devin の指摘）。
- Git LFS は、画像を入れる場合には効く（checkout しないブランチの LFS の中身は落ちてこない）。ただし、運用の負担（各クラスターへの導入、容量と帯域）がある。また、uv.lock と `.py` には効かない。

**まとめ**: A を先に片付ければ、体感の重さは大きく減る見込み。B は中長期の設計の相談として、MLOps と fullcombo 側で時間をかけて決めるのがよい。相談の投稿も Devin の調査も B だけを扱っていて、A が抜けている。相談者と話すときは、まず A を伝えるのがよさそう。

### Slack での共有（要約）

> mono-e2e の肥大化を止めるのと、GPU クラスターでの開発体験を上げるために、クラスター間の自動データ共有をやった方がいいかも？のデザイン。

> 2. `s3://cluster-shared-files-767397804933/shared/<user>/<共有先のパス>` に送られる（ユーザー専用の空間）。
> 3. 各クラスターの daemon が 1 分に一度 S3 との差分を見て、`/data/shared/<user>/<共有先のパス>` に無ければ取り、S3 側で消えていれば消す。

### 設計の要点（Notion）

- **目的**: fullcombo の workspace で GitHub に置くファイルの数とサイズを減らす。MLE がクラスター間でファイルを簡単に共有できるようにする。
- **背景の書き方**: uv.lock は miwa さんの対応（[mono-e2e#7509](https://github.com/turingmotors/mono-e2e/pull/7509) のことと思われる）で防げる。Python ファイルは個別に対応する。この設計の対象は実験用のリソース。Git LFS も monorepo を大きくするので、なるべく使いたくない。
- **書き込み**: 窓口は backend-api だけ。利用者は S3 の資格情報を持たず、presigned URL で上げる。backend-api が検査（サイズ・SHA-256・種類・秘密情報）してから公開する（fail-closed）。
- **配布**: 各クラスターの daemon（mlops-slurm-operator に処理を足し、systemd timer で起動）が backend-api から差分を取り、`/data/shared/<owner>/<path>` に置く。正本は backend-api の DB（Supabase Postgres）。put したクラスターには `.inbox/` を通した近道で十数秒で反映する。ほかのクラスターには 1〜2 分で届く（計算値）。
- **制限**: 1 ファイル 64MiB まで。拡張子の allowlist はコード・設定・テキストだけ（`.py` `.sh` `.toml` `.yaml` `.json` `.jsonl` `.txt` `.md` `.csv` `.tsv` など）。**画像・PDF・`.npz` などのバイナリは対象外**。パートナーデータ・個人情報・顧客データも対象外。
- **版と削除**: S3 の versioning と DB で版を残す。本人の削除は論理削除、管理者の取り消し（revoke）は物理削除。
- **作るもの**: 9 本の PR（cdk-apps 2、mono-e2e の db-models・backend-api 2・jadd-cli、cluster-daemons 2、mono-turing-infra）。
- **確認したい相手**: インフラチーム（daemon の監視と復旧、容量、代わりのサービスの有無）、AI チーム（要望、64MB で足りるか）、gmo2 / gaggle の担当（外部事業者が root を持つ環境に置いてよいか、S3 への帯域）、cluster-daemons の担当、backend-api の担当、セキュリティの担当。

## ブランチを消せば軽くなるかの確認（2026-11-11）

問い: 重いファイルの載ったブランチを GitHub で消せば、clone・pull の重さは確実に解消されるか。

**結論: 新しく clone する人と、しばらく fetch していない人には、消した時点から効く。Git の仕組み上、ほぼ確実。** ただし、すでに取った人の手元は減らない。また、いくつか例外がある。

仕組み:

- clone・fetch では、サーバー（GitHub の upload-pack）は、相手が求めた ref からたどれるオブジェクトのうち、相手がまだ持っていないものだけを送る。どの ref からもたどれなくなったオブジェクトは、GitHub の中に残っていても送られない。
- 送るオブジェクトの差分圧縮の元が、送らないオブジェクトだった場合も、送らないオブジェクトは付いてこない（圧縮し直すか、元を外して送る）。

手元（`/usr/app/mono-e2e`、fetch は 2026-11-10）で確かめたこと:

- `shuhei_goda/ego-mask-sam2-boundary-parts` の先端は、ほかのブランチにもタグ（598 本）にも含まれていない。
- 届くオブジェクトの量（`git rev-list --objects --disk-usage`。手元の pack での圧縮後の値）:

| 対象 | 量 |
|---|---|
| 全ブランチ＋タグ（いまの clone） | 2,245MB |
| ego のブランチを除く | 863MB |
| 4 本（ego、`shuhei_goda/vehicle-id-end-to-end`、`codex/vehicle-id-mask-probe`、`feat/fullcombo-back`）を除く | 580MB |
| main だけ | 338MB |

例外と注意:

1. **すでに取った人の手元は減らない。** そもそも取った後の pull では、同じものは二度と届かないので、いま pull が重いわけではない。重いのは、10/29 以降まだ fetch していない人と、新しく clone する人。手元を減らすには、各自が参照を消して gc する（「対策の案」の 1）。既定では `git pull` は消えたブランチの参照を消さない（`fetch.prune` は既定で false）。`git fetch --prune` をしても、gc するまでは容量は減らない。
2. **PR の参照（`refs/pull/6875/head` など）は GitHub に残る。** ブランチを消しても PR の参照は消えず、利用者には消せない（GitHub のサポートに頼む必要がある）。既定の clone・fetch は `refs/pull/*` を取らないので、ふつうは影響しない。ただし、`git clone --mirror`（ミラーやキャッシュ）、fetch の設定に `refs/pull/*` を足している人、`gh pr checkout 6875` をした人には届く。
3. **手元に持っている人が push し直せば戻る。** 担当の方に事情を伝えて、合意のうえで消す必要がある。PR は、head のブランチを消すと自動で閉じる。
4. **GitHub が示すリポジトリのサイズ（約 2.2GB）はすぐには減らない。** GitHub の中の掃除は GitHub 次第。clone で届く量とは関係ない。
5. **数字は見積もり。** 手元の pack の圧縮のされ方で計算しているので、GitHub から実際に届く量は多少違う。消した後に、新しく clone して実測するのが確実。

## なぜこうなったかの見直し（2026-11-11）

問い: 岩政さんの経緯と設計を見ても、「ML エンジニアに、複数の環境の間でファイルを同期したい需要があった」が原因という考察は変わらないか。

**結論: 半分だけ当たっていて、重い件（A）の原因としては外れていた。** 問題を分けると、原因も分かれる。

### A（作業ブランチの 1.3GB の画像）: 同期ではなく「人が見る」ための置き場が無かった

[mono-e2e#6875](https://github.com/turingmotors/mono-e2e/pull/6875) と [mono-e2e#7038](https://github.com/turingmotors/mono-e2e/pull/7038) の本文に、目的がはっきり書かれていた（2026-11-11 に `gh pr view` で確認）。

- #6875 の題は「[作業用・マージ対象外] SAM2車体マスク改善・検収履歴」。本文は「車体マスク v2 の作成・修正・検収履歴と、共通マスクの比較画像を**保持する**作業 PR」。
- 「最終一覧から参照する 381 枚の JPEG は `results/ver2_published_previews_20261030/` に同一バイト列で保持し、**固定 commit から参照**しています」。
- main に入った `results/ver2/README.md` には、作業ブランチのコミット `13937d3`（10/30）の画像への GitHub のリンクが **335 個**ある。「採択欄のカメラ名を押すと学習画角の重畳画像へ移動します」。
- 一方で、正本（PNG・参照点・元画像）は S3 に sha256 付きで保存し、往復の照合まで済ませている。main には 5.24MiB だけを入れ、「旧画像 blob を親コミットに残さないよう 1 コミットに整理」している。

読み取れること:

- **作業ブランチは、検収用の画像のギャラリー（ブラウザーで見る・リンクで示す場所）として使われていた。** クラスター間の同期のためではない。
- 作業はとても丁寧で、Git の大きさにも気を配っている。**main に入れないことには気を配ったが、マージしないブランチも全員の clone に入ることは考えに入っていなかった**（推測）。ルールが main しか見ていないこと（考察の 2）と合う。
- 正本の置き場（S3）はあるが、**S3 の画像はブラウザーで見たりリンクで人に示したりしにくい**。人が画像を見比べて検収するには、GitHub の Markdown とリンクが一番手軽だった（推測）。
- 2 日で 49 コミット（すべて shuhei_goda さん名義）、PR の本文の書き方（「ユーザー確認に基づき」）から、コーディングエージェントが作業していた可能性が高い（推測）。エージェントが main の外のブランチに成果物を積む流れが、今後も増える恐れがある。
- 岩政さんの設計は画像・PDF を対象外にしているので、この需要には応えない。

### B（main の workspace の肥大）: 原因は 3 つあり、同期の需要はその 1 つ

| 中身 | 量（展開後） | 原因 |
|---|---|---|
| uv.lock | 173MB | ADR 0002 の、再現性のために exp ごとに lock を持つ設計。同期とは関係ない。11/9 に既定で外した |
| `main.py` などの `.py` | 192MB | 同じく ADR 0002 の、exp ごとに学習コードを写す設計。同期とは関係ない |
| 実験用のリソース（csv・json・txt など） | 約 170MB | **クラスターをまたいで使えるようにしたい**（同期の需要）と、実験の記録として一緒に残したい、の両方と思われる（後者は推測） |

- 「同期の需要」が効いているのは 3 つめだけ。岩政さんの設計の背景も、uv.lock と Python ファイルは別に対応するとし、対象を実験用のリソースに絞っている。
- 前の考察（「1. 現場の運用から読み取れること」）では、A の作業ブランチを「Git をファイルの受け渡しに使っていた」と推測し、クラスターと手元の間の受け渡しの可能性も挙げていた。PR の本文から、受け渡しではなく**閲覧と参照**のためだったと分かったので、ここで直す。

### 見直した原因のまとめ

1. **人が成果物（画像）を見る・示す置き場が無い** → GitHub がギャラリーの代わりになった（A の直接の原因）。
2. **ルールと注意が main しか見ていない** → マージしないブランチに積むのは安全だと思われた（A を許した条件）。
3. **exp ごとに写す設計（ADR 0002）** → uv.lock と `.py` が増えた（B の大半）。前提の再現性は 11/9 にやめている。
4. **クラスターをまたいで使えるデータの置き場が無い** → 実験用のリソースが Git に入った（B の一部）。岩政さんの設計はここに応える。

補足: main の README のリンクは、ブランチ名ではなくコミット `13937d3` を指している。このコミットは `refs/pull/6875/head` の祖先なので、ブランチを消しても GitHub の画面ではたどれる見込み（PR の参照は消えないため。実際に消して確かめてはいない）。clone には届かない。

## 岩政さんの案の代わりになる実装の考察（2026-11-11）

エージェントの考察。岩政さんの案（「岩政さんの取り組み」）がやろうとしていることを要件に分け、それぞれ別の実装で満たせるかを考えた。どれもまだ誰とも話していない。

### 案が満たそうとしている要件

1. どのクラスターでも、同じパスで同じファイルを読める。
2. 誰が・いつ・何を置いたか追える。
3. 版が残り、誤って消しても戻せる。
4. 大きさ・種類・秘密情報で、置けるものを絞る。
5. put したクラスターには、すぐ反映する。
6. その結果、Git に置かずに済む。

案の要点は、**配る側（daemon）が各クラスターの `/data/shared/` に先回りして置く**こと（push 型）。版・履歴・取り消し・秘密情報の検査を、DB と backend-api で自前で作る。

### 判断の分かれ目

| 分かれ目 | 案の選択 | ほかの選択 |
|---|---|---|
| いつ届けるか | 先に配る（daemon が 1 分ごと） | 使うときに取りに行く（ジョブの開始時） |
| 版・履歴を何で持つか | 自前の DB（3 表）と S3 の versioning | Git、S3 の versioning だけ、既存の道具 |
| 実験とデータを何で結ぶか | パスだけ（`/data/shared/<owner>/<path>` の最新版） | 中身のハッシュ（sha256）で固定する |

### 代わりの実装

確かめたこと（2026-11-11、mono-e2e の `origin/main`）:

- `jadd backup dump / load / ls / rm` がすでにある（`routers/backup.py`）。ユーザーごとの S3 の領域（`s3://{BACKUP_BUCKET}/{user_name}/`）に presigned URL で置き、自分の領域にしか書けず、読むのは全員に開いている。監査ログも残す。gaggle の容量の逼迫を受けて作られた退避用。バケットに versioning は無い。
- fullcombo の `runtime/data_cloud.py` は、クラスターごとの保存先（AWS の S3、GCP の GCS、GMO・gaggle の `/data`）を 1 か所で解決している。
- 各クラスターには awscli・rclone・gh・git-lfs が配られている（Notion の設計書の「確認済みの事実」）。
- mono-e2e の CI には TruffleHog がある（`.trufflehog-exclude-paths`）。

**実装 1. 使うときに取りに行く（pull 型）**

- ジョブの開始時（または `data_cloud` の resolver の中）で、backend-api から presigned GET をもらって S3 から取り、ノードのローカルに sha256 をキーにしてキャッシュする。Devin が最初に推奨した形。
- 利点: daemon が要らない。`/data/shared/` の権限・singleton・watchdog・cursor の問題がまるごと無くなる。即時反映（`.inbox/`）も要らない（取りに行けば常に最新）。外部事業者が root を持つクラスターにも、使うときにしか置かれない。
- 欠点: ジョブの開始時に backend-api と S3 に届く必要がある。GMO・gaggle から S3 への帯域は未確認（案でも同じ）。

**実装 2. 既存の `jadd backup` を広げる**

- 実装 1 の取りに行く道具として、`jadd backup dump / load` をそのまま使うか、`jadd share` を同じ作りで足す。バケットに versioning を付け、種類と秘密情報の検査を足す。
- 利点: presigned URL・ユーザーごとの領域・監査ログという骨組みがすでにある。新しく作るものが一番少ない。
- 欠点: 退避用として作られているので、用途を混ぜるなら名前と保存の方針（いつ消すか）を分ける必要がある。

**実装 3. Git にはハッシュの一覧だけを置き、中身は S3 に置く**

- 実験のディレクトリーに、小さな一覧（パス → sha256・大きさ）を commit する。中身は S3 に sha256 をキーにして置き、実装 1 の方法で取りに行く。DVC や git-annex と同じ考え方で、自前でも数百行で作れる（推測）。
- 利点: **実験とデータの組み合わせが Git に残る**。いつの実験がどの版のデータを使ったかが commit で分かる（いまの「実験の記録として Git に置きたい」需要にも応える。この需要は推測）。履歴・取り消し・レビューは Git のものを使える。同じ中身は 1 つしか置かれないので、コピーしても増えない。
- 欠点: 「最新版を共有する」使い方には一手間かかる（一覧を更新する）。DVC を使うなら、各クラスターに S3 の読み取りの資格情報が要る。

**実装 4. 置き場の同期を既存の道具でやる**

- 各クラスターで `rclone sync`（または `aws s3 sync`）を systemd timer で回し、S3 の共有バケットを `/data/shared/` に写す。版は S3 の versioning、監査は CloudTrail のデータイベントか S3 のアクセスログに任せる。
- 利点: 案の push 型は保ったまま、差分の API・DB の 3 表・cursor を作らずに済む。
- 欠点: 各クラスターに S3 の読み取りの資格情報が要る（案は backend-api を通すことで避けている）。daemon の監視の問題は残る。S3 で消すと全クラスターで消える（案と同じ）。

**実装 5. S3 をそのままマウントする**

- Mountpoint for Amazon S3、rclone mount、gcsfuse などで、共有バケットを各クラスターに読み取り専用でマウントする。
- 利点: 同期の状態を持たない。常に最新。
- 欠点: 計算ノードに FUSE を入れる必要がある。AWS の外からの遅延。外部事業者のクラスターに入れてよいか。学習中に S3 が遅いとジョブが詰まる。

**実装 6. 別の Git リポジトリにする**

- 案が置けるのはテキスト（コード・設定・csv など）で 64MB までなので、**そもそも Git が得意な種類**。実験用のリソースを mono-e2e から別のリポジトリに分ければ、版・履歴・作者・取り消し・レビュー・秘密情報の検査（CI の TruffleHog）がすべて Git と GitHub で手に入る。各クラスターは定期的に pull するか、ジョブの開始時に取る。
- 利点: 新しく作るものがほぼ無い。案が DB で作ろうとしている機能の多くは、Git がすでに持っている。
- 欠点: リポジトリが 1 つ増える。Git を使う以上、置く人が commit・push の手間を負う。大きくなれば同じ問題がまた起きる（ただし mono-e2e とは切り離される）。

### 比べると

| 実装 | 新しく作る量 | クラスター側の運用 | 実験とデータの固定 | 外部のクラスターへの配慮 |
|---|---|---|---|---|
| 岩政さんの案（push・自前の DB） | 多い（9 PR・4 リポジトリ） | daemon を 4 クラスターで保守 | パスの最新版だけ | 全ファイルが常に置かれる |
| 実装 1 取りに行く | 中 | ほぼ無し | 取り方次第 | 使うときだけ |
| 実装 2 `jadd backup` を広げる | 少ない | ほぼ無し | パスの最新版だけ | 使うときだけ |
| 実装 3 ハッシュの一覧を Git に | 中 | ほぼ無し | **commit で固定** | 使うときだけ |
| 実装 4 rclone で同期 | 少ない | timer を保守 | パスの最新版だけ | 全ファイルが常に置かれる |
| 実装 5 マウント | 少ない | FUSE を保守 | パスの最新版だけ | 常に見える |
| 実装 6 別リポジトリ | ほぼ無し | pull の timer か無し | commit で固定 | 取り方次第 |

### 所見

- **案で一番重いのは「先に配る」こと**。daemon、`/data/shared/` の権限、`.inbox/` の近道、cursor、watchdog が無い GMO・gaggle の保守は、どれも push 型にしたことから来ている。岩政さん自身が不安と書いているのもここ。**使うときに取りに行く形（実装 1・2・3）にすれば、ほとんど要らなくなる**。push 型が要るのは、ジョブの開始時にネットワークに頼れない場合や、利用者が `ls` で `/data/shared/` を眺めたい場合。ヒアリングで確かめる価値がある。
- **版・履歴・取り消し・秘密情報の検査を自前で作るのは、置けるのがテキストだけなら過剰かもしれない**（実装 3・6 なら Git がすでに持っている）。自前で作る理由は「Git から外したい」ことだが、外したいのは Git が重くなるからで、その重さの大半は写す設計（uv.lock・`main.py`・表のコピー）から来ていた。重複の lint と uv.lock の除外で、すでに歯止めがかかり始めている。
- **どの実装を選ぶかより先に、需要の確認が要る**。ヒアリング先の 4 では、「同期の需要」は写す設計の副作用かもしれないと分かった。需要が「実験とデータを一緒に残したい」なら実装 3、「最新版を各クラスターで使いたい」なら実装 1・2、「各クラスターで眺めたい」なら岩政さんの案か実装 4 が向く。
- 重い件（問題 A）の「画像を見る・示す」需要には、どの実装も応えない（画像は対象外）。これは別の置き場（S3 の画像をブラウザーで見せる仕組みなど）の話になる。

## 案: workspace を別リポジトリにし、Git LFS を付ける（2026-11-11 に検討）

ユーザーの問い: mono-e2e とは別に workspace 用のリポジトリを作り、Git LFS も付けて提供したほうがよいのではないか。

**エージェントの見立て: デマンド（D1・D2）とエージェント前提の運用には、岩政さんの案よりよく合う。ただし、確かめないと決められない点が 4 つある。**

### 確かめた事実

- 実験は、モノレポの中のパッケージを相対パスで参照している。テンプレートの `pyproject.toml` は `fullcombo = { path = "../../..", editable = true }`。main の exp の `pyproject.toml` 400 個を見ると、`fullcombo`（398）のほか、`packages/atlas-simulator`（30）、`packages/vae`（24）、`packages/modelcore-fullcombo`（3）などを相対パスで参照している。
- turingmotors の GitHub のプランは **Team**（75 席・71 人。`gh api orgs/turingmotors`、2026-11-11）。
- GitHub の Git LFS（[Git LFS の課金](https://docs.github.com/billing/managing-billing-for-git-large-file-storage/about-billing-for-git-large-file-storage)、[About Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage)。2026-11-11 に検索で確認）:
  - Team の無料枠は、ストレージ 250GiB と、ダウンロードの帯域 250GiB/月。組織全体で共有する（mono-e2e の `.mbtiles` の分も含む）。
  - 1 ファイルの上限は、Team で 4GB。
  - 枠を超えると、支払い方法があれば従量で課金。予算を $0 にすると、その月は LFS が止まる。
- private リポジトリの LFS のファイルも、GitHub の画面で開け、見るには GitHub のログインが要る。

### デマンドへの合い方

| 観点 | 別リポジトリ＋LFS | 岩政さんの案 |
|---|---|---|
| D1 クラスター間の共有（大きさ・種類は様々） | ◯ どの種類も、1 ファイル 4GB まで | △ テキストだけ、64MB まで |
| D2 URL と認証付きで結果を共有 | ◯ GitHub のファイルの URL、ログインが要る | ✕ 範囲外 |
| 版・作者・取り消し・レビュー | ◯ Git と GitHub のもの | ◯ 自前で作る |
| エージェントが使えるか | ◯ いまと同じ git の操作 | ◯ 新しい CLI を覚えさせる |
| 新しく作るもの | 少ない（リポジトリ、置き方、CI） | 多い（9 PR、daemon） |
| mono-e2e の clone への影響 | 無くなる | Git に置かなくなった分だけ減る |

Miwa さんの「Git が一番デマンドを満たす」を、そのまま生かせるのが一番の利点。

### 確かめないと決められない点

1. **mono-e2e とのつなぎ方。** exp は `../../..` で fullcombo などを参照しているので、別リポジトリにすると、mono-e2e の checkout の決まった場所に置く必要がある。
   - 案: 新しいリポジトリを mono-e2e の `projects/fullcombo/workspace/` に clone し、mono-e2e 側ではそこを `.gitignore` する（入れ子のリポジトリ）。相対パスはいまのまま使える見込み（推測。uv で確かめる必要がある）。
   - 失うもの: fullcombo の API を変える PR と、それを使う exp の修正を 1 つの PR にできなくなる。exp がどの版の fullcombo で動いたかの結び付きも弱まる（再現はやめたので、影響は小さいかもしれない）。
   - `clean_config_lint` など、mono-e2e の CI が workspace を検査している分は、新しいリポジトリの CI に移す（mono-e2e を一緒に checkout する）必要がある。
2. **LFS の費用と、消しにくさ。** 帯域の枠（250GiB/月）は、4 クラスターでエージェントが pull するたびに LFS のファイルを落とすと、すぐ使い切る恐れがある。ego mask の 1.3GB を数人が落とせば数 GB。自分の分だけ落とす設定（`lfs.fetchinclude` や sparse-checkout をユーザーごとのディレクトリーに絞る）を、エージェントに守らせる必要がある。また、**GitHub の LFS のファイルは、リポジトリを消すか GitHub のサポートに頼まない限り消せない**（ストレージが減らない）。この点は公式ドキュメントで確かめ直す。
3. **結果の画像を GitHub に置いてよいか。** 車載カメラの画像には、人や車のナンバーが写り得る。岩政さんの案は個人情報・パートナーデータを対象外にしている。GitHub に置けるデータの範囲を、データの取り扱いの規程と照らす必要がある（ego mask の作業ブランチには、すでに置かれている）。
4. **新しいリポジトリも、いずれ同じように重くなる。** `.py` の写しや大きい結果がたまる。影響は workspace を使う人だけに閉じ、LFS のファイルは checkout しなければ落ちてこない。それでも、ブランチの後始末と置き方のルールは要る（エージェント向けの指示と lint で）。

### そのほか

- すでに mono-e2e にある分（main の workspace の 574MB、履歴の 112MB）は、移しても mono-e2e の履歴に残る。checkout は軽くなる。
- 大きいデータセット（GB 単位）は、これまでどおり S3 / derived-data の領分。4GB の上限があるので、LFS をデータセットの置き場にはしない。
- 決めるのは、workspace の設計を決めてきた Teranishi さん・Miwa さん（fullcombo 側）と、MLOps（岩政さん）。

## 2026-11-04 の調査の結果

**原因は、main ではなく作業ブランチに入った、車体マスクの検収用の画像（約 1.3GB）。** clone や fetch は既定で全ブランチを取るので、main にマージされていないブランチでも手元のリポジトリが重くなる。

- 手元の pack は合計 2.1GB。そのうち 1.33GB は 11/4 の fetch で作られた pack だった。
- 直近 3 週間に増えたオブジェクトはディスク上で約 1.86GB。このうち main から届く分は約 39MB しかない。

ブランチ別の増分（main に含まれない分）:

| ブランチ | 増分 | PR |
|---|---|---|
| `shuhei_goda/ego-mask-sam2-boundary-parts` | **1,317MB** | [mono-e2e#6875](https://github.com/turingmotors/mono-e2e/pull/6875)（OPEN、「作業用・マージ対象外」） |
| `shuhei_goda/vehicle-id-end-to-end` と `codex/vehicle-id-mask-probe` | 2 本で約 206MB（中身はほぼ同じ） | [mono-e2e#7061](https://github.com/turingmotors/mono-e2e/pull/7061)、[mono-e2e#6700](https://github.com/turingmotors/mono-e2e/pull/6700)（OPEN） |
| `feat/fullcombo-back` | 66MB（`masaki_kawamura/exp_*/data/*.npz`） | 見つからず |
| その他 | それぞれ 3MB 以下 | |

一番大きいブランチの中身:

- 場所は `projects/fullcombo/workspace/shuhei_goda/ego_body_mask/results/` の下（`ver2_accepted_20261029/masks`、`ver2_repairs_20261029/round*`、`ver2_exp2668_supplement_20261030` など）。
- 種類は jpg が約 1.05GB、png が約 270MB、pdf が約 200MB（マスク画像、参考画像、検収用の PDF）。
- 10/29〜10/30 の 2 日間に約 40 回のコミットで、修正版のマスクを何度も積み直している。同じような画像が版ごとに履歴に残ったため大きくなった。
- 最終版は [mono-e2e#7038](https://github.com/turingmotors/mono-e2e/pull/7038) として main に squash マージされている。main に入ったのは約 49MB だけ。

当時作ったブランチ別・ファイル別のサイズの一覧（`blobs-paths.tsv`）は一時フォルダに置いていたので、もう残っていない。必要なら作り直す。

## 対策の案（まだ決めていない）

1. **手元だけ軽くする**: fetch の対象を main と自分のブランチに絞り（`git remote set-branches`）、不要なリモート追跡ブランチの参照を消してから `git reflog expire` と `git gc --prune=now` をする。1.5GB ほど減る見込み。2026-11-04 に手順を案内したが、2026-11-11 の時点では未実行（pack は 2.12GiB、fetch は `+refs/heads/*` のまま）。
2. **根本的な対策**: 担当の方に、作業用ブランチ（[mono-e2e#6875](https://github.com/turingmotors/mono-e2e/pull/6875) など）を閉じて消してもらうよう相談する。ブランチを消せば、新しく clone・fetch する人には届かなくなる。あわせて、`workspace/*/results` に画像を commit しない運用（`.gitignore`、S3 に置くなど）を提案する。
