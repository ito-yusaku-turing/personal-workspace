## 1. 軸

### 認証と認可の線引き

| 軸 | 問い | 中の層 |
|---|---|---|
| 認証 | この要求は誰（どの機械）からか。その確かさを保てているか | 発行と保持 / 受け口での検証 / 照合 / 停止 / 機械の資格情報 |
| 認可 | その人（機械）に何を許すか。それを誰がどこで決め、変えるか | 入場 / 機能 / 割り当ての運用 / データ / 台帳の保護 / 管理面 |

境界で迷うものは次のように置く。

- **退職・離任で止める**のは認証（身元そのものを無効にする）。止めたあとに「付けていたロールを外す」のは認可。
- **照合のキー**（`(iss, sub)` か email か）は認証。そのキーで「この人が持ち主か」を判定するのは認可。

### 認可を「どこで運用するか」の 4 つの要素

認可は「判定する場所」だけ決めても運用が決まらない。次の 4 つに分けて置き場所を見る。

| 要素 | 意味 | 例 |
|---|---|---|
| 判定 | 要求のたびに、許すかどうかを決めるコードが動く場所 | `defineRoute`・`proxy.ts`・backend-api の deps |
| ルール | 「このロールなら何ができるか」の対応。誰が、どう変えるか | `RolePermissions.ts`（JADD STUDIO の PR で変える） |
| 割り当て | 「誰にどのロールを付けるか」の台帳。誰が、どう変えるか | JADD STUDIO のユーザー管理画面、Entra のアプリへの割り当て、backend-api の `user_role` の行 |
| 台帳の保護 | 割り当ての台帳を、判定の外から書き換えられないか | backend-prod の DB を直接読み書きできる主体 |

### エンドポイント

| 記号 | 受け口 | 呼び手 | いまの認証 |
|---|---|---|---|
| E1 | JADD STUDIO（画面と API ルート） | 人（社員・協力会社・隔離ロール）がブラウザから | JADD Studio の Supabase（Google、メール + TOTP）。セッションはサーバー側 |
| E2 | backend-api | JADD STUDIO のサーバーが、人の身元で呼ぶ | JADD Studio の Supabase の JWT を、BFF の authorizer が HS256 で検証（BFF の `/v1/{proxy+}` を経由） |
| E3 | backend-api | 人が直接呼ぶ（jadd-cli・スクリプト・手元や Slurm の長時間タスク） | backend-prod の Supabase の JWT、または人の API キー |
| E4 | backend-api（と、その下流） | 機械（号車・CI・signage・サービス・AWS 内のジョブ） | 共有の service key（`sk_`）、IAM |
| E5 | データの基盤（Databricks・S3・backend-prod の DB） | アプリのサービスアカウント。backend-prod の DB を読める 39 主体 | SP・IAM・接続文字列。アプリを通らない |
| E0 | 管理面（ブローカー・Okta の設定、identity リポ） | 管理者・CI | 管理画面・Terraform |

E2 と E3 は受け口が同じ backend-api。呼び手と持っている資格情報が違うので分けた。E2 だけを守っても E3 から迂回できる、という論点を見えるようにするため。

## 4. 認可の課題

### 層ごとの判定と運用（いまの姿と、決まった形）

| 層 | 判定 | ルール（変える人・手段） | 割り当て（台帳） | 割り当てを変える人 |
|---|---|---|---|---|
| 入場（協力会社） | ブローカーの Actions がクレームを見る（決定済み） | ブローカーの設定。identity リポの PR | 相手先の Entra ID のアプリへの割り当て | 相手先の IT |
| JADD STUDIO の機能（E1） | `proxy.ts`・`layout.tsx`・`defineRoute` | `RolePermissions.ts`。JADD STUDIO の PR | JADD STUDIO の DB の利用者のロール | JADD STUDIO の admin（ユーザー管理画面） |
| JADD STUDIO から backend-api への出口（E2） | `accessPolicy.ts` のホワイトリスト | `accessPolicy.ts`。JADD STUDIO の PR | JADD STUDIO のロール | 同上 |
| backend-api の機能（E2・E3・E4） | **いまは無い。** backend-api のスコープで判定する（決定済み） | backend-api のコード。mono-e2e の PR | `user_role`。協力会社は `(iss, sub)` の行、社員は認証した接続で判定 | **未決**（Z7） |
| データの単位 | JADD STUDIO の `TripAccessPolicy` だけ（`external_viewer` を許可した車両に絞る）。backend-api には無い | JADD STUDIO のコード | JADD STUDIO 側の許可した車両 | JADD STUDIO の admin |
| 所有者・帰属 | backend-api が email で判定 | backend-api のコード | 作成者の記録（email・`sub`） | — |
| 管理面（E0） | identity リポの CI。読み書きの credential を SP 側で分ける（方針は決定済み） | identity リポ | — | **未決**（コーポレート IT か、アプリ側か） |

この表から、運用で穴になりやすいのは次の 3 か所と見ている。

- **backend-api の割り当てを誰が変えるか**（Z7）。判定とルールの置き場所は決まったが、`user_role` の行を足す人・手段が決まっていない。
- **同じ人のロールが JADD STUDIO と backend-api の 2 か所にできる**（Z6）。
- **データの単位の判定が JADD STUDIO にしか無い**（Z8）。backend-api を直接呼べば効かない。

## 6. 複雑さの見立てと、分け方の案

38 件・6 列で、1 枚の地図としては読めるが、1 回の議論で扱うには多い。2 章の見えることから、次の 5 つに分けられる。分け目でほかの塊と共有する課題は少ない。
