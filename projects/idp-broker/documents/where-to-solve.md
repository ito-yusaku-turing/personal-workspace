# どの問題を、どこで解くか（認証・認可の持ち場の整理）

- 作成: 2026-10-16
- 目的: チームで議論する題材。ブローカー（社内アプリの認証の入口となる IdP）の選定を進める中で、「どの問題を、どこで解くか」を先に決めると判断が速く、筋が良くなる場面が続いた。その例と、置き場所を決めるときの問いをまとめる
- 関連: 報告書「社内アプリの認証の入口となる IdP の選定」（[`idp-broker-report.md`](idp-broker-report.md)）、補足資料「ブローカー 3 候補と、backend-api・JADD STUDIO・CLI の認証」（[`backend-api-auth-supplement.md`](backend-api-auth-supplement.md)）、安本さんの「service key 廃止の設計メモ」（2026-10-05）

## 1. 気づき

- 問題を解く場所を誤ると、**迂回できる門番**、**二重の台帳**、**止めても効かない停止**ができる。
- 逆に、置き場所を決めると、**比べるべき論点が絞れる**。ブローカーの比較では、「ブローカーの選び方で答えが変わる問題」と「アプリの設計で解く問題」を分けたことで、比べる項目が半分以下になった。
- 置き場所は、技術の都合より先に「**その判断に要る情報と責任を、誰が持っているか**」で決まることが多い。

## 2. 登場する持ち場

| 持ち場 | 役割 |
|---|---|
| 相手先の IdP | 協力会社の社員の本人確認・在籍・異動（協力会社の人事の正本） |
| Okta | 自社の社員の本人確認・在籍（SmartHR を正本に、identity リポで管理） |
| ブローカー | 社内アプリの認証の入口。複数の IdP を受け、アプリにトークンを出す |
| JADD STUDIO | 画面と、そのサーバー。利用者のロールを持つ |
| backend-api | データと処理の API。資源の手前にある最後の門 |
| AWS（IAM・IoT） | 機械とジョブの身元 |
| identity リポ | 「誰がどのサービスにどんな権限で入れるか」の変更の起点。設定をコードで持ち、PR で変える |

## 3. 今日の議論で決まった置き場所

| 問題 | 解く場所 | 退けた置き場所 | 決め手 |
|---|---|---|---|
| 協力会社のうち、誰が利用者候補になるか（入場） | 相手先の IdP（こちら向けのアプリへの割り当て） | JADD STUDIO での事前登録、ブローカーでの個人の許可リスト | 異動や退職を知っているのは相手先。こちらが写しを持つと、合わせ続ける手間と食い違いが生まれる |
| 利用者が何をできるか（権限） | 各アプリ（JADD STUDIO のロール、backend-api のスコープ） | ブローカーのロール、相手先の IdP のアプリロール | 権限の判断はこちらの責任。アプリの機能と一緒に変わるので、アプリのコードと同じ場所で PR に載せる |
| backend-api を誰に許すか | backend-api（`user_role` の行と、コードのスコープ） | JADD STUDIO のホワイトリストだけ | トークンを自分で取れば JADD STUDIO を通らずに呼べる。**門番は、迂回できない資源の手前に置く** |
| 退職・離任した人を止める | 起点は IdP（Okta・相手先）、伝達はブローカー（SCIM → 各アプリへの通知）、取りこぼしは各アプリの同期 | アプリごとに別々の起点を持つ（いまは JADD STUDIO と backend-prod が別々に Google を見ている） | 在籍の正本は IdP にしか無い。アプリは「止める」を受け取り、念のため自分でも確かめる |
| 利用者の照合 | 発行元と ID の組（`(iss, sub)`） | email | email の確かさは発行元によって違う（Google は確かめるが、Entra ID は相手先の管理者が書き換えられる） |
| 機械（車載装置・CI）の身元 | AWS（IoT の証明書・IAM）と backend-api の API キー | ブローカー、Okta | 人の身元の仕組みに機械を混ぜない（identity リポの「サービスアカウントを Okta に作らない」と同じ）。台帳と 1 台単位の失効は IoT の仕組みがそろっている |
| CLI から起動した長時間タスクの資格情報 | アプリの設計（人の API キー、または AWS 内のジョブの role） | ブローカーのリフレッシュトークン | ログインの仕組み（ブローカー）は人がその場にいる前提。人がいない処理には、そのための資格情報を持たせる |
| ブローカーの設定の管理 | identity リポの IaC lane（コード・PR・CI で適用） | 管理画面での手作業 | 「誰がどこに入れるか」の変更の起点を 1 本に保つ。読み取りと書き込みの credential の分離は、workflow の書き方でなく SP 側で強制する |
| ブローカーの選定で何を比べるか | ブローカーの選び方で答えが変わる問題だけ | アプリの設計で解く問題を混ぜて比べる | どの候補でも答えが同じ問題は、選定の判断材料にならない。混ぜると比べる表が膨らみ、決め手が埋もれる |

## 4. 置き場所を決めるときの問い

今日の判断で効いた問いを並べる。上から順に当てると、たいていの問題は置き場所が決まる。

| 問い | 例 |
|---|---|
| その判断に要る情報を、いちばん早く正確に持つのは誰か | 協力会社の社員の異動を知っているのは相手先の IdP |
| その判断の責任を負うのは誰か | 何をさせるかはこちらの責任なので、相手先にもブローカーにも任せない |
| そこで止めれば、迂回されないか | JADD STUDIO のホワイトリストは、backend-api を直接呼ばれると効かない |
| 止めたとき、すぐ効くか | DB の行は次のリクエストから効く。トークンに載せた権限は、期限まで残る |
| 正本は 1 つか（同じ事実を 2 か所で持っていないか） | 協力会社の在籍を相手先とこちらの両方で持つと、食い違う |
| 変更をレビューできるか | コードと PR に載る場所に置く。管理画面の手作業は履歴が残りにくい |
| その問題は、いま比べている選択肢によって答えが変わるか | 変わらないなら、その比較の論点から外し、別に解く |

## 5. 置き場所がまだ決まっていない問題（議論したいこと）

| 問題 | 候補の置き場所 | 論点 |
|---|---|---|
| データの単位の認可（許した人に、どのデータまで見せるか） | backend-api / JADD STUDIO（いまの `TripAccessPolicy`）/ データの基盤（Databricks・S3 の権限） | backend-api を直接呼べる以上、JADD STUDIO だけでは迂回される。データの基盤まで下げるか、backend-api で持つか |
| ロールの正本 | JADD STUDIO のロール / backend-api の `user_role` | いまは 2 か所にできつつある（設計メモは別に持つ案）。同じ人の権限を 2 か所で付ける運用を受け入れるか、片方を正本にしてもう片方へ配るか |
| 退職の同期の本数 | ブローカーに寄せる / アプリごとに持つ | いまは JADD STUDIO と backend-prod が別々に Google を見ている。ブローカーの導入後、起点を 1 本にできるか |
| BFF の authorizer が持っていた役割の行き先 | backend-api の API Gateway / backend-api のアプリ | API キーの検証、号車・サービスの経路制限、`iss` の確認。BFF の撤廃後にどこで行うか |
| 機体の台帳 | AWS IoT の Thing / CDK / backend-api の DB | キッティング・封印・貸出の手順を 1 本にできる場所はどこか |

## 6. チームで話したいこと

- 4 章の問いに、足りないもの・違うと思うものはあるか
- 5 章の各問題を、誰が持ち、いつまでに決めるか
- 新しい機能や連携を設計するとき、この問いを使う場所（設計メモの雛形、レビューの観点など）を作るか
