権限の頂点の輪

CorpIT への聞き取り（2026-11-02）で、GCP が最上位にあると分かりました。権限を上から下への階層として描き、下の層から上の層へ戻る矢印を異常ポイントとして赤で示します。ID 基盤が自分自身をコードで管理すると、こうした戻りの矢印が生まれやすくなります。

上から下（階層どおり） 下から上（異常。太い線は経路を確認済み） 下から上（異常。推定）

異常下から上へ戻る経路確かさ確かめること
C1identity の admin が environment のブランチの制限を外し、自分のブランチから apply の鍵を取る。そのまま自分を owner にできる経路は確認済み。3 つの environment はどれもブランチの制限だけGCP の Workload Identity の条件で ref まで確かめていれば止まる（I27）
C2identity の PR で gcp-organization-admins@ に自分を足し、GCP の組織管理者になるグループのメンバーを IaC で書けるのは確認済み。ロールは未確認そのグループに付いている GCP のロール（I19）
C4最上位の 4 名が Okta を通って GCP にログインしていれば、Okta の管理者がなりすませる。緊急用の資格情報を Keeper（Okta の App）に置いていても同じ推定4 名のログインの方法（I18）、緊急用の資格情報の置き場（I24）
E4aws@ が AWS の root の登録のメールなら、identity の PR でメンバーを足して回復のメールを受け取れる推定aws@ の用途（I20）
  • CorpIT によれば、このうちいくつかはすでに止めてあります。どれをどの仕組みで止めているかは、次の聞き取りで確かめます（I27）。
  • GCP の管理者が apply の鍵で GitHub を書き換えられるのは、上から下への矢印で、階層どおりです。管理者が 4 名に絞られていれば想定内です。
  • Workspace の super admin には、apply から戻る矢印がありません。GCP と同じ最上位の層に置きました。同じ 4 名かどうかは I26 で確かめます。

あるべき姿の案: 異常ポイントを消し、矢印を上から下だけにする

原則は「下の層は、自分の管理者を守る仕組みに書き込めない」です。頂点は Workspace 全体ではなく、日常に使わない数名の専用アカウントに限ります。

辺今ほどき方
E1identity が特権のグループのメンバーを書ける特権のグループを apply の書き込みの対象から外し、super admin が直接管理する
E2管理者が Okta を通ってログインしていれば、Okta の管理者が頂点に届く管理者の専用アカウントは Okta から外し、Google 自身のログインとセキュリティキーにする
E3GitHub の owner・identity の admin が apply の鍵を取れる（P5）Team プランでは断てない。E1 を切って、apply の届く範囲を一般のユーザー・グループ・チームに縮める
E4aws@ が root のメールなら、apply で回復のメールを受け取れるroot のメールを、IaC の外で super admin だけが触れるアドレスに移す
E5緊急用の資格情報を Keeper（Okta の App）に置いていれば、輪が残るOkta に依存しない置き場に分ける

E1 を切っても、GitHub の owner は cdk-apps を通して AWS の大部分に届きます。頂点ではありませんが、最も大きな枝として残るリスクに数えます。
