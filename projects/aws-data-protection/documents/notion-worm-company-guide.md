# 走行データの原本を消えないようにする仕組みの導入（S3 Object Lock）

当社は 2026年11月に、走行データなどの原本を置く場所へ、**一度書いたデータを、決めた手順を踏まない限り誰にも消せなくする仕組み**を入れました。この資料では、なぜ入れたのかと、データを消す必要が出たときに何をしなければならないかを説明します。

## 1. 走行データは最も重要なデータ

自動運転の開発は、自社の車両で集めた走行データの上に成り立っています。AI のモデルの学習にも、性能の評価にも、不具合の調査にも、この走行データを使います。

走行データには、ほかのデータにない特徴があります。

- **二度と集められない。** 同じ日・同じ場所・同じ天気・同じ交通の状況での走行は、もう一度は起こりません。消えたデータの代わりを集め直すことはできません。
- **集めるのに大きな費用と時間がかかっている。** 走行データは、車両・センサー・運転する人・走る時間を積み重ねて集めたものです。人手で付けたラベル（アノテーション）も、付け直すには同じだけの費用と時間がかかります。

そのため、走行データを失うと、学習・評価・調査のすべてが過去にさかのぼってできなくなり、開発そのものが大きく後退します。この仕組みを入れたのは、**一度の誤操作や事故で、何年もかけて集めたデータが失われうる**からです。

## 2. 用語

| 用語 | 意味 |
|---|---|
| S3 | AWS（Amazon Web Services）のデータの保存の仕組み（Amazon S3）。走行データは S3 に置いています。データを入れる箱を「バケット」（bucket）、1 つ 1 つのデータを「オブジェクト」（object）と呼びます |
| WORM | Write Once Read Many の略。一度書いたデータは、誰も書き換えも削除もできず、読むことだけができる、という保存のしかた |
| S3 Object Lock | S3 で WORM を実現する機能。データの版ごとに保持設定を付けられる。保持設定が効いているあいだ、その版は誰にも消せない |
| 保持設定 | S3 Object Lock で版に付ける保護（retention）の総称。データ保持フラグと保持期間がある |
| データ保持フラグ | この資料での呼び名。保持設定のうち、この仕組みで使っている「イベントホールド」（EventHold）のこと。データ保持フラグが付いているあいだ、その版は誰にも消せない。フラグを外しても、その版はすぐには消せず、外した時点から保持期間が始まる |
| 保持期間 | 保持設定のうち、決めた日時まで版を消せなくするもの（retention period）。この仕組みでは、データ保持フラグを外した時点から 15 日の保持期間が始まる |
| バージョニング | S3 で、上書きや削除をしても前の版（バージョン）を残しておく機能（S3 Versioning） |
| ライフサイクルルール | S3 に、決めた条件のデータを自動で消させる設定（S3 Lifecycle） |

## 3. 2 段構えの守り

### 3.1 1 段目: バージョニング（2026年10月に導入）

バージョニングを入れたバケットでは、削除に 2 種類あります。

| 削除の種類 | 何が起きるか | 戻せるか |
|---|---|---|
| **通常の削除**（`DeleteObject`） | S3 が削除マーカー（delete marker。「削除済み」を表す、中身の無い版）を置き、データが見えなくなるだけ。データ自体は前の版として残る | **戻せる** |
| **版の削除**（版の ID〈version ID〉を指定した `DeleteObject`） | S3 が、指定した版そのものを消す | 戻せない |

上書きしたときも同じで、S3 は上書きする前の版を残します。

**バージョニングのおかげで、通常の削除は気軽にできるようになりました。** 誰かが誤って消しても、前の版を使って元に戻せるからです。不要になったデータの片付けは、これまでどおり通常の削除で行ってください。

一方の「版の削除」は取り返しがつかないので、バケットポリシー（bucket policy）が、ごく一部の管理者以外には版の削除を禁じています。

### 3.2 2 段目: S3 Object Lock（2026年11月に導入）

1 段目だけでは、版の削除ができる管理者が誤って（あるいはアカウントを乗っ取られて）消してしまうと、取り返せません。また、誰かがライフサイクルルール（S3 Lifecycle）の条件を誤って設定すると、S3 が大量のデータを自動で消してしまいます。

S3 Object Lock は、ここを塞ぎます。

- 対象のバケットの今あるデータには、導入のときにデータ保持フラグ（EventHold）を付けてあります。新しく書かれたデータには、S3 がデータ保持フラグを自動で付けます（既定の保持設定、default retention）。
- データ保持フラグが付いている版は、**管理者にも消せず、ライフサイクルルールでも消えません。**
- データ保持フラグを外すには、決めた手順（4 章）を踏む必要があります。
- 誰かがデータ保持フラグを外したあとも、その版は **15 日** のあいだ消せません（フラグを外した時点で、15 日の保持期間〈retention period〉が始まる）。そのあいだに関係者が誤りや不正に気づけば、削除を取りやめられます。

S3 Object Lock には、決めた権限を持つ人なら保持設定を無視できる「ガバナンスモード」（governance mode）と、誰にも無視できない「コンプライアンスモード」（compliance mode）があります。導入したのはガバナンスモードです。ガバナンスモードには「保持設定を無視してその場で消す」権限（`s3:BypassGovernanceRetention`）がありますが、バケットポリシーが、この権限を全員に禁じています。そのため、ふだんの守りの強さはコンプライアンスモードに近くなります。それでいて、保持設定を誤って付けてしまったときには、管理者がこの禁止をいったん外して直せます。

## 4. データを消す必要が出たとき

### 4.1 消す必要が出るケース

たとえば、次のようなケースです。

- 保存の費用を減らすために、使わなくなった種類のデータをまとめて消す。
- 法令や契約に基づいて消す（個人情報の削除の依頼、契約の終了など）。
- 置き場所を誤ったデータを消す。

### 4.2 しなければならないこと

| # | すること | 誰が |
|---|---|---|
| 1 | 何を、なぜ消すかを決め、消す対象を 1 件ずつ記録した一覧（マニフェスト、manifest）を作る | データを扱う担当者 |
| 2 | 通常の削除（`DeleteObject`）で、対象を見えなくする。この時点では、まだ元に戻せる | 同上 |
| 3 | 一覧に沿ってデータ保持フラグを外すことを承認する。承認を受けて、S3 Batch Operations（S3 の一括処理の機能）がフラグを外す | **AWS アカウントの最上位の管理者**（AWSAdministratorAccess の権限を持つ人） |
| 4 | **15 日待つ**。このあいだなら、データを扱う担当者が削除を取りやめられる | — |
| 5 | 残っている版を消す。データを扱う担当者がライフサイクルルールを、レビュー（インフラのコードの pull request）を経て一時的に入れ、S3 がそのルールに沿って版を消す | データを扱う担当者（設定の変更はレビューが要る） |

- **その場ですぐに消すことは、誰にもできません。** 急ぎの依頼でも、消し終わるまでに最短で 2〜3 週間かかります。消す期限がある依頼（契約や法令によるもの）を受ける人は、この日数を見込んでください。
- **最上位の管理者の承認が要ります。** データ保持フラグを外す作業は、承認を受けた決まった仕組み（S3 Batch Operations の専用のロール〈IAM role〉）だけが行えるようにしてあり、管理者を含め、人が直接外すことはできません。
- **消し終わるまで、保存の費用はかかり続けます。** 大量に消すときは、待ちの 15 日分の費用も見込んでください。
