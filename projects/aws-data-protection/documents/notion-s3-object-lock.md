# S3 Object Lock（WORM）の整理

作成: 2026-10-26 ／ 伊藤

収集データ（原本バケット）を WORM 化する検討のための資料です。S3 Object Lock の仕組み、今の守りに加えたときの効果、入れる前に決めることをまとめました。AWS のドキュメント（2026-10-26 時点）で確かめた内容です。

**要点**

- Object Lock は、オブジェクトの**版ごと**に鍵をかけ、期限まで（または解除するまで）消すことも上書きすることもできなくします。
- **コンプライアンスモード**では、root を含めて誰も消せません。期限前に消す方法は、AWS アカウントを削除することだけです。**ガバナンスモード**では、特別な権限（`s3:BypassGovernanceRetention`）を持つ人だけが消せます。
- 一度有効にすると、**バケットから外せず、バージョニングも止められません**。モードと期間の選び方を誤ると、取り返しがつきません。

## 1. WORM と S3 Object Lock

WORM（Write Once Read Many）は、「一度書いたデータは、決めた期間、誰も消すことも書き換えることもできない」という保存の仕方です。S3 では Object Lock で実現します。

- **鍵は版に付きます。** バケットではなく、オブジェクトの版（バージョン）1 つずつに付きます。そのため、バージョニングが必須です（原本バケット 12 本は入れ済み）。
- **ふつうの削除はできます。** 版を指定しない `DELETE` は、削除マーカーを置くだけなので成功します。消せなくなるのは、鍵のかかった版そのものです。版を指定した削除は `403 Access Denied` になります。
- **上書きもできます。** 同じキーに書くと新しい版ができるだけで、鍵のかかった古い版は残ります。
- 削除マーカー自体は守られません。消せば元の版が今の版に戻ります。

## 2. 鍵の種類

1 つの版に、保持期間とリーガルホールドの両方を付けられます。

| 種類 | 期限 | 外し方 | 向いている用途 |
|---|---|---|---|
| **固定の保持期間**（fixed retention） | 「この日まで」を版ごとに持つ | モードによる（次の節） | 保存期間が決まっているデータ |
| **可変の保持期間**（variable retention、イベントホールド） | ホールドを解除するまで守る。解除すると、そこから決めた期間（1 日〜100 年）守る | 解除には `s3:PutObjectRetention` の権限が要る。解除しても、その期間はさらに守られる | 期限が決められないデータ。「消すと決めてから N 日は戻せる」形にしたいとき |
| **リーガルホールド**（legal hold） | 外すまで | `s3:PutObjectLegalHold` の権限で、いつでも外せる | 監査・訴訟などで、一時的に凍結するとき |

- 可変の保持期間は、2026-09-08 に追加された機能です。追加の費用はかかりません。
- バケットに**既定の保持期間**（固定・可変のどちらでも）を設定すると、それ以降に書かれる版に自動で鍵がかかります。
- 保持期間は延ばせますが、コンプライアンスモードでは縮められません。上限は 100 年です。

## 3. 2 つのモード

| | ガバナンスモード | コンプライアンスモード |
|---|---|---|
| 期限前の削除・期間の短縮 | `s3:BypassGovernanceRetention` を持ち、リクエストで「迂回する」と指定したときだけできる | **誰もできない。root もできない** |
| モードの変更 | 上の権限でできる | できない |
| 失敗したとき | 権限を持つ人が直せる | **直せない。設定した期間、保存の費用がかかり続ける** |
| 用途 | 大半の人には消させないが、いざというときは消せるようにしたい | 規制や、絶対に消させたくないデータ |

注意:

- `s3:BypassGovernanceRetention` は `s3:*` に含まれます。`AdministratorAccess` など、S3 の全権限を持つ主体は迂回できます。
- **S3 のコンソールは、迂回のヘッダーを自動で付けます。** 権限を持つ人がコンソールから消すと、ガバナンスモードの鍵は効きません。API や CLI では、明示的に指定しない限り迂回されません。
- ガバナンスモードからコンプライアンスモードへは移せますが、逆はできません。AWS も「コンプライアンスにする前に、ガバナンスで期間の設定を試す」使い方を勧めています。

## 4. 入れるときに知っておくこと

- **戻せないこと**
  - 一度有効にすると、Object Lock を無効にできず、バージョニングも止められません。
  - 有効にするのは、既存のバケットにも後からできます。
- **既存の版には自動でかからない**
  - 既定の保持期間は、それ以降に書かれる版にだけ効きます。
  - 既存の版にかけるには、S3 Batch Operations で 1 つずつ設定します。
- **ライフサイクル**
  - ライフサイクルは、鍵のかかった版を消せません。削除マーカーを置く動作と、ストレージクラスの移動（Intelligent-Tiering など）はそのまま動きます。
  - 意図して大量に消す運用（例: LiDAR の間引き）は、期限が来るかホールドを解除するまでできなくなります。
- **書き込み側**
  - 保持期間を付けて書き込むときは、`Content-MD5` かチェックサムのヘッダーが要ります。
  - 新しい SDK は既定で付けます。ただし、古いツール・DataSync・Databricks などの経路で通るかは、事前に確かめる必要があります。
- **そのほか**
  - Object Lock を有効にしたバケットは、S3 サーバーアクセスログの書き込み先にできません。
  - 暗号鍵は守られません。SSE-KMS の KMS キーが消されると、版は残っていても読めなくなります。
  - レプリケーションと組み合わせるときは、複製先のバケットでも Object Lock を有効にする必要があります。

## 5. 今の守りにどう重なるか

今の守りの層に、データそのものを守る層が加わります。

```
 ┌──────────────────────────────────────────────┐
 │ 人の権限の整理（BreakGlass・MFA・不要な主体の掃除）    │  そもそも強い主体を減らす
 ├──────────────────────────────────────────────┤
 │ SCP・RCP（組織の層。予定）                          │  アカウントの中から外せない Deny
 ├──────────────────────────────────────────────┤
 │ バケットポリシーの Deny（ステージ 1）                │  例外の主体以外を止める
 ├──────────────────────────────────────────────┤
 │ ★ Object Lock（版の層）                           │  権限に関係なく、版を消させない
 ├──────────────────────────────────────────────┤
 │ バージョニング（第一弾）                            │  ふつうの削除・上書きを戻せる
 └──────────────────────────────────────────────┘
   横から 削除の検知（ステージ 2、毎時の報告）           … どの層を抜けられても気づく
```

### どの攻撃・事故が、どこで止まるか

| 起こること | 今 | ＋ガバナンス | ＋コンプライアンス |
|---|---|---|---|
| アプリのバグ・ふつうの削除・上書き | 戻せる（バージョニング） | 同じ | 同じ |
| 例外以外の主体が古い版を消す | 止まる（バケットポリシー） | 止まる | 止まる |
| 例外の主体（SSO の FullAccess・AWSAdministratorAccess）が古い版を消す | **通る** | 迂回の権限があれば通る（コンソールなら自動で） | **止まる** |
| deploy のロールを名乗る経路 | **通る** | 通る（cfn-exec-role は `AdministratorAccess`） | **止まる** |
| ライフサイクルに Expiration を混ぜる（調査の G08） | **通る**（翌日消える） | 古い版は残る。今の版に削除マーカーが付くだけ | 同じ |
| バージョニングを止める | 例外の主体なら通る | **できない** | できない |
| バケットポリシーを消す（管理アカウントの `S3UnlockBucketPolicy` を含む） | 守りが消える | 消えても鍵は残る | 同じ |
| root | 認証情報を消す予定 | 迂回できる | **止まる** |
| AWS アカウントの閉鎖 | 消える | 消える | 消える |

一番大きく変わるのは、ライフサイクルに Expiration を混ぜる攻撃です。今は「deploy できる人なら翌日に原本を消せる」状態ですが、どちらのモードでも古い版は守られます。

### 既存の層の役割の変わり方

- **バケットポリシー:** 引き続き要ります。ガバナンスモードにするなら、`s3:BypassGovernanceRetention` と、鍵の設定の変更（`PutBucketObjectLockConfiguration`・`PutObjectRetention`・`PutObjectLegalHold`）を、例外の主体だけに限る役割が加わります。
- **SCP・RCP:** RCP で `s3:BypassGovernanceRetention` を BreakGlass 以外に拒否すると、ガバナンスモードでも、アカウントの中からは誰も迂回できなくなります。組織の管理者が RCP を外せば戻せる点が、コンプライアンスとの違いです。
- **削除の検知:** 引き続き要ります。消せなくても、削除マーカーは付きます。迂回の試みや、ホールドの解除（`s3:ObjectRetention:Put` のイベント）も知りたいためです。
- **人の権限の整理:** データを消される心配は大きく減りますが、読み取りの漏えいや、ほかのリソースの破壊への備えとして意味は残ります。

### Object Lock でも残る穴

- **AWS アカウントの閉鎖。** コンプライアンスモードでも防げません。防ぐには、別のアカウントへの複製やバックアップ（後述の AWS Backup Vault Lock など）が要ります。
- **固定の保持期間の期限切れ。** 期限が来ると、ただの版に戻ります。原本を期限なく守るなら、可変の保持期間（イベントホールド）を使うか、期間を定期的に延ばします。
- **暗号鍵の削除**（SSE-KMS の場合）。
- **読み取り・持ち出し。** Object Lock は消させない守りで、読ませない守りではありません。

## 6. 費用

- **保存の費用:** 鍵をかけた版は消せないので、その期間の保存費用が必ずかかります。原本バケットは数 PB 規模なので、期間の長さがそのまま費用になります。間引きなどで消す予定だったデータも残ります。
- **既存の版に鍵をかける費用（試算）:** 原本バケット 12 本は約 6.5 億オブジェクトです。
  - Batch Operations: ジョブあたり $0.25 ＋ 100 万オブジェクトあたり $1 → 約 $650。
  - 版ごとの `PutObjectRetention` のリクエスト: PUT の料金（S3 Standard で 1,000 件あたり $0.005）なら約 $3,250。ストレージクラスによってはもっと高くなります。
  - 合わせて**数千ドル規模**の見込みです。版の数（古い版を含む）とストレージクラスの内訳から、正確に見積もり直す必要があります。
- Object Lock の機能そのものに、追加の料金はありません。

## 7. 似た機能との違い

「アカウントを解約するまで消せない」と言われるのは、S3 Object Lock のコンプライアンスモードのことです。S3 の外に、似た仕組みが 2 つあります。

| 機能 | 何を守るか | 特徴 |
|---|---|---|
| **S3 Object Lock** | S3 のオブジェクトの版 | 今回の本命 |
| S3 Glacier Vault Lock | 旧来の Glacier の「ボールト」（S3 の Glacier ストレージクラスとは別物） | ボールトのポリシーを一度ロックすると変えられない。今の S3 のバケットには使えない |
| AWS Backup Vault Lock（コンプライアンスモード） | AWS Backup のバックアップ | 猶予期間の後はロックを外せない。原本とは別に、消せない写しを持つ形。アカウントの閉鎖に備えるなら、別のアカウントに置く |

## 8. 決めること

1. **対象:** 原本バケット 12 本すべてか、一部（例: 自社収集の S1 だけ）か。DENSO から受け取ったデータ（S2）に、契約上の消去・返却の義務が無いか。
2. **モード:** コンプライアンスか、ガバナンスか。
3. **鍵の種類と期間:** 固定の保持期間（何年か）か、可変の保持期間（ホールドを解除してから何日守るか）か。
4. **消す必要が出たときの手順:** 個人情報の削除依頼、契約終了時の消去、間引き。コンプライアンスモードでは、期限前には応じられません。
5. **既存の版にさかのぼって鍵をかけるか:** Batch Operations の費用（数千ドル規模）と手間がかかります。
6. **アカウントの閉鎖にも備えるか:** 別のアカウントへのバックアップが要り、数 PB を二重に持つ費用がかかります。

## 9. 進め方の案（伊藤）

- **まず、検証用のバケット（カナリア）で試す。** 原本バケットと同じ条件のカナリア（[cdk-apps#2267](https://github.com/turingmotors/cdk-apps/pull/2267)）で、書き込みの経路（Databricks・DataSync・Batch）が通るか、削除の検知にどう見えるかを確かめます。Object Lock は外せないので、カナリアは使い捨ての別のバケットにします。
- **監査ログのバケットから入れる。** 削除の記録を置くバケット（`original-bucket-audit-logs-767397804933`）は、保存期間（1 年）が決まっていて容量も小さいので、コンプライアンスモードの最初の対象に向いています。今は「ふつうの削除の権限で、監査ログを消せる」という課題も残っています。
- **原本バケットは、次のどちらかを推奨します。**
  - **案 A（戻せる余地を残す）:** ガバナンスモード ＋ RCP で `s3:BypassGovernanceRetention` を BreakGlass だけに許す。普段はコンプライアンスとほぼ同じ強さで、設定の誤りや消去の義務が生じたときは BreakGlass で戻せます。
  - **案 B（最も強い）:** コンプライアンスモード ＋ 既定の可変の保持期間（イベントホールド。例: 解除後 30 日）。原本は期限なく守られ、消すにはホールドの解除が要ります。解除は記録されて検知でき、解除しても 30 日は誰も消せません。間引きなどで消すときは、ホールドを解除して 30 日待ちます。
- どちらの案でも、ステージ 1 のバケットポリシー、削除の検知、人の権限の整理は並行して進めます。
