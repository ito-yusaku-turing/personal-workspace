## 2. 何を守るか

**対象は 9 本です。** データの種別（第一弾の「走行データ消失リスクへの対応」で決めた分類）のうち、S1（自社で集めたデータ）と S2（他社から受け取ったデータ）と、S4 のうち人手のラベルです。どれも、失うと取り返せないか、付け直すのが難しいものです。

| 種別 | バケット |
|---|---|
| S1 自社で集めたデータ | td1-raw、tuscenes-raw、td1-rlog、tuscenes-calibration（旧）、tuscenes-calibration（新） |
| S2 他社から受け取ったデータ | denso-taxi-video、denso-nx-raw、denso-taxi-processed |
| S4 外注の成果物（人手のラベル） | tuscenes-annotation |

**外した 3 本:** この 3 本には、今の保護（この章の末尾の注）が残ります。tuscenes-annotation は 11-05 に一度外しましたが、2026-11-10 に対象に戻しました。

| バケット | 外した理由 |
|---|---|
| tuscenes-model（種別 S3: AI モデル） | 作り直せる。入れ替わりが激しく、意図しない削除があっても損害は軽い |
| tuscenes-annotation（種別 S4: 外注の成果物） | 作り直せる（11-05 に外したときの理由）。**2026-11-10 に対象に戻した**（人手のラベルで、付け直すのが難しい。10 章の Q1） |
| gaming-data-collection（シミュレータで集めた走行動画） | シミュレータがあれば集め直せる。収集は終わっている。持ち主の了承済み（2026-11-10） |
| denso-raw（2024-12 に集めた走行データ） | 持ち主が退職して不在。2025-05 を最後に使われた形跡が無い（2026-11-10） |

DENSO から受け取ったデータには、返却や消去の義務がありません。そのため、消せなくしても契約上の問題はありません。

**どう守るか:** 各バージョンに、ガバナンスモードのイベントホールドを付けます。

- **イベントホールド**は、解除するまで保護し、解除してから決めた日数（解除後の保持期間。30 日）保護する保持です。
- **ガバナンスモード**では、迂回の権限を持つ主体だけが、保持を無視して消せます。この計画では、迂回を全員に禁じます。
- 新しく書かれるバージョンには、既定の保持設定で自動で付きます。今ある最新のバージョンには、S3 Batch Operations でまとめて付けます。今ある最新ではないバージョンには付けません（原本バケットは基本的に上書きをしないので、ほとんど無い見込み）。

> **今の保護**（2026-10 に入れたもの）: バージョニングと、バケットポリシーの Deny（バージョンを指定した削除と、バケットの設定の変更を、ごく一部の主体以外に禁じる）。今の保護だけでは、例外の主体（FullAccess・AWSAdministratorAccess）がバージョンを指定して消すと取り返せず、ライフサイクルの失効を足す変更がマージされると大量に消えます。Object Lock を入れると、どちらでも保護されたバージョンは消えなくなります（ライフサイクルで消えないことは検証済み）。

## 3. 終わった時点の姿

第 3 段階まで終えたあとの姿です。

### 3.1 誰が何をできるか

今と比べて変わるのは、**FullAccess が、バージョンを指定した削除と、バケットの設定の変更を、直接はできなくなる**ことです。日々の作業でこれらの操作は使わないので、作業は止まりません。

| 操作 | 書き込み元・一般の利用者 | FullAccess | AWSAdministratorAccess | ジョブのロール |
|---|---|---|---|---|
| 読み取り・書き込み・上書き・通常の削除 | 今の権限のまま | できる（※1） | できる | — |
| イベントホールドの解除・付け直し | できない | できない | ジョブを作れば、ジョブのロールが行う | **できる**（このロールだけ） |
| 迂回して消す | できない | できない | できない（※2） | できない |
| バージョンを指定した削除 | できない | できない | できる（保護されていないものだけ） | — |
| バケットの設定の変更 | できない | できない | できる（※2） | — |

- ※1 td1-raw と tuscenes-raw では、今も FullAccess は通常の削除ができません。これは変えません。
- ※2 バケットポリシーから迂回の禁止を外せば、迂回して消せます。この変更は通知されます（3.3）。deploy の経路（cdk-apps の `main` へのマージ）も同じです。
- **完全削除用の権限**（保護されたバージョンを最終的に消すために、保護を外せる権限）は、AWSAdministratorAccess をそのまま使います。ジョブのロールをジョブに渡せるのは、AWSAdministratorAccess だけです。

### 3.2 守りの部品

| 部品 | 役目 |
|---|---|
| バケットポリシー | 迂回とコンプライアンスモードの保持を全員に禁じる。保持の変更をジョブのロールだけにする。バージョンを指定した削除とバケットの設定の変更から、FullAccess を外す |
| ジョブのロール | S3 Batch Operations だけが使える。決めた日数のイベントホールドを付ける・外すことだけができ、削除・迂回・コンプライアンスモードの保持・ほかの日数はできない |
| 組織のポリシー（SCP） | ジョブのロールを渡す操作と、そのロールの変更を禁じる。deploy の経路を GitHub Actions 以外から使えないようにする |
| レポートの置き場 | ジョブが作った対象の一覧と結果を残す（何に保護を付けたかの記録）。原本バケットと同じ守りを入れる |

中身（文の名前・ロールの名前・例外の主体）は、8.1 にあります。

### 3.3 通知

| 何を | 届き方 |
|---|---|
| イベントホールドの解除 | まとめて数分のうちにメール |
| バケットの設定の変更（拒まれた試みを含む）と、S3 Batch Operations のジョブの作成・状態の変更 | メール |
| 通知の仕組みそのものの変更 | メール |

解除のイベントが EventBridge に届くのは 0〜2 秒、拒まれた試みも届くことを確かめました（検証済み）。送り先は最初は SNS のメールで、Slack は後で足します。

### 3.4 残るリスク

次の手口は、塞がずに受け入れ、変更の通知で気づく形にします。

| リスク | 中身 |
|---|---|
| バケットポリシーを書き換えられる主体（AWSAdministratorAccess・deploy の経路・root・管理アカウント） | 迂回の禁止を外せば、すぐ消せる。cdk-apps の変更は PR のレビューで止める |
| 既存のスタックの更新 | cdk-apps のスタックに付いた deploy の経路のロールで、スタックを更新できる主体がバケットポリシーを書き換えられる（AWS の仕様）。手当ては次の検討に回す |
| 既存の最新ではないバージョン | Object Lock の保護は付かず、今の保護だけ。ほとんど無い見込み |
| 通知を止める | 通知の仕組みを 1 つずつ外せる。最後に残った仕組みを外す操作は通知されない |

迂回の禁止を RCP（アカウントのリソースに効かせる権限の上限）に重ねることや、コンプライアンスモードへの移行は、この計画には入れません。組織の権限の整理（別の検討）が固まってから、別に決めます。

## 4. 導入の手順と結果

### 4.1 第 1 段階: 部品を置く

| 項目 | 中身 |
|---|---|
| 状態 | **レビュー待ち**（[cdk-apps#2500](https://github.com/turingmotors/cdk-apps/pull/2500)、2026-11-09 に作成） |

これらの禁止を先に入れるのは、第 2 段階で Object Lock を入れたその時から、保護されたバージョンを迂回して消せず、ジョブのロール以外は保持を外せない状態にするためです。第 2 段階で保持を変えるのはジョブのロールだけなので、先に入れても作業は止まりません。保持の変更の禁止は、当初は第 3 段階の予定でしたが、2026-11-10 に前倒ししました（10 章の Q2）。

### 4.2 第 2 段階: Object Lock を入れる

**予行（予行用のバケットで試す）**

予行用のバケット（原本バケットと同じ守りを入れた、データを置かないバケット）に、後から Object Lock を入れて試します。予行のあとも、手順の訓練に使います。

| 確かめること | 結果 |
|---|---|
| ジョブに対象の一覧を作らせると、最新のバージョンだけが入るか | **確かめた**（2026-11-09）。古いバージョンと、最新が削除マーカーのキーは入らない。ジョブは確認待ちで止め、流す前に一覧を確かめられる |
| 既存のバケットに、後から Object Lock を有効にしたときの振る舞い | 予行で確かめる |
| 既定の保持設定を外すと、チェックサムなしで書けるようになるか（書き込みが止まったときの戻し方） | 予行で確かめる |
| ジョブのロールで、保持を付ける・外すジョブが通るか。コンプライアンスモードの保持は拒まれるか | 予行で確かめる |
| DataSync が、Object Lock のバケットに書き込めるか | 予行で確かめる |

**各バケットに入れる**

書き込みが止まるのが、いちばん大きいリスクです。書き込みが少なく、書き込み元の問題が無いものから入れます。

| 順 | バケット | 理由 | 前に要るもの | 状態 |

各バケットでの作業:

1. Object Lock を有効にし、既定の保持設定を CLI で入れる。**有効にする操作は戻せません。**
2. 1 日ほど、書き込み元のエラーを見る。

- 終わった条件は、順ごとに数日、書き込みのエラーが無いことです。
- tuscenes-calibration（新）だけは SSE-KMS で暗号化されているので、少ない件数で先に流します。

## 5. 運用

### 5.1 日々の作業

読み取り、書き込み、上書き、通常の削除は、これまでどおりできます。

ただし、Object Lock を入れたバケットへの書き込みには、**チェックサムのヘッダー**（`Content-MD5` か `x-amz-checksum-*`）が必須になり、無いと拒まれます（検証済み）。AWS CLI と SDK の既定なら付くので、ほとんどの書き込み元はそのまま動く見込みです。次の書き方は拒まれます（検証済み）。

- boto3 1.36 以降で `request_checksum_calculation="when_required"` を設定している（環境変数や `~/.aws/config` での設定を含む）。
- 署名付き URL で、チェックサムを署名に入れずに発行している。boto3 の既定の署名（SigV2）の URL も拒まれる。
- `curl` や `requests` などで、SDK を通さずに直接 PUT していて、チェックサムのヘッダーを付けていない。

対象の 9 本の書き込み元の見込みは次のとおりです（洗い出しの方法と限界は 8.3）。

| 書き込み元 | 見込み |
|---|---|
| 走行データのアップロード PC（AWS CLI） | 通る見込み。PC の設定で `when_required` にしていないかは、入れる前に確かめる |
| Datalake の rlog のデコーダー（boto3） | 通る見込み |
| perception-detection・localization の自動の処理（tuscenes-annotation へ） | 通る見込み（11-02 の洗い出しで、これらのロールの書き込みはチェックサムを付けていた。どのバケットへの書き込みかは記録していないので、入れる前に確かめる） |
| DataSync（Azure から denso-taxi-video・denso-nx-raw・denso-taxi-processed へ） | 不明。予行用のバケットで試す |
| Databricks | 書き込む経路は見当たらない。Unity Catalog の volume の場所を確かめる |

### 5.2 誤って通常の削除をしたとき

通常の削除は、削除マーカーを置くだけなので、データは残っています。削除マーカーの 1 つ前のバージョンを、同じキーにコピーすれば戻せます（FullAccess など、読み取りと書き込みの権限を持つ人ができます）。削除マーカーを消す方法は、AWSAdministratorAccess だけができます。

### 5.3 急ぎの依頼や障害のとき

- **すぐ消してほしいと言われたら:** 「完全に消すには、最低でも 30 日かかる」と答えます。消す手順は、そのときに決めます（5.4）。
- **書き込みが止まったら:** AWSAdministratorAccess の人が、そのバケットの既定の保持設定を外します。Object Lock 自体は外せません。既定が無ければ新しいバージョンに保持は付かないので、チェックサムなしでも書けるようになる見込みです（予行で確かめる）。
- **イベントホールドを付ける対象を誤ったら:** 解除のジョブで外せます。外したバージョンも、30 日は消せません。
- **ジョブの日数（解除後の保持期間）を誤ったら:** ジョブのロールは決めた日数でしか付けられないので、ふつうは起きません。それでも誤った場合、解除では直せません。解除すると、保持期限が「解除した時刻＋誤った日数」で固まるからです。直すには、PR でジョブのロールに迂回の権限を足し、迂回の禁止をいったん外して付け直します。**このため、ジョブを作る前に、設定を 2 人で確かめます。**

### 5.4 意図して消すとき（費用を減らすための削除）

手順は、消す必要が出たときに、完全削除用の権限を持つ人と MLOps チームで決めます。解除してから 30 日は消せないので、そのときに決めても、消せるようになる日はほとんど変わりません。

- 決まっていること: 解除してから 30 日たつまで消せない。解除は通知される。
- そのときに決めること: 対象の一覧の作り方、誰が確かめるか、消す方法、途中で取りやめる方法。

### 5.5 戻せないこと

- バケットの Object Lock は、一度有効にすると無効にできません。バージョニングも止められなくなります。
- 既定の保持設定は後から外せます。付けた保持も、ガバナンスモードなので、迂回の禁止をいったん外せば直せます（5.3）。
- そのため、予行用のバケットで試してから、書き込みの少ないバケットから順に入れます。

**ジョブのロールとレポートの置き場**（cdk-apps の `apps/original-bucket-audit`。第 1 段階）

| 部品 | 中身 |
|---|---|
| ジョブのロール `original-bucket-lock-batch` | S3 Batch Operations だけが引き受けられる。9 本と予行用のバケットの、保持を付ける・外す・読むことと、対象の一覧を作ること、レポートを書くことだけができる。バージョンを指定した削除・迂回・タグ付けはできない。コンプライアンスモードの保持の要求（条件キー `s3:object-lock-mode` が `COMPLIANCE`）は、ロールのポリシーでも拒む。付けられるのは、解除後の保持期間が 30 日（`EVENT_HOLD_DAYS`）のイベントホールドだけで、ほかの日数・年での指定・固定の期限は拒む |

### 8.2 用語

詳しくは「S3 Object Lock（WORM）の仕組み」の 10 章にあります。

| 用語 | 意味 |
|---|---|
| 原本バケット | 集め直せない・受け取り直せないデータを置く S3 バケット。今の保護は 12 本、Object Lock の対象は 9 本 |
| 主体 | AWS の操作を行う IAM のユーザーやロール |
| バージョン | 同じキーに書くたびにできる、オブジェクトの 1 つ 1 つ。Object Lock で保護される単位 |
| 最新のバージョン・最新ではないバージョン | 1 つのキーの、読み取りで返るものと、それ以外 |
| 通常の削除・削除マーカー | バージョンを指定しない削除。「消した」という印のバージョン（削除マーカー）を置くだけで、データは残る |
| イベントホールド | 解除するまで保護し、解除してから決めた日数保護する保持 |
| 解除後の保持期間 | イベントホールドを解除してから保護する日数 |
| 既定の保持設定 | 新しく書かれたバージョンに自動で付ける保持の値 |
| ガバナンスモード・コンプライアンスモード | 迂回の権限を持つ主体だけが保持を無視できるモードと、root を含めて誰も無視できないモード |
| 迂回 | ガバナンスモードの保持を無視すること（`s3:BypassGovernanceRetention`） |
| S3 Batch Operations | 一覧で指定したたくさんのオブジェクトに、同じ操作をまとめて行う機能 |
| FullAccess・AWSAdministratorAccess | tuscenes-prod の SSO の権限セット。FullAccess は日々の作業で使う権限のうち最も強いもの（14 名）。AWSAdministratorAccess はその上の権限 |
| deploy の経路 | cdk-apps の `main` へのマージで、GitHub Actions が CDK の deploy に使う IAM ロールと、CloudFormation が使うロール |

### Q1. tuscenes-annotation は作り直せるのか

**対象に戻しました（2026-11-10）。** tuscenes-annotation は、第一弾の分類で S4（外注の成果物）にしたバケットです。人手で付けたラベルが中心です（13.5 TB、約 1,770 万件）。

- 11-05 には「元の走行データがあれば、費用をかければ付け直せる」として対象から外していました。
- 「付け直すのは難しく、大事なデータなので対象にしてほしい」という意見を受けて、対象に戻しました。保持を付ける費用は約 $124 です。
- このバケットには、人手のラベルのほかに、自動の処理の出力も毎日書かれています（物体検出・車線の自動ラベル、位置推定の毎晩の出力。開発用の試し出力を含む）。既定の保持設定はバケット全体に効くので、それらにも保持が付きます。扱いは 6.2 で決めます。

### Q2. 似た権限を持つロールを新しく作ることも、禁止する必要はないか

**ロールの作成は禁止しません。作られても、保持は外せないようにします。** そのための文（`DenyLockChange`）は、当初は第 3 段階の予定でしたが、このコメントを受けて第 1 段階に前倒ししました（2026-11-10）。

保持を外す操作（`s3:PutObjectRetention`）を誰が呼べるかは、IAM のポリシーとバケットポリシーの両方で決まります。どちらかに Deny があれば、もう一方で許していても拒否されます。第 1 段階で、バケットポリシーに `DenyLockChange` を入れます。ジョブのロール（`original-bucket-lock-batch`）以外の全員に、保持の変更を禁じる文です。新しいロールの IAM で保持の変更を許しても、バケットの側で拒否されます。

| 抜け道 | 結果（第 3 段階のあと） | 止めるもの（入る段階） |
|---|---|---|
| 保持の変更を許したロールを新しく作り、ジョブに渡す | 拒否される | `DenyLockChange`（バケットポリシー。第 1 段階） |
| 本物と同じ名前のロールを作る | 作れない（IAM のロール名はアカウントの中で一意。パスを変えても同じ名前は作れない） | IAM の仕様 |
| 本物のロールを消して、同じ名前で作り直す | 消せない | 組織のポリシー（このロールの作成・削除の禁止。第 3 段階） |
| 本物のロールの信頼やポリシーを書き換える | 書き換えられない | 組織のポリシー（信頼・ポリシーの変更の禁止。第 3 段階） |
| 本物のロールをジョブに渡す | AWSAdministratorAccess だけができる | 組織のポリシー（`iam:PassRole` の禁止。第 3 段階） |
| 迂回する・コンプライアンスモードの保持を付ける | 誰にもできない | `DenyGovernanceBypass`・`DenyComplianceMode`（第 1 段階） |

- ロールの作成を広く禁じないのは、cdk-apps の deploy がいろいろなロールを作るので止まってしまうからです。守りはバケットの側にあるので、禁じなくても効きます。
- **第 3 段階まで残る穴:** 前倒しで、IAM で `s3:PutObjectRetention` を持つだけの主体（td1-raw では 24 件。FullAccess・TeamE2E など）は、第 1 段階から保持を外せなくなります。ただし、ジョブのロールを渡す操作とロールの変更の禁止（組織のポリシー）は第 3 段階で入ります。それまでは、ジョブを作れて、このロールを渡せる主体（FullAccess など）なら、このロールで解除のジョブを作れます。解除の通知も、第 3 段階の通知の PR からです。解除しても 30 日は消せません。

### Q3. deploy のロールから、バケットポリシーの変更を禁止できないか

**できます。** 今は「cdk-apps の変更は PR のレビューで止める」ことに頼っていて、GitHub の権限管理に依存しています。これを、AWS の側で止める形にできます。

**禁止する相手は、CloudFormation の実行ロール（cfn-exec-role）です。** deploy でバケットポリシーが書き換わるまでには、ロールが 3 つ関わります。

| 順 | ロール | すること |
|---|---|---|
| 1 | GitHub Actions の deploy のロール（`GithubActions-CdkDeployRole*`） | `main` へのマージで、GitHub Actions が使う |
| 2 | CDK の deploy のロール（`cdk-hnb659fds-deploy-role-*`） | CloudFormation に変更を渡し、cfn-exec-role を使わせる |
| 3 | CloudFormation の実行ロール（`cdk-hnb659fds-cfn-exec-role-*`） | S3 に `PutBucketPolicy` を実際に呼ぶ |

S3 から見ると、バケットポリシーを書き換えに来るのは 3 です。守りの文（`DenyProtectionRemoval`）が例外にしているのも 3 なので、3 を、バケットポリシーの変更（`s3:PutBucketPolicy`・`s3:DeleteBucketPolicy`）の例外から外します。1・2 だけを止めても、3 を直接使う道が残ります。

**禁止の書き方は 2 通りあります。**

| 手段 | 書く場所 | 拒否を外せる人 | 正当にポリシーを変えたいとき |
|---|---|---|---|
| ① バケットポリシー | 守りの文で、Object Lock を入れる 9 本だけ、この 2 つの操作を cfn-exec-role の例外から外す | AWSAdministratorAccess・root | 管理者が手でポリシーを書き換えて禁止を一時的に外し、そのあと deploy する（deploy で禁止は元に戻る） |
| ② 組織のポリシー（SCP） | organization-policy のアプリで、cfn-exec-role が 9 本のバケットポリシーを変えることを禁じる | 管理アカウントの管理者（変更の PR は、山本さん・安本さんの承認が必須） | 例外を一時的に足す PR と、外す PR の 2 往復 |

- **①は自分で自分を守ります。** 禁止を外す変更を PR で入れても、その deploy は cfn-exec-role が行うので拒否されます。GitHub に何がマージされても、deploy では迂回の禁止を外せません。把握した抜け道として残している「既存のスタックの更新」（3.4）も、バケットポリシーについては塞がります。
- バージョニングとライフサイクルの例外は残します。Object Lock を入れたバケットでは、バージョニングを止められず、ライフサイクルでも保持の付いた版は消えないためです。
- **引き換えに、9 本のバケットポリシーは、ほかの文（別アカウントへの読み取りの許可など）も含めて deploy で変えられなくなります。** 変えるたびに手作業が要ります。直近の変更は 10-26・10-13・09-17 の 3 回で、年に数回の見込みです。
- ①のあとも、AWSAdministratorAccess と root は、今と同じくポリシーを書き換えられます（バケットの持ち主のアカウントの root は、S3 の仕様で、どんな拒否があってもバケットポリシーを消せます）。変更は通知されます。
- **今の計画には、まだ入っていません。** 入れるなら第 3 段階の「権限の絞り込み」の PR で、①を先に入れる案です。

あわせて、GitHub 側で気になった点です。`main` のルールセットは、PR 必須・承認 1 件・CODEOWNERS の承認必須です。

- 承認のあとに push しても、承認が外れない設定になっている。承認をもらったあとにコミットを足せば、レビューされずにマージできる。
- PR を経ずに `main` に入れられる例外（Integration）が 1 つある。
- 守りの共通パッケージ（`packages/original-bucket-guard`）に、専用の CODEOWNERS が無い。

### Q4. 新しくアップロードしたデータに、Object Lock は自動で付くのか

**自動で付きます。** 第 2 段階で、各バケットに既定の保持設定（ガバナンスモード・イベントホールド・解除後 30 日）を入れます。それ以降に書かれた版には、書き込みのたびに S3 が自動で保持を付けます。書き込み元の変更は要りません。変わるのは、チェックサムのヘッダーが要ることだけです（5.1）。

| 版 | 保持 |
|---|---|
| 既定の保持設定を入れたあとに書かれた版（新しいアップロード・上書き） | 自動で付く |
| 入れる前からある版のうち、最新の版 | S3 Batch Operations のジョブでまとめて付ける |
| 入れる前からある版のうち、最新ではない版 | 付けない（今の保護だけ）。原本バケットは基本的に上書きをしないので、数は少ない見込み |

- 既定の保持設定はバケット全体に効きます。プレフィックスごとに分けることはできません。
- Object Lock を有効にしてからジョブを流し終えるまでの間に、もとからある版が上書きされると、その古い版には保持が付きません。原本バケットではほぼ起きない想定です。
