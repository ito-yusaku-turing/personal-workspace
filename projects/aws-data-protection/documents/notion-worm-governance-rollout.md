# 原本バケットの WORM 化: ガバナンスモードでの導入

作成: 2026-11-05 ／ 伊藤

<!-- Notion: https://app.notion.com/p/40fa93b3e6f2811bb51ffaef3cc970e9 （MLOps 1チーム / ドキュメント置き場。2026-11-05 に下書きで作成。このファイルが原本） -->

原本バケット（集め直せない走行データなどを置く S3 バケット）に、S3 Object Lock をガバナンスモードで導入する計画です。この資料には、導入後の姿（目標状態）と運用、導入の手順、注意することを書きます。

この資料で「Object Lock を導入する」は、次の 3 つをまとめた作業を指します。

1. バケットで Object Lock を有効にする（戻せない）。
2. 既定の保持設定（新しく書かれたバージョンに自動で付ける保持の値）を入れる。
3. 今ある最新のバージョンに、S3 Batch Operations でイベントホールドを付ける。

S3 Object Lock の仕組みは、参照用の資料「S3 Object Lock（WORM）の仕組み」にまとめています。先に読んでおくと読みやすくなりますが、必須ではありません。この資料に要るところは、引用して説明します。

本文の印は次の意味です。

- **（検証済み）**: 検証用のバケットで試して、そのとおりに動くことを確かめた（2026-11-02〜05）。
- **（未検証）**: この計画に関わるが、まだ試していない。導入の前に予行で確かめる（5.3）。
- 印の無いもの: AWS のドキュメントによる。

**要点**

- **何をするか:** 対象の 10 本で、新しく書かれるバージョンと、今ある最新のバージョンを Object Lock で保護します。保護されたバージョンは、権限があっても、すぐには消せなくなります。
- **消すとき:** イベントホールドを解除してから 30 日たつと、消せるようになります。解除は、数分のうちにメールで通知されます。
- **日々の作業:** 読み取り、書き込み、上書き、通常の削除（削除マーカーを置くだけの削除）は、これまでどおりできます。
- **書き込み:** チェックサムのヘッダー（`Content-MD5` か `x-amz-checksum-*`）が必須になります。AWS CLI と SDK の既定なら付くので、ほとんどの書き込み元はそのまま動く見込みです（4.1）。
- **意図して消すとき（費用を減らすための削除）:** MLOps チームが消すと決めたら、FullAccess の人が対象の一覧を作り、AWSAdministratorAccess の人が承認してジョブを作ります。ジョブがイベントホールドを解除し、30 日待ってから、ライフサイクルで消します。
- **戻せないこと:** Object Lock は、一度有効にすると無効にできません。そのため、予行用のバケットで試してから、書き込みの少ないバケットから順に導入します。
- **チームで決めてほしいこと:** 7 章にあります。

## 1. なぜ導入するのか

### 1.1 今の保護

原本バケットには、2026-10 に次の 2 つの保護を入れました。この資料では、この 2 つをまとめて「今の保護」と呼びます。

| 保護 | 防げること |
|---|---|
| バージョニング | 通常の削除や上書きをしても、元のバージョンが最新ではないバージョンとして残る。誤って消しても戻せる |
| バケットポリシーの Deny（cdk-apps の共通のパッケージ `packages/original-bucket-guard` が作る） | ① バージョンを指定した削除とバケットの削除を、SSO の FullAccess・AWSAdministratorAccess 以外に禁じる。② バケットの設定の変更（バージョニングの停止・ライフサイクル・バケットポリシーの変更など）を、上の 2 つと deploy のロール以外に禁じる |

- **FullAccess・AWSAdministratorAccess** は、tuscenes-prod（原本バケットのある AWS アカウント）の SSO の権限セットです。FullAccess は日々の作業で使う権限のうち最も強いもので、14 名が持っています。AWSAdministratorAccess はその上の権限です。
- **deploy のロール**は、cdk-apps の `main` へのマージで GitHub Actions が CDK の deploy に使う IAM ロールです。

### 1.2 残っている問題

- **例外の主体（FullAccess・AWSAdministratorAccess）なら、バージョンを指定した削除で、データを完全に消せます。** 誤操作でも、アカウントの乗っ取りでも、取り返しがつきません。
- **ライフサイクルで、大量に消せます。** 誰かがライフサイクルの失効を足す変更を cdk-apps の `main` にマージすると、deploy のロールがそれを入れ、すべてのバージョンが消えます。
- **消したことに、すぐには気づけません。**

### 1.3 Object Lock で何が変わるか

> **引用（「S3 Object Lock（WORM）の仕組み」要点・1 章より）**
> 保護されるのは、オブジェクトのバージョン 1 つ 1 つです。保護されている間も、通常の削除と上書きはできます。どちらも新しいもの（削除マーカーや新しいバージョン）を足すだけで、保護されているバージョンは残るからです。消せなくなるのは、「バージョンを指定した削除」です。

Object Lock を導入し、迂回（3.1）を全員に禁じると、例外の主体でも、ライフサイクルでも、保護されたバージョンを消せなくなります。ライフサイクルで消えないことは、検証で確かめました（検証済み）。消すには、先にイベントホールドを解除し、30 日待つ必要があります。解除は通知されるので、誤りや乗っ取りに 30 日のうちに気づいて止められます。

## 2. 対象

対象は、データの種別（第一弾の「走行データ消失リスクへの対応」で決めた分類）のうち、**S1（自社で集めたデータ）と S2（他社から受け取ったデータ）の 10 本**です。どちらも、失うと取り返せません。

| 種別 | バケット |
|---|---|
| S1 自社で集めたデータ | td1-raw、tuscenes-raw、td1-rlog、gaming-data-collection、tuscenes-calibration（旧。バケット名 `tuscenes-calibration`）、tuscenes-calibration（新。バケット名 `tuscenes-calibration-767397804933`） |
| S2 他社から受け取ったデータ | denso-taxi-video、denso-nx-raw、denso-raw、denso-taxi-processed |

**対象から外したもの:** tuscenes-model（種別 S3: AI モデル）と tuscenes-annotation（種別 S4: 外注の成果物）です。どちらも費用をかければ作り直せます。tuscenes-model は入れ替わりが激しく、意図しない削除があっても損害は軽いと判断しました。この 2 本には、今の保護が残ります。

S2 のうち DENSO から受け取ったデータには、返却や消去の義務がありません。そのため、消せなくしても契約上の問題はありません。

## 3. 目標状態

この章は、導入の手順（5 章）をすべて終えたあとの状態です。

### 3.1 各バージョンの状態

| 項目 | 値 |
|---|---|
| モード | **ガバナンスモード** |
| 保護の種類 | **イベントホールド** |
| 解除後の保持期間（イベントホールドを解除してから保護する日数） | **30 日**（仮の値。7 章） |
| 新しく書かれるバージョン | 既定の保持設定で、自動でイベントホールドが付く |
| 既存のバージョンのうち、最新のバージョン | S3 Batch Operations で、まとめてイベントホールドを付ける |
| 既存のバージョンのうち、最新ではないバージョン | **付けない**。今の保護だけになる（3.6）。原本バケットは基本的に上書きの PUT をしないので、ほとんど無い見込み（数えてはいない） |

> **引用（「S3 Object Lock（WORM）の仕組み」3 章・4 章より）**
> - **イベントホールド**は、解除するまで保護し、解除すると、そこから決めた日数（解除後の保持期間）保護する保持です。保持期限を前もって決められないデータに向いています。
> - **ガバナンスモード**では、迂回の権限（`s3:BypassGovernanceRetention`）を持つ主体が、リクエストで迂回を指定したときだけ、保持を無視して消せます。これを**迂回**と呼びます。**コンプライアンスモード**では、root を含めて誰も消せません。

主体は、AWS の操作を行う IAM のユーザーやロールのことです。

**ガバナンスモードにした理由:**

- 設定を誤ったときに直せます。ただし、迂回の禁止をいったん外す必要があります（4.4）。コンプライアンスモードで日数などを誤ると、誰も直せず、期限まで保存の費用がかかり続けます。
- 後からコンプライアンスモードへ移せます。移すときに迂回が要るかは、まだ試していません（未検証）。
- 迂回をバケットポリシーで全員に禁じれば、ふだんはコンプライアンスモードに近い強さになります（3.3）。
- コンプライアンスモードでの解除の振る舞いを、まだ試していません（未検証）。

ガバナンスモードで増えるリスクは、バケットポリシーから迂回の禁止を外し、迂回して消す手口だけです。この変更は通知されます（3.5・3.6）。

### 3.2 誰が何をできるか

今と比べて変わるのは、**FullAccess が、バージョンを指定した削除と、バケットの設定の変更を、直接はできなくなる**ことです。日々の作業でこれらの操作は使わないので、作業は止まりません。

| 操作 | 書き込み元のシステム・一般の利用者 | FullAccess | AWSAdministratorAccess | 解除用のジョブのロール | deploy のロール |
|---|---|---|---|---|---|
| 読み取り・書き込み・上書き・通常の削除 | 今の権限のまま | できる（※1） | できる | — | — |
| イベントホールドの解除・付け直し | できない | できない | **できない**（ジョブを作って承認する） | **できる**（このロールだけ） | できない |
| 迂回して消す | できない | できない | できない（※2） | できない | できない（※2） |
| バージョンを指定した削除 | できない | できない | できる（保護されていないものだけ） | — | できない |
| 既定の保持設定の変更 | できない | できない | できる | — | できない |
| バケットの設定の変更（バケットポリシー・ライフサイクル・バージョニングなど） | できない | 直接はできない（※2） | できる | — | できる |

- ※1 td1-raw と tuscenes-raw では、今も FullAccess の権限セットに削除の Deny があり、FullAccess は通常の削除もできません。これは変えません。
- ※2 バケットポリシーを書き換えられる主体は、迂回の禁止を外せば迂回して消せます（3.6）。FullAccess も、deploy のロールを引き受ければ、バケットポリシーを書き換えられます（3.6）。
- イベントホールドの解除は、人の権限では行えません。AWSAdministratorAccess の人が S3 Batch Operations のジョブを作り、ジョブのロールが解除します（3.4・4.2）。
- 今、AWSAdministratorAccess を持っていると分かっているのは山本 修平さんです。ほかに 1〜2 名いる見込みで、確かめています。承認する人は 7 章で決めます。

### 3.3 バケットポリシー

共通のパッケージ `packages/original-bucket-guard` が作る Deny の文（Statement）は、次の 4 つになります。原本バケットのバケットポリシーには、ほかに、別のアカウントへの読み取りを許す文などが残ります。

| 文 | 禁じる操作 | 例外 |
|---|---|---|
| `DenyGovernanceBypass`（新） | 迂回（`s3:BypassGovernanceRetention`） | **なし（全員）** |
| `DenyLockChange`（新） | 保持の変更（`s3:PutObjectRetention`）、リーガルホールド（保持とは別の、外すまで消せないフラグ。`s3:PutObjectLegalHold`） | 解除用のジョブのロールだけ |
| `DenyIrreversibleDelete`（既存の文を直す） | バージョンを指定した削除・バケットの削除・既定の保持設定の変更 | AWSAdministratorAccess だけ（FullAccess を外す） |
| `DenyProtectionRemoval`（既存の文を直す） | バケットの設定の変更（バケットポリシー・ライフサイクル・バージョニングなど） | AWSAdministratorAccess と deploy のロール（FullAccess を外す） |

- 共通のパッケージは、原本バケット 12 本（対象の 10 本と、外した 2 本）すべてで同じです。新しい 2 つの文は、Object Lock の無い 2 本では何も効きません。既存の 2 つの文から FullAccess を外す変更は、12 本すべてに効きます。
- 迂回を全員に禁じると、FullAccess も迂回できなくなります（検証済み）。書き込み・上書き・通常の削除は止まりません（検証済み）。

### 3.4 解除用のジョブのロールと承認

| 部品 | 中身 |
|---|---|
| 解除用のジョブのロール `original-bucket-lock-batch` | S3 Batch Operations だけが使えるロール。対象の 10 本にあるバージョンの、保持の変更とタグ付けができる。cdk-apps の中央管理のロール（パス `/central/`）として置く。このパスのロールは、組織のポリシーで変更を禁じているので、FullAccess は中身を変えられない |
| 組織のポリシーの文 | このロールをジョブに渡す操作（`iam:PassRole`）を、AWSAdministratorAccess 以外に禁じる |
| マニフェストの置き場 | 消す対象の一覧（CSV）を置くバケット。FullAccess が一覧を書き、ジョブが結果を書く |

組織のポリシー（SCP。AWS Organizations で、アカウントの全員に効かせる権限の上限）は、cdk-apps の `apps/organization-policy` で管理しています。

**この計画での承認**とは、AWSAdministratorAccess の人が、このロールを渡してジョブを作ることです。ロールを渡せるのは AWSAdministratorAccess だけなので、ほかの人はこのロールでジョブを作れません。

> **引用（「S3 Object Lock（WORM）の仕組み」5.3 より）**
> ジョブは、作った人ではなく、ジョブに渡した IAM ロールの権限で動きます。ジョブを作るには、そのロールを渡す権限（`iam:PassRole`）が要ります。マニフェストは、ジョブを作るときに ETag で固定されます。

ETag は、オブジェクトの中身から S3 が計算する値です。

- FullAccess が自分でロールを作ってジョブを作っても、そのロールは `DenyLockChange` の例外ではないので、解除は拒まれます。
- 承認のあとにマニフェストを差し替えても、ETag が合わないので、差し替えた中身ではジョブは動きません。

### 3.5 通知

| 何を | どう拾うか | 届き方 |
|---|---|---|
| イベントホールドの解除 | EventBridge の `Object Retention Updated` のうち、`event-hold` が `ON` 以外 | CloudWatch のアラームでまとめて、SNS からメール |
| バケットの設定の変更（バケットポリシー・既定の保持設定・ライフサイクル・バージョニング・通知の設定・バケットの削除など） | CloudTrail の管理イベント（EventBridge の `AWS API Call via CloudTrail`）。**拒まれた試みも拾う** | SNS からメール |
| 通知の仕組みそのものの変更（ルール・アラーム・ロググループ・SNS のトピック） | 同上 | SNS からメール |

- 解除のイベントは、イベントの時刻から 0〜2 秒で EventBridge に届きました（検証済み）。メールはアラームでまとめるので、届くまで 1〜3 分かかる見込みです（未検証）。
- バケットの設定の変更は、拒まれた試みも EventBridge に届きました（検証済み）。
- 解除を 1 件ずつメールにしないのは、まとめて解除すると億の単位のイベントが出るためです。イベントホールドを付けるとき（`ON`）は通知しません。
- 送り先は、最初は SNS のメールです。Slack（Amazon Q Developer in chat applications、旧 AWS Chatbot）は後で足します。受け手は 7 章で決めます。

### 3.6 目標状態でも残るリスク

| リスク | 中身 | 気づき方 |
|---|---|---|
| AWSAdministratorAccess の乗っ取り・誤操作 | バケットポリシーから迂回の禁止を外せば、その場で迂回して消せる | バケットポリシーの変更が通知される |
| deploy のロールの悪用 | deploy のロールは、tuscenes-prod の中の誰でも引き受けられる信頼になっている。FullAccess・AWSAdministratorAccess のほか、Databricks や Amplify のロールなど、20 余りの主体が引き受けられる。引き受けた主体は、CloudFormation を通してバケットポリシーを書き換え、迂回の禁止を外せる。cdk-apps の `main` へのマージでも同じことができる | バケットポリシーの変更が通知される。マージは PR のレビューで止める。信頼を狭める作業は別の課題（未着手） |
| root・AWS Organizations の管理アカウントの管理者 | バケットポリシーを消せる（AWS の仕様） | 変更が通知される。tuscenes-prod の root の認証情報は削除を依頼中 |
| 既存の最新ではないバージョン | Object Lock の保護は付けない。今の保護だけ。ほとんど無い見込み | — |
| 通知を止める | 通知の仕組みを 1 つずつ外せば、通知を止められる | 通知の仕組みの変更も通知する。ただし、最後に残った仕組みを外す操作は通知されない |

導入の途中（5 章の手順 B〜D のあいだ）は、このほかに、FullAccess などがイベントホールドを解除できます（5.1）。

この先の強化（コンプライアンスモードへの移行、組織のポリシーで迂回を禁じる、通知の仕組みを tuscenes-prod の外の AWS アカウントに置く、など）は、組織の権限の整理（別の検討）が固まってから、別に決めます。

## 4. 運用

### 4.1 日々の作業

読み取り、書き込み、上書き、通常の削除は、これまでどおりできます。

ただし、書き込みには**チェックサムのヘッダー**が必須になります。

> **要約（「S3 Object Lock（WORM）の仕組み」6.2 の表より）**
> 保持が付く書き込み（既定の保持設定があるバケットへの書き込みを含む）では、`Content-MD5` かチェックサムのヘッダー（`x-amz-checksum-*`）が必須で、無いと拒まれます（検証済み）。AWS CLI と boto3 の既定は付けるので通ります。boto3 1.36 以降で `request_checksum_calculation="when_required"` にしていると、何も付けなくなるので拒まれます。署名付き URL（presigned URL）は、SigV4 で、発行のときにチェックサムを署名に入れたときだけ通ります。

対象の 10 本の書き込み元は、次のとおりです（洗い出しの方法と限界は、末尾の参考資料）。

| 書き込み元 | 見込み |
|---|---|
| 走行データのアップロード PC（AWS CLI 2.15〜2.38） | 通る見込み。CLI の既定が Content-MD5 か CRC を付ける。PC の設定で `when_required` にしていないかは、導入の前に確かめる |
| Datalake の rlog のデコーダー（boto3 1.36） | 通る見込み（CRC32 を付ける） |
| gaming-data-collection の PC（boto3） | 通る見込み（1.35 以降は既定で付ける）。設定は導入の前に確かめる |
| DataSync（Azure から denso-taxi-video・denso-nx-raw・denso-taxi-processed へ） | 不明。導入の前に、予行用のバケットに向けて試す |
| Databricks | 書き込む経路は見当たらない。Unity Catalog の volume の場所を確かめる |

洗い出しの期間（3 日余り）には、対象の 10 本のうち 9 本で書き込みがありませんでした。この表は、ログに出た書き込み元と、コードから分かる書き込み元によるものです。

### 4.2 意図して消すとき（費用を減らすための削除）

3 か月に 1 度あるかないかを見込んでいます。やるかどうかの検討と決定は、MLOps チームで行います。

| # | 手順 | 誰が |
|---|---|---|
| 1 | 対象のバージョンの一覧（マニフェスト。`Bucket,Key,VersionId` の CSV）を作って、置き場に置く。対象はプレフィックスや正規表現で決めてよい（正規表現は、S3 インベントリか一覧から絞って CSV にする） | FullAccess の人 |
| 2 | チームの決定と一覧を確かめ、ジョブを 2 本作る（① タグ付け、② イベントホールドの解除）。これが承認 | AWSAdministratorAccess の人 |
| 3 | 対象のバージョンにタグを付け、イベントホールドを解除する。解除が通知される | 解除用のジョブのロール |
| 4 | **30 日待つ** | — |
| 5 | タグで絞ったライフサイクルのルールを、cdk-apps の PR で足す。ルールは 2 段にする（下の「取りやめるとき」）。消え終わったら外す | PR を作る人と、レビューする人 |

- タグで絞ったライフサイクルのルールは、意図した削除のたびに足し、終わったら外します。ルールを常に置いておくと、タグを付けるだけで、Object Lock の保護の無いバージョン（既存の最新ではないバージョン）が消えてしまうためです。
- タグ付けのジョブは、そのバージョンのタグを丸ごと置き換えます。

#### 途中で取りやめるとき（ロールバック）

取りやめる方法の基本は、**対象のバージョンに、イベントホールドを付け直す**ことです。AWSAdministratorAccess の人が、同じマニフェストで、イベントホールドを付けるジョブ（`EventHold: ON`）を作ります。付け直したバージョンは、ライフサイクルでも消えなくなります。

| 取りやめる時点 | 状態 | 戻し方 | 戻せるか |
|---|---|---|---|
| 手順 3 の途中（タグ付けだけ済み、解除はまだ） | Object Lock の保護はそのまま。タグが付いただけ | 何もしなくてよい。ライフサイクルのルールが無いので、タグだけでは何も起きない。タグを元に戻したいときは、元のタグ一式を付けるタグ付けのジョブを作る | 戻せる |
| 手順 4 の 30 日のあいだ | 解除したが、保持期限のうちなので消せない | イベントホールドを付け直す。保持期限は、付け直した時刻から数え直しになる（検証済み） | 戻せる |
| 30 日を過ぎ、手順 5 の前 | 保持期限が切れ、Object Lock の保護が無い。今の保護だけ（バージョンを指定した削除は、AWSAdministratorAccess しかできない） | イベントホールドを付け直す。保持期限の切れたバージョンに付け直せるかは、まだ試していない（未検証）。保護の無い既存のバージョンには付けられた（検証済み） | 戻せる見込み |
| 手順 5 のあと、ライフサイクルが動く前 | ライフサイクルのルールが入っている | **先にイベントホールドを付け直し**、そのあと PR でルールを外す。PR より付け直しのほうが早い。保護されたバージョンは、ライフサイクルでも消えない（検証済み） | 戻せる見込み（付け直しは未検証） |
| ライフサイクルが、最新のバージョンを失効させた後（① の段） | 削除マーカーが最新のバージョンになった。データは最新ではないバージョンとして残っている | イベントホールドを付け直してから、削除マーカーを消す（AWSAdministratorAccess）か、削除マーカーの 1 つ前のバージョンを同じキーにコピーする（4.3）。コピーするときはタグを引き継がない（`--tagging-directive REPLACE`）。引き継ぐと、またライフサイクルで消される | 戻せる見込み（付け直しは未検証） |
| ライフサイクルが、最新ではないバージョンを失効させた後（② の段） | バージョンが消えた | 戻せない。ほかに写しは無い | **戻せない** |

- 手順 5 のルールは 2 段にします。① 最新のバージョンを失効させる（削除マーカーが付くだけで、戻せる）。② 最新ではないバージョンは、さらに数日たってから失効させる（`NoncurrentVersionExpiration` の `NoncurrentDays`）。②までの数日が、最後に取りやめられる期間です。日数は 7 章で決めます。タグの条件が最新ではないバージョンにどう効くかは、予行で確かめます（5.3）。
- ライフサイクルは、すぐには動きません。ルールを入れたあとの最初の 0 時（UTC）に動きました（検証済み）。AWS は、実際に消えるまでに遅れることがあるとしています。
- 付け直し（イベントホールドを付ける操作）は通知されません。通知するのは解除だけです。取りやめた人が、チームに知らせます。

### 4.3 誤って通常の削除をしたとき

通常の削除は、削除マーカーを置くだけなので、データは残っています。戻し方は 2 つあります。

| 戻し方 | 誰ができるか |
|---|---|
| 削除マーカーの 1 つ前のバージョン（誤って消す前の最新のバージョン）を、同じキーにコピーする（`CopyObject` でバージョンを指定） | FullAccess など、読み取りと書き込みの権限を持つ人 |
| 削除マーカーを消す（バージョンを指定した削除） | AWSAdministratorAccess だけ（バケットポリシーで、バージョンを指定した削除を禁じているため） |

### 4.4 急ぎの依頼や障害のとき

- **すぐ消してほしいと言われたら:** 依頼を受けた人は、「完全に消すには、最低でも 30 日と、ライフサイクルが動くまでの日数（4.2）がかかる」と答えます。緊急の削除の手順は用意しません。
- **書き込みが止まったら:** AWSAdministratorAccess の人が、そのバケットの既定の保持設定を外します（CLI で、`Rule` の無い設定を `put-object-lock-configuration` で入れる。手順 D までは FullAccess でもできる）。Object Lock 自体は外せません。既定が無ければ新しいバージョンに保持は付かないので、チェックサムなしでも書けるようになる見込みです（未検証）。
- **イベントホールドを付ける対象を誤ったら:** 解除のジョブで外せます。外したバージョンも、解除後の保持期間（30 日）は消せません。
- **イベントホールドを付けるジョブの日数（解除後の保持期間）を誤ったら:** 解除のジョブでは直せません。解除すると、保持期限が「解除した時刻＋誤った日数」で固まるからです。直すには、バケットポリシーから迂回の禁止をいったん外し、迂回の権限を持つロールで、迂回のジョブを作って保持を付け直します。迂回の禁止を外す変更は通知されます。直したら、迂回の禁止を元に戻します。**このため、ジョブを作る前に、設定を 2 人で確かめます。**

## 6. 注意すること

### 6.1 Object Lock は、一度有効にすると戻せない

- バケットの Object Lock は、一度有効にすると無効にできません。
- バージョニングも止められなくなります。
- 戻せないのはこの 2 つです。既定の保持設定は後から外せます。付けた保持も、ガバナンスモードなので、迂回の禁止をいったん外せば直せます（4.4）。
- そのため、原本バケットに導入する前に予行用のバケットで試し（5.1 の手順 B）、書き込みの少ないバケットから順に導入します（5.2）。

### 6.2 チェックサムを付けない書き込みは、できなくなる

既定の保持設定を入れたバケットでは、`Content-MD5` かチェックサムのヘッダー（`x-amz-checksum-*`）を付けない書き込みは拒まれます（検証済み）。1 回の PUT も、マルチパートアップロードのパートも同じです。

**各段階の前に、そのバケットの書き込み元を精査し、チェックサムに対応していない書き込み方法を洗い出します**（4.1・5.3）。とくに次の書き方は拒まれます（検証済み）。

- boto3 1.36 以降で `request_checksum_calculation="when_required"` を設定している（`AWS_REQUEST_CHECKSUM_CALCULATION` の環境変数や `~/.aws/config` での設定を含む）。
- 署名付き URL で、チェックサムを署名に入れずに発行している。boto3 の既定の署名（SigV2）の URL も拒まれる。
- `curl` や `requests` などで、SDK を通さずに直接 PUT していて、チェックサムのヘッダーを付けていない。

## 8. 用語

詳しくは「S3 Object Lock（WORM）の仕組み」の 10 章にあります。

| 用語 | 意味 |
|---|---|
| 原本バケット | 集め直せない・受け取り直せないデータを置く S3 バケット。今の保護は 12 本、Object Lock の対象は 10 本 |
| 主体 | AWS の操作を行う IAM のユーザーやロール |
| バージョン | 同じキーに書くたびにできる、オブジェクトの 1 つ 1 つ。Object Lock で保護される単位 |
| 最新のバージョン・最新ではないバージョン | 1 つのキーに複数のバージョンがある場合の、最新のもの（読み取りで返るもの）と、それ以外。AWS の用語では current version・noncurrent version |
| 通常の削除 | バージョンを指定しない削除。削除マーカーを置くだけで、データは残る |
| 削除マーカー | 通常の削除で置かれる「消した」という印のバージョン |
| 保持・保持期限 | バージョンごとの Object Lock の保護の状態と、その期限 |
| イベントホールド | 解除するまで保護し、解除してから決めた日数保護する保持 |
| 解除後の保持期間 | イベントホールドを解除してから保護する日数 |
| 既定の保持設定 | 新しく書かれたバージョンに自動で付ける保持の値 |
| ガバナンスモード・コンプライアンスモード | 迂回の権限を持つ主体だけが保持を無視できるモードと、root を含めて誰も保持を無視できないモード |
| 迂回 | ガバナンスモードの保持を無視すること（`s3:BypassGovernanceRetention`） |
| 失効 | ライフサイクルで自動に消すこと。保護されているバージョンは消えない |
| S3 Batch Operations | 一覧で指定したたくさんのオブジェクトに、同じ操作をまとめて行う機能 |
| マニフェスト | S3 Batch Operations に渡す、対象の一覧 |
| FullAccess・AWSAdministratorAccess | tuscenes-prod の SSO の権限セット。FullAccess は日々の作業で使う権限のうち最も強いもの（14 名）。AWSAdministratorAccess はその上の権限 |
| deploy のロール | cdk-apps の `main` へのマージで、GitHub Actions が CDK の deploy に使う IAM ロール |
