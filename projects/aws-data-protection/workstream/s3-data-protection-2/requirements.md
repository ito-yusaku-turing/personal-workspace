## 3. 要件の下書き（2026-10-30 の伊藤の回答から）

1. **存続:** データが消えては困る S3 バケットのデータは、MLOps チームが意図して消すと判断するその時まで存続しなければならない。
2. **判断と責任:** 消すかどうかは、最終的に MLOps チームのメンバーが判断する。すべての意思決定の責任は MLOps チームが持つ。
3. **検知:** 意図しない操作と、取り返しのつかない操作は、すべて検知の対象にする（守りの解除を含む）。誰が気づくべきかは、別の軸の設計項目にする。
4. **対象の出入り:** 対象は「データが消えては困る S3 バケット」と抽象化する。新しいバケットが加わることも、移行や廃棄で外れることもある。
5. **前提:** 個人情報や、消去の期限を持つデータは無い。

設計の進め方の決まりごと:

- BreakGlass・WORM などの手段は、どれも選択肢として扱う。選択肢ごとに、どの役割を担えるかを整理する。
- 費用は、必要なら決裁を取るので、議論の対象にしない。
- 監査ログの問題は分けて扱う。

## 4. 要件を明確にするための問い（未回答）

| # | 問い | なぜ要るか |
|---|---|---|
| a | **守る性質は「存続」だけか。** 改ざんされないこと（完全性）、読めること（鍵の削除や、ポリシーで誰も読めなくなることへの備え）も含むか | 含めると、鍵の管理やアクセスのポリシーも守りの対象に入る |
| b | **想定する脅威の範囲。** 誤操作だけか、乗っ取られた主体や内部の悪意も含むか | 範囲で、要る守りの強さが大きく変わる。これまでは「誤操作が一番上」としてきた。誤操作だけなら今の層の延長で足りる可能性が高い。乗っ取りまで含めるなら、WORM や組織の層が要る |
| c | **範囲の外に置くもの。** アカウントの閉鎖、リージョンや AWS 自体の障害、監査ログ | 外に置くなら、残るリスクとして明記する |
| d | **「取り返しのつかない操作」とは何か** | 検知の対象を決めるのに要る。候補: 古い版の削除、守りを外す操作（バージョニング・ライフサイクル・ポリシー・鍵）、権限の変更、ホールドの解除、バケットの削除 |
| e | **消えてから気づくまで、戻すまでに許せる時間** | 検知の速さと、戻す手段（バックアップの要否）が決まる |
| f | **意図して消すとき、判断から実行までに何を求めるか** | 記録だけでよいか、2 人目の確認が要るか、猶予を置くか |
| g | **意図した操作と意図しない操作を、どう見分けるか** | すべてを検知すると、MLOps が判断して行う操作も検知される。事前に申告した操作と照らし合わせるか、すべて通知して人が確かめるか |
| h | **対象のバケットの台帳を、どこに、誰が持つか** | 対象の出入りを扱うのに要る。WORM のように外せない守りを入れたバケットは、外れるときに手当てが要る |

a・b・e で、どの選択肢が要るかがほぼ決まる。とくに **b が一番効く**。

## 5. 設計の骨格の案（要件が固まった後に使う）

選択肢を当てはめる役割の枠。

| 役割 | 中身 | 当てはまる選択肢の例 |
|---|---|---|
| 止める | 権限のない操作を拒む | バケットポリシー、SCP・RCP、主体の掃除 |
| 遅らせる | 取り返しのつかない操作に猶予を置く | WORM（解除の後の猶予） |
| 気づく | 意図しない操作を検知する | 削除の検知（ステージ 2）、守りの変更・解除の検知 |
| 戻す | 消えたものを復元する | バージョニング、別の場所への写し |
| 判断と特権の経路 | 誰が判断し、何を通して実行するか | MLOps の判断、BreakGlass |

選択肢を比べる軸の案: どの役割を担えるか、前提（ほかの選択肢への依存）、採ったら戻せるか（WORM は戻せない）、運用の手間。
