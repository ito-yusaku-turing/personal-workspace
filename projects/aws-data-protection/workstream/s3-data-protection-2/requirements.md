## 3. 要件の下書き（2026-10-30 の伊藤の回答から）

1. **存続:** データが消えては困る S3 バケットのデータは、MLOps チームが意図して消すと判断するその時まで存続しなければならない。
2. **判断と責任:** 消すかどうかは、最終的に MLOps チームのメンバーが判断する。すべての意思決定の責任は MLOps チームが持つ。
3. **検知:** 意図しない操作と、取り返しのつかない操作は、すべて検知の対象にする（守りの解除を含む）。誰が気づくべきかは、別の軸の設計項目にする。
4. **対象の出入り:** 対象は「データが消えては困る S3 バケット」と抽象化する。新しいバケットが加わることも、移行や廃棄で外れることもある。
5. **前提:** 個人情報や、消去の期限を持つデータは無い。

2026-10-30 に、4 章の問いへの回答で足した要件:

6. **守る性質:** 存続と完全性。上書き・改ざんされても元の版が残り、いつ・だれが変えたかが分かること。一時的に読めなくなること（締め出し）は、戻せれば許す（問い a）。
7. **脅威の範囲:** 誤操作と、乗っ取られた主体（外の攻撃者が、キー・SSO のセッション・CI・GitHub App などを乗っ取る）。内部の悪意は範囲の外（問い b）。
8. **範囲の外:** リージョンや AWS 自体の障害、アカウントの閉鎖、監査ログ（別の問題として扱う）。残るリスクとして明記する（問い c）。
9. **取り返しのつかない操作:** 古い版の削除（ライフサイクルの失効を含む）とバケットの削除、守りを外す操作（バージョニング・ライフサイクル・バケットポリシー・所有権・ACL）、例外に届く権限の変更（deploy のロール・例外のロールの作成と信頼の変更、例外の権限セットの割り当て、SCP の変更など）、鍵の解除（WORM を入れたとき）。拒否された試みも含む（問い d）。
10. **気づくまでの時間:** 取り返しのつかない操作は数分以内（即時）に通知する（問い e）。
11. **戻すまでの時間:** 期限は問わない。戻せればよい（問い e）。
12. **意図して消すとき:** 実行の前に判断の記録（だれが・何を・なぜ）を残し、実行する人とは別の MLOps のメンバーが確かめる（問い f）。
13. **見分け方:** 取り返しのつかない操作は、意図したものも含めてすべて即時に通知し、受けた人が判断の記録と照らす。ふつうの削除・上書きは本人に知らせ、本人が気づく形にする（問い g）。
14. **台帳:** 対象のバケットの一覧は、cdk-apps の共通部（`packages/original-bucket-guard`）に置く。守り・記録・検知はそこから読む。持ち主は MLOps で、出入りは PR と承認で行う（問い h）。

設計の進め方の決まりごと:

- BreakGlass・WORM などの手段は、どれも選択肢として扱う。選択肢ごとに、どの役割を担えるかを整理する。
- 費用は、必要なら決裁を取るので、議論の対象にしない。
- 監査ログの問題は分けて扱う。

### 4.1 回答から決まること（設計への影響）

弱点の番号（W1〜W16）は [current-state.md](current-state.md) の 6 章。

- **アカウントの中の守りだけでは足りない（b）。** 例外の主体や deploy の経路を乗っ取られると、バケットポリシーは外される（W4〜W6）。乗っ取られた主体が外せない層が、少なくとも 1 つ要る。候補は、組織の層（SCP・RCP）、WORM、別のアカウントへの写し。アカウントの閉鎖は範囲の外（c）なので、写しは「閉鎖への備え」ではなく「乗っ取りへの備え」として比べる。
- **1 つの主体だけでは、取り返しのつかない操作を通せない形にする（f）。** 2 人目の確認を、手続きだけでなく仕組みで求めるか（2 人が揃わないと外れない層）は、選択肢を比べるときに決める。**共有済みのプランの原則 4（承認ではなく、短いセッション＋通知）と食い違う**ので、プランを直す必要がある。
- **今いちばん大きい穴（W2: cdk-apps の PR 1 本で、ライフサイクルから大量に消せる）は、要件 9・10・12 のすべてに反する。** 承認 1 名は「2 人目の確認」に近いが、何を消すかの判断の確認にはなっていない。ライフサイクルの変更を即時に通知すれば（要件 10）、実行までの 1〜2 日のうちに戻せる。
- **即時の通知が要る（e）。** 毎時の報告（ステージ 2 の設計）では足りない。守りの変更と権限の変更は管理イベントなので、EventBridge で受けられる（10-29 の決定）。古い版の削除はデータイベントで、CloudTrail から EventBridge への配信はベストエフォートなので、取りこぼしの手当て（ログファイルとの突き合わせ）を組み合わせる。
- **戻すまでの期限は問わない（e）。** 復旧の速さは設計の軸にしない。戻す手順と道具（W12）は要るが、急がない。
- **内部の悪意は範囲の外（b）。** 例外の主体自身が消すことは、判断の記録・2 人目・通知で抑える範囲にとどめる。監査ログの守り（W11）も、別の問題として扱う。
- **台帳を共通部に置く（h）。** 5 か所に散らばった一覧（W16）を 1 つにする。新しいバケットは、一覧に足せば守り・記録・検知が付く形にする。

## 5. 設計の骨格の案（要件が固まった後に使う）

選択肢を当てはめる役割の枠。

| 役割 | 中身 | 当てはまる選択肢の例 |
|---|---|---|
| 止める | 権限のない操作を拒む | バケットポリシー、SCP・RCP、主体の掃除 |
| 遅らせる | 取り返しのつかない操作に猶予を置く | WORM（解除の後の猶予） |
| 気づく | 意図しない操作を検知する | 削除の検知（ステージ 2）、守りの変更・解除の検知 |
| 戻す | 消えたものを復元する | バージョニング、別の場所への写し |

選択肢を比べる軸の案: どの役割を担えるか、前提（ほかの選択肢への依存）、採ったら戻せるか（WORM は戻せない）、運用の手間。

## 7. 要承認操作とシステム保全責任者（2026-11-02 の伊藤の決定）

要件 12（2 人目の確認）の議論で決めたこと。仕組みで強制する方法は、権限の構造を調べてから決める（下の「保留」）。

### 7.1 用語

- **要承認操作:** 提案と承認を通さないと実行できない操作。要件 9 の「取り返しのつかない操作」と同じ集まりを指す。守りの変更のように厳密には戻せるものも含むので、別の名前にした。検知（要件 10・13）の対象でもある。
- **システム保全責任者:** 要承認操作を提案・承認できる人の名簿に載った人。仮に 3 人とする。データだけでなく、パイプラインなどの仕組みにも広がる見込みがあるので、名前を S3 やデータに縛らない。
- **提案者・承認者:** 要承認操作ごとの役割。システム保全責任者は互いに対等で、1 件ごとに提案者と承認者に分かれて実行する。提案者と承認者は別の人。
- **最高権限者・通常権限メンバー:** 7.5.1 で足した人のグループ（案）。最高権限者はシステム保全責任者を任命・解任し、通知の受け手の基盤を持つ。通常権限メンバーは、保全性に関わらない変更と cdk の deploy を行う。

### 7.2 S3 のバケットの要承認操作（案。おおむね了承）

1. 消す: 古い版の削除（ライフサイクルの失効を含む）、バケットの削除
2. 守りの変更: バージョニング・ライフサイクル・バケットポリシー・所有権・ACL・Object Lock の既定の変更
3. 権限の変更: deploy のロール・例外のロール・解除用のロールの作成と信頼の変更、例外の権限セットの割り当て、SCP・RCP の変更
4. 鍵の解除: WORM のホールドの解除（入れたとき）
5. 台帳の変更: 対象のバケットを台帳から外すこと
6. 名簿の変更: システム保全責任者の入れ替え。対象の種類によらない共通の操作（→ 7.5 で、最高権限者の操作に移す案にした）

対象がパイプラインなどに広がったら、その種類ごとの要承認操作を足す。名簿と、提案と承認の流れは、S3 専用の場所（`packages/original-bucket-guard`）に置かず、共通にする。

### 7.3 決まったことから導かれること

- 実行には、システム保全責任者のうち 2 人が要る。1 人が乗っ取られても通らない。2 人が不在だと止まるが、要件 11（戻すまでの期限なし）から許せる範囲とみる。
- 共有済みのプランの原則 4（承認フローは置かない）は、やめることになる。

### 7.4 保留

- **名簿の行き詰まり。** 名簿の変更も 2 人が要るので、2 人以上が不在になる・乗っ取られると行き詰まる。
  - **方針（2026-11-02、伊藤）: システム保全責任者より上位の権限保持者は、できれば作らない。** システム保全責任者は互いに対等とし、仕組みを強めて人数を増やすことで行き詰まりを避ける。
  - → 同じ日の CorpIT への聞き取りで前提が変わったので、7.5 で見直した（案）。
  - **構造上の上位権限者の扱い（2026-11-02、伊藤）:** GitHub の組織の owner、AWS の管理アカウントなど、仕組みの構造の上でシステム保全責任者より上に立つ権限は、設計しなくても既にあり、無くせない（[privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md)）。存在は受け入れ、**上位として何が存在しているかの把握と管理を徹底する**。
    - 流れには組み込まない（普段の要承認操作には使わない）。
    - 何が存在するかを台帳にする（privilege-map.md の 8 章）。
    - 数を絞る。使えば即時に通知する。残るリスクとして明記する。
    - 名簿の行き詰まりと流れの故障では、最後のエスケープハッチになる。
    - システム保全責任者自身が構造上の上位権限者を兼ねると、1 人で流れを迂回できる。兼ねないようにする（案。前提 (a) と同じ考え。未決定）。
- **前提の確認（未回答）:** (a) システム保全責任者も普段は直接の権限を持たない、(b) 提案者もシステム保全責任者の中から出す、(c) 流れそのものの故障には、管理アカウントからの操作を最後の手段にする。
- **人数:** 3 人か 4 人か。人数を増やして行き詰まりを避ける場合の注意（名簿から人を外す操作の扱い、不在がまとまって起きること、補充の決まり、最初の名簿の決め方）は、2026-11-02 の議論の記録（workstream）にある。
- **頂点の問題は別の案件に分けた（2026-11-02、伊藤）。** 構造上の上位権限者は、互いに届き合う「頂点の群」になっていて、要件 7 に対して良くない（[privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md) の 9 章）。データの保全の範囲を超えるので、[project:privileged-access の「権限の頂点の把握と管理」](../../../privileged-access/workstream/apex-privileges.md)で、CorpIT と一体で取り組む。この案件は次を前提に進める。
  - 頂点の群の乗っ取りは、別の案件で扱う残るリスクとする。GitHub の上の 2 人の確認が効くのは、ふつうの経路（誤操作、ふつうのメンバーの乗っ取り）まで。
  - 頂点に頼らない守り（WORM の猶予と、輪の外への通知の受け手）は、この案件で持つ。
- **不明点は、ヒアリング項目として溜める**（[privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md) の 7 章）。設計を整理してから、まとめて相談する（2026-11-02、伊藤）。
- **権限の構造の調査を先に行う（2026-11-02、伊藤）。** GitHub の組織・identity・cdk-apps・AWS の各層に、流れを迂回できる経路がどれだけあるかを洗い出さないと、設計が穴だらけになるため。 結果は [privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md)。

#### 7.5.2 示唆と条件

1. **任命・解任を最高権限者に移すことで、権限を使う人と、誰が使うかを決める人が分かれる。**
   - 7.5 の最初の案では、名簿の普段の変更はシステム保全責任者 2 人が行っていた。その形では、2 人が乗っ取られると名簿も書き換えられた。今回の整理では、それができない。
   - 名簿の行き詰まり（7.4 の保留）も、任命の中で解ける。行き詰まりを避けるためにシステム保全責任者を増やす必要は薄れ、仮の 3 名のままで成り立つ。
   - 7.2 の 6（名簿の変更）は、システム保全責任者の要承認操作から、最高権限者の操作に移る。
   - **任命するのは MLOps のメンバーに限る**（要件 2）。誰を候補にするかは MLOps が決め、最高権限者は MLOps の依頼の記録に基づいて任命する。依頼の本人確認は、依頼とは別の経路（対面・電話など）で行う。
2. **最高権限者 1 人の乗っ取りで、名簿を丸ごと入れ替えられる。これに備える。**
   - 4 名はそれぞれ 1 人で名簿に届く（3 名は GitHub の owner、大戸さんは GCP から apply の鍵へ）。「2 名で任命する」と決めても、仕組みでは強制できない。攻撃者が 1 人を乗っ取り、全員を解任して手先を任命すれば、次の承認から思いどおりに通せる。
   - 手当て（案）:
     - **名簿の変更は必ず通知する。** 受け手には、今のシステム保全責任者と MLOps を入れる。
     - **任命されてから権限を使えるまでに、待ちの期間を置く。** その間に、今のシステム保全責任者が異議を出せる。期間の長さと、仕組みで強制する方法は未定。
     - **解任で、名簿を 2 名未満にしない。**
   - **名簿の承認者を、最高権限者にそろえる。** 名簿の実体の承認者は、今は CorpIT の 1 名（山本 修平・山下 卓也。identity の `team_memberships.tf`、P6）で、**山下さんは最高権限者の 4 名に入らない**。名簿のチームの行を別のファイルに分け、その Code Owner を最高権限者にする（CODEOWNERS はファイルの単位なので）。cdk-apps の `.github/CODEOWNERS`（P11）も同じ扱いにする。名簿のチームの maintainer は 0 にする（P4）。
3. **システム保全責任者が兼ねてよいもの、兼ねないもの。**
   - 兼ねない: **最高権限者**（任命する人と使う人が同じになる）、**GitHub の組織の owner**（P1。組織のルールセットを変えられる。C1（[privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md) の 9.1）が通るなら、実質の最上位にも近い）。
   - **cdk-apps の admin（P3）は兼ねてよい。ただし、`main` の保護を組織のルールセットに移すことを条件にする**（伊藤の意向）。
     - 兼任の問題: cdk-apps の deploy のロールが鍵を渡す条件は `repo:turingmotors/cdk-apps:ref:refs/heads/main` だけ（`apps/organization-policy/ci-cdk-deploy-role.yml`、cfc61a5e。確認済み）。`main` の保護が唯一の関門で、今はそれがリポジトリのルールセットなので、admin が 1 人で無効にして、守りの変更や CODEOWNERS の書き換えを `main` に入れられる。システム保全責任者が admin を兼ねると、そのアカウント 1 つの乗っ取りで要承認操作が通る。
     - ただし、兼任を禁じても穴は残る。cdk-apps の admin は 13 名いて、全員が同じ経路をたどれる。塞ぐべきは「リポジトリの admin が `main` の保護を外せる」こと。
     - 条件 1: `main` の保護を、組織のルールセットに移す。組織の owner にしか変えられないので、リポジトリの admin は外せない。最後の push の承認（P12）も入れる。迂回できる主体は自動マージの App（P13）だけにし、その範囲を確かめる。
     - 条件 2: deploy のロールの信頼を、`main` に縛ったままにする。admin は environment の制限を変えられるが、信頼が `ref` で縛ってあれば、別のブランチからは deploy できない。
     - 条件 3: リポジトリの設定の変更（ルールセット・admin の付け外し・environment）を、検知の対象に入れる（K7）。
     - この形なら、admin が 1 人でできるのはリポジトリの設定の変更までで、要承認操作には届かない。maintainer が人を足しても（P4）、足された人も保護を外せない。
     - 確かめること: 組織のルールセットを、いまの Team プランで使えるか（使えるはずだが未確認）。CorpIT に設定してもらえるか（I30・I4）。
   - 当たる人（確認済み）: MLOps 1 の候補（犬塚 眞太郎・岩政 公平・伊藤 祐策・安本 雅啓）は、全員が `team-mlops-1-admin` で cdk-apps の admin。条件を満たせば、そのまま兼ねてよい。安本さんは owner と `team-leaders` も持つので、owner を兼ねない決まりに当たる（I28）。
4. **「通常権限メンバーが cdk の deploy もできる」には、K2（要承認操作の専用の経路）が前提になる。**
   - 今は tuscenes-prod の deploy のロールが 1 組で、どのアプリの PR からでも原本バケットの守りを変えられる（W2）。このままでは、ふつうの deploy と保全性に関わる変更を分けられない。
   - 要ること: ふつうの deploy のロールに、守りの変更を Deny する。守りの設定は共通部（`packages/original-bucket-guard`）に集め、その Code Owner をシステム保全責任者にする。守りの変更は、専用の経路のロールからだけ通す。
   - **この人のグループの整理の土台は K2 になる。**
5. **3 つのグループに入らない、AWS を直接さわれる人がいる。**
   - tuscenes-prod の FullAccess・AWSAdministratorAccess の 14 名（P14）と、AWS の管理アカウントの管理者は、GitHub を通らずに守りを外せる。
   - 通常権限メンバーとして扱うなら、バケットポリシーの例外から外す（K3）。外せない人がいるなら、4 つ目のグループとして台帳（[privilege-map.md](../../../privileged-access/workstream/apex-privileges/privilege-map.md) の 8 章）に載せ、残るリスクとして扱う。AWS の管理アカウントの管理者が最高権限者の中にいれば（I10）、最高権限者に含めて扱える。
6. **最高権限者は、保全の権限を自分で使わない。**
   - 最高権限者は、技術的には組織のルールセットを変えて、自分で守りの変更を通せる。無くせない残るリスク。
   - 役割として「任命・解任と通知の受け手の基盤は持つが、保全の操作の提案と承認はしない」と決め、最高権限者の操作は通知する。
7. **通知の受け手の基盤は、最高権限者が持つ。ただし、受け手の守りには条件が要る。**
   - 受け手は、最上位の層（Workspace・GCP の側）に置く。AWS のアカウントの管理者と、最高権限者でない GitHub の owner は、そこに届かない。
   - **IaC の外に置くだけでは守れない。** Workspace の apply のサービスアカウント（`tf-google-workspace-apply@`）には、ユーザーとグループのすべての操作（パスワードの再設定・停止・削除を含む）が付いている（identity の `platform/google-workspace/README.md`。確認済み）。範囲がドメイン全体なら（I29）、C1 で apply の資格を取った人は、IaC の外の受け手も書き換えられる。人のアカウントは Okta がプロビジョニングしているので、Okta の管理者も受け手を止められるとみられる（推定。I17）。守る条件は「apply のサービスアカウントの管理ロールと、Okta のプロビジョニングが届かないこと」。案: 受け手を Okta の管理の外の OU に置き、apply のロールの範囲をその OU の外に限る。
   - **最高権限者自身の操作の通知は、最高権限者が消せない場所にも残す。** 受け手の基盤を持つのも最高権限者なので、自分の操作の通知を消せる。案: AWS のログ専用のアカウント（Object Lock）のような別系統にも写す。
   - **生存確認は、本物と同じ経路を通るカナリアの操作にする。** 送る仕組みが丸ごと止まったときだけでなく、EventBridge のルールの書き換えで特定のイベントだけ落とされたときにも気づくため。ステージ 2 のカナリアを流用し、届いたかの判定は受け手の側で行う。
8. **2 人の確認が効く範囲と、残る迂回の経路。**
   - 2 人の確認が効かない経路: P3（admin がルールセットを外す）、P4（maintainer がチームに人を足す）、P5・P7（identity の admin）、P12（承認のあとの push）、P13（自動マージの App）、P14（AWS の直接の権限。示唆 5）。
   - P3・P4・P12・P13 は、組織のルールセット（示唆 3 の条件）で、要承認操作に届かなくする。P5・P7 は、admin が 1 人で変えられることは変わらないので、検知の対象に足す（K7）。P14 は K3 で狭める。
9. **残るリスクを名前で書く。**
   - 「最高権限者（と、AWS の管理アカウントの管理者）のアカウントの乗っ取り」。
   - これに効くのは、WORM のコンプライアンスモードだけ（K6 のフルスペック）。Quick Win はガバナンスモードで、迂回の Deny を外せる主体（バケットポリシーを変えられる主体）には効かない。**フルスペックまでは、この乗っ取りに効く守りが無い期間がある。**
   - 最高権限者の要件（管理用のアカウントの分離、フィッシングに強い MFA）は、[project:privileged-access](../../../privileged-access/workstream/apex-privileges.md) で扱う。

別の案（7.5.1 には入れていない）: 前提 (c)（流れの故障の最後の手段は管理アカウント）は、AWS の管理アカウントの管理者が最高権限者の中にいれば、「最高権限者」に一本化できる（I10）。

## 8. 課題の整理（2026-11-02）

頂点の問題を [project:privileged-access](../../../privileged-access/workstream/apex-privileges.md) に分けたあとの、この案件の課題。弱点の番号（W）は [current-state.md](current-state.md) の 6 章。

### 8.1 決まっていること

- 要件 1〜14（3 章）。脅威は誤操作と乗っ取り。取り返しのつかない操作はすぐに通知し、意図して消すときは判断の記録と 2 人目の確認を求める。
- BreakGlass は撤回の方向。WORM（コンプライアンス・イベントホールド・解除の後 30 日）は、外せない層の本命の候補（仮決定）。
- 要承認操作・システム保全責任者・提案者と承認者（7 章）。
- 人のグループは、7.5.1 で最高権限者・システム保全責任者・通常権限メンバーの 3 つに整理した（案）。最高権限者は、システム保全責任者の任命・解任と、通知の受け手の基盤を持つ。最高権限者のアカウントの乗っ取りは、別の案件で扱う残るリスクとする。
