手順 C で、各バケットの最新版にイベントホールドを付けるジョブの対象の一覧を、S3 Batch Operations に作らせられるか（ManifestGenerator）を確かめる。AWS のドキュメントには、バージョニングが有効なバケットでの版の扱いが書かれていない（2026-11-09 に確かめた）。

## 確かめること

| # | 問い | なぜ要るか |
|---|---|---|
| M1 | 作られた一覧に、古い版が入るか | 入るなら、古い版にもホールドが付いてしまう（D7 は古い版にかけない）。最新版だけに絞る設定は、ドキュメントに無い |
| M2 | 最新が削除マーカーのキーは、一覧に入るか。入るなら、ジョブはどうなるか | 原本バケットにも、通常の削除をしたキーがある |
| M3 | 一覧に版の ID の列があるか | 無ければ、ジョブを流した時点の最新版に付く |
| M4 | 記号・空白・日本語を含むキーを、一覧とジョブが正しく扱うか | 大きいバケットで流す前の確かめ（I6） |
| M5 | 確認待ちの設定（`--confirmation-required`）で、一覧を作った段階で止まるか | API から作ったジョブで効くかは、ドキュメントが食い違う。止まるなら、流す前に一覧を確かめられる |

## 0. 前提と注意

- **カナリア `original-bucket-canary-767397804933` を使う。** 訓練用に使うと決めた（D23）。Object Lock はまだ入っていない。
- 操作は、前回（10-30）と同じ**タグ付け**にする。カナリアに対しては無害。
- 費用は、ジョブ 1 本で $0.25 程度。
- **古い版は、カナリアのライフサイクルで 3 日たつと消える。** setup から run までを 3 日以内に行う。
- 試験用のロール `original-bucket-canary-manifest-probe` は、最後に消す（cleanup）。作ったキーは残す。

```bash
aws sso login --profile full         # 切れていれば
cd ~/runbook/manifest-probe
```

## 1. 手順

| 手順 | コマンド | すること | 終わったら |
|---|---|---|---|
| 1 | `bash manifest-probe.sh setup` | 試すキー 4 つ（下の表）と、試験用のロールを作る | 15 秒ほど置く |
| 2 | `bash manifest-probe.sh job` | ジョブを作る（確認待ちの設定つき）。止まるまで待ち（最長 30 分）、作られた一覧を出す | **エージェントに知らせる**。エージェントがログを読む（M1〜M5） |
| 3 | `bash manifest-probe.sh run` | 確認待ちのジョブを流す。終わるまで待ち、結果のレポートと各版のタグを出す | **エージェントに知らせる** |
| 4 | `bash manifest-probe.sh cleanup` | 試験用のロールを消す | — |

- `bash manifest-probe.sh show` で、いつでも今の状態（版・ジョブ・一覧・レポート・タグ）を出せる。
- ジョブが `Failed` になったら、エージェントに知らせる。ロールの権限の不足なら、エージェントがスクリプトを直す。

試すキー（`manifest-probe/obj/` の下）:

| キー | 作り方 | 版の状態 |
|---|---|---|
| `a.txt` | 1 回書く | 最新版だけ |
| `b.txt` | 2 回書く | 最新版と古い版 |
| `c.txt` | 書いてから消す | 最新が削除マーカー。古い版が 1 つ |
| `d 日本語+%&.txt` | 1 回書く | 最新版だけ（M4） |

試験用のロール: 信頼は S3 Batch Operations だけ（`aws:SourceAccount` で tuscenes-prod に固定）。権限は、カナリアの `manifest-probe/obj/` の読み取りとタグ付け、`manifest-probe/out/`（作られた一覧）と `manifest-probe/report/`（結果のレポート）への書き込み、一覧を作るための `s3:PutInventoryConfiguration`。

## 結果

| # | 結果 | 根拠 |
|---|---|---|
| M1 | **入らない**。b は最新版だけが一覧に入り、古い版は入らなかった。タグも最新版にだけ付いた | job・run のログ（一覧の CSV、各版のタグ） |
| M2 | **入らない**。最新が削除マーカーの c は、削除マーカーもその前の版も一覧に入らず、ジョブの対象にならなかった | job のログ（一覧の CSV） |
| M3 | **ある**。列は `Bucket, Key, VersionId, IsLatest, IsDeleteMarker`。一覧は作った時点の写しになる | job のログ（`manifest.json` の `fileSchema`） |
| M4 | **正しく扱う**。一覧ではキーが URL エンコード（空白は `%20`）され、ジョブは d にもタグを付けた。結果のレポートでは空白が `+` になる（エンコードの形が一覧と違うので、レポートを読むときは注意） | run のログ（結果のレポート、各版のタグ） |
| M5 | **止まる**。作ってから約 20 秒で `Suspended`（件数 3）。`Ready` にすると約 40 秒で終わった。流す前に一覧を確かめられる | job・run のログ |

ジョブ ID: `81f30b34-6899-4586-95cb-2aee6629bc5f`（3 件、成功 3）。作られた一覧の置き場: `manifest-probe/out/<バケット名>/<ジョブ ID>/`（目次の `manifest.json` と、`data/` の CSV（gzip））

**手順 C への意味:** 対象の一覧は、ジョブに作らせれば足りる（S3 Inventory は要らない）。古い版に付けない（D7）とも合う。一覧は作った時点の写しなので、既定の保持設定を入れてから作る。確認待ちで止めて、件数と中身を 2 人で確かめてから流せる。8 億件の規模での時間と費用、ジョブと独立に件数を突き合わせる手段は、まだ分かっていない。
