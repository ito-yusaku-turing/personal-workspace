作成: 2026-10-29 ／ 伊藤（下書きはエージェント）

> **2026-10-29 追記:** チーム向けの資料は [breakglass-proposal.md](breakglass-proposal.md) に書いた。この資料は内部の検討の記録として残す。同日、伊藤の方針で「ふだんの権限は今の FullAccess のまま変えず、昇格は BreakGlass のときだけ」と決めた（5.2 の形）。

**叩き台です。** 伊藤の判断とチームの議論の前の案で、決まったことはまだありません。一般論は [特権アクセスと break-glass の一般論](../../documents/privileged-access-and-break-glass.md) にまとめ、ここでは当社（tuscenes-prod と原本バケット 12 本）に当てはめた案だけを書きます。

## 1. この資料で決めたいこと

第二弾の 4 原則のうち、次の 2 つを実際の運用にします。

- 原則 2: 古い版の削除と、守りを外す操作は、break-glass の人だけに限る。
- 原則 4: 普段は使わず、必要なときに昇格する（承認ではなく、短いセッション＋通知）。

ステージ 1 のバケットポリシーの例外は、暫定で SSO の FullAccess と AWSAdministratorAccess にしています。BreakGlass の権限セットと名簿ができたら、例外をそちらに差し替えます（TODO 10）。WORM 化の案 A（ガバナンスモードの迂回を BreakGlass だけに許す）も、この設計が前提です（TODO 26）。

## 2. 用語: 「昇格用」と「緊急用」を分ける

一般論では、次の 2 つを別のものとして扱います。

| | 昇格用（特権の昇格） | 緊急用（本来の break-glass） |
|---|---|---|
| 何のためか | ふだんの作業では使わない強い操作を、必要なときだけ行う | IdP（Okta）や SSO が止まったときにも、アカウントに入る |
| 使う頻度 | まれだが、計画して使う（復旧・意図した削除・守りの設定の変更） | ほぼ使わない。使ったらインシデント |
| 入口 | ふだんと同じ Okta → IAM Identity Center | Okta を通らない別の経路 |

これまで「BreakGlass」と呼んできた権限セット（[permission-upgrade-plan.md](permission-upgrade-plan.md) の「break-glass の権限セットはどれか」）は、**昇格用**です。Okta が止まれば、これも使えません。

**論点 A:** 名前をどうするか。

- 案 1（推奨）: 権限セットの名前は `BreakGlass` のまま、資料の中では「昇格用」と呼ぶ。すでにプランやバケットポリシーの設計に `AWSReservedSSO_BreakGlass_*` と書いているため、変える手間が要らない。
- 案 2: 権限セットを `Elevated` などに改め、`BreakGlass` は緊急用に取っておく。一般の用語に合う。

## 4. 想定する脅威と、守りの強さの目安

大企業の仕組みをそのまま持ち込むと、人数に対して重すぎます。何から守るかで、強さを決めます。

| 脅威 | 起こりやすさ | この設計で効かせたいこと |
|---|---|---|
| うっかりした誤操作（スクリプトの誤り、対象の取り違え） | 高い | ふだんの権限では、古い版も守りも消せない。昇格するときに「今から強い操作をする」と意識させる |
| 認証の情報を盗まれる（フィッシング、端末の乗っ取り） | 中くらい | 昇格用はフィッシングに強い MFA でしか使えない。使ったら必ず通知が飛ぶ |
| 内部の悪意 | 低い | 通知とログで、後から必ず分かるようにする。予防までは狙わない |

## 5. 叩き台

### 5.1 名簿

- **人数は 2〜3 名にします。** 1 名だと、その人が休んだときに誰も復旧できません。4 名以上は、絞った意味が薄れます。
- 選ぶ基準:
  - 正社員であること（業務委託の人は外す）。
  - 原本バケットの運用に、職務上の責任があること（MLOps 1 チームを想定）。
  - 下の 5.3 の認証の要件を満たせること。
- 名簿は identity の Okta のグループ（例: `APP:AWS BreakGlass`）で持ち、割り当ては cdk-apps の `organization-policy` で行います。どちらも PR とレビューを通るので、変更が記録に残ります。
- **論点 B:** 誰にするか。

### 5.2 権限セット

- 名前は `BreakGlass`（論点 A）、中身は AdministratorAccess、セッションは 1 時間。
- 割り当て先は tuscenes-prod だけにします。ほかのアカウントに広げるかは、別に考えます。
- ステージ 1 のバケットポリシーの例外を、FullAccess・AWSAdministratorAccess から `AWSReservedSSO_BreakGlass_*` に差し替えます。差し替えると、FullAccess の人は 12 本の古い版を消せず、守りも外せなくなります。**ふだんの権限を削る作業（ステージ 3 の普段用の権限セット）を待たずに、原則 2 はここで実現します。**
- 残る抜け穴: FullAccess の人は、CDK の deploy のロールを経由すれば、まだ守りを外せます（[cdk-apps#2252](https://github.com/turingmotors/cdk-apps/pull/2252) の README の「残っている抜け穴」）。塞ぐのは SCP・RCP（TODO 24）か、FullAccess を普段用に置き換える作業（ステージ 3）です。

### 5.3 認証

- 昇格用のグループの人には、フィッシングに強い要素を必須にします。例えば、Okta FastPass（生体認証つき）や、FIDO2 のセキュリティキーです。
- **確かめること:** Okta の認証ポリシーは、アプリ（IAM Identity Center）ごとに付きます。権限セットごとには分けられないはずです。そのため、次のどちらかになると考えています。
  - 案 1: AWS のアプリを使う全員（`APP:AWS`）に、フィッシングに強い要素を必須にする。簡単で、守りも広く効く。
  - 案 2: 昇格用のグループの人にだけ、ルールで強い要素を求める。ただし、その人がふだんの権限で入るときにも同じ要素が要る。
- どちらにするかは、identity の担当（CorpIT）と相談します（TODO 11）。

### 5.4 使うときの規律

- 使ってよい場面:
  - 削除や誤操作からの復旧（削除マーカーを消す、古い版から戻す）。
  - 意図した大量の削除。ライフサイクルの規則を書いて行う（原則 2）。
  - 守りの設定の変更（バケットポリシー、バージョニング、ライフサイクル、Object Lock）。
  - 訓練。
- 使う前に、理由を決めた Slack のチャンネルのスレッドに書きます。承認は求めません。
- 昇格したら、通知が自動でそのチャンネルに飛びます。**名簿に入っていない人が、その通知を見て確かめます。**
- 認証の情報やセッションを、ほかの人と共有しません。

### 5.5 通知

- 昇格用のロールの利用（`AWSReservedSSO_BreakGlass_*` を名乗った記録）を、CloudTrail の管理イベントから EventBridge で拾い、Slack に送ります。
- **保留にしている部品に頼っています。** 「Slack の bot」と「管理イベントを EventBridge で受ける仕組み」は、ステージ 2 で作る予定でした（10-29 に保留）。BreakGlass を使い始める前に、この 2 つだけは先に作る必要があります。
- **確かめること:** SSO のロールを名乗る記録（`AssumeRoleWithSAML`）が、どのリージョンに記録されるか。

### 5.6 見直しと訓練

- 名簿は、半年ごとと、異動のときに見直します。
- 訓練も半年ごとに行います。カナリアのバケットで、昇格して古い版を消し、通知が飛ぶことを確かめます。Microsoft のガイドは緊急用のアカウントを 90 日ごとに試すよう求めていますが、昇格用はふだんの入口と同じ Okta を通るので、半年ごとで足りると考えています。
- 一度も使われないまま、手順が使えなくなっていることを防ぐのが目的です。

### 5.7 緊急用の入口（Okta が止まったとき）

- root の認証情報を消すと、Okta が止まったときに tuscenes-prod に入る道が無くなります。
- 管理アカウントからの `sts:AssumeRoot` は、緊急用の入口になりません。できる作業が、S3・SQS の全拒否のポリシーの削除と、root の認証情報の管理に限られるためです。ステージ 1 で締め出されたときの戻し道にはなります。
- 案:
  - 案 1: AWS のガイドの形。管理アカウント（か緊急用の専用アカウント）に、ハードウェアの MFA を付けた緊急用の IAM ユーザーを 2 人分置きます。各アカウントには、そのユーザーが名乗れる緊急用のロールを置きます。パスワードと MFA のキーは別の人が持ち、使うには 2 人が要るようにします。組織全体の仕組みなので、CorpIT の担当になります。
  - 案 2: root のパスワードの回復を、緊急時の手順にする。root の一元管理で「パスワードの回復を許可」し、root のメールを受け取れる人が設定し直します。終わったら認証の情報を再び消します。ただし、root のメールの受信箱自体が Okta（Google Workspace のログイン）に頼っていると、Okta が止まったときに使えない可能性があります。
  - 案 3: 置かない。Okta が止まっているあいだは待ちます。原本バケットの守りは、止まっているあいだも効き続けます。
- **論点 C:** 緊急用の入口を、この案件で扱うか、CorpIT の root の案件（[aws-root-credentials.md](../aws-root-credentials.md)）に寄せるか。組織全体に関わるので、私は CorpIT に寄せるのがよいと考えています。この案件としては、当面は案 3（待つ）で困らないことを確かめれば足ります。

### 5.8 名簿の外にいる「同等の人」

- 管理アカウントの管理者（`AWSControlTowerAdmins` の 7 名）と、`organization-policy` の deploy の経路を変えられる人は、自分に BreakGlass を割り当てられます。そのため、実質的には名簿と同じ強さを持ちます。
- この人たちを名簿に数えるのではなく、「割り当ての変更が必ず記録・通知される」ことで補います。
  - `organization-policy` の PR のレビュー（CODEOWNERS の 2 名）。
  - 管理アカウントの CloudTrail の通知（CorpIT の側の設定）。
