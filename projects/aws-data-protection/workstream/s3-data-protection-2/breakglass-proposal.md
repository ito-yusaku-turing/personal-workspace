## 1. BreakGlass 権限とは

この資料で扱う BreakGlass は、**権限**です。tuscenes-prod に IAM ロール `BreakGlass` として作り、Okta に足す BreakGlass 専用のアプリから入ります。ふだんの入口（Okta → AWS IAM Identity Center）とは別の入口にすることで、入るたびに本人確認をし直せるようにします（4 章）。

人のうち、BreakGlass 権限で入った人だけが、原本バケットに対する次の操作をできます。以下、この表の操作をまとめて「**古い版の削除や守りを外す操作**」と呼びます。

| 分類 | 操作 | S3 の API |
|---|---|---|
| 消すと戻せない操作 | 古い版の削除 | `s3:DeleteObjectVersion` |
| | バケットの削除 | `s3:DeleteBucket` |
| | Object Lock の設定の変更 | `s3:PutBucketObjectLockConfiguration` |
| 守りを外す操作 | バージョニングの停止 | `s3:PutBucketVersioning` |
| | ライフサイクルの変更・削除 | `s3:PutLifecycleConfiguration` |
| | バケットポリシーの変更・削除 | `s3:PutBucketPolicy`、`s3:DeleteBucketPolicy` |
| | 所有者の設定・ACL の変更 | `s3:PutBucketOwnershipControls`、`s3:PutBucketAcl` |

- ふつうの削除と上書き（`s3:DeleteObject`・`s3:PutObject`）は、この表に入りません。バージョニングで古い版が残り、戻せるためです。
- 人以外では、CDK の deploy の経路（CloudFormation が使う実行ロール）が、守りを外す操作をできます。CDK で守りの設定そのものを管理しているためです。この経路の扱いは 2.2 に書きます。root の扱いは 5 章に書きます。

BreakGlass 権限の中身は、AdministratorAccess です。BreakGlass 権限を持つ人は、日常の作業で FullAccess（2 章）も使っています。BreakGlass 権限で増えるのは上の表の操作だけにし、復旧の作業の途中で FullAccess と行き来しなくて済むようにします。中身を S3 の操作に絞る案は、補足 2 に書きます。

### 1.1 設計の考え方

名前は、非常ボタンなどを覆うガラスに書かれた "Break glass in case of emergency"（非常時はガラスを割ってください）に由来します。BreakGlass 権限は、この非常ボタンと同じ 2 つの性質を持つように設計します。

**必要なときは、許可を待たずに使える**

- 非常ボタンは、誰かの許可を得てから押すものではありません。BreakGlass 権限も、承認の手続きを挟まず、持っている人が自分の判断で使えるようにします。
- 復旧の作業は、急ぐことが多いためです。承認者が不在で作業が止まる、ということが起きないようにします。
- その代わり、持つ人を 2〜3 名に絞り、BreakGlass 権限のセッションは 1 時間で切れるようにします。

**使ったことが必ず分かる**

- 割れたガラスは元に戻せないので、非常ボタンが押されたことは必ず分かります。BreakGlass 権限も、使ったことが必ず周りに分かるようにします。
  - 使う前に、理由を Slack に書きます。
  - BreakGlass 権限で入ったら、Slack に自動で通知が飛びます。
  - BreakGlass 権限を持たない人が、通知を確かめます（1.3）。
- BreakGlass 権限で入るたびに、フィッシングに強い MFA（スマートフォンのパスキーなど）を求めます。通知に出た名前が、本当にその人の操作であることを保証するためです。具体的な形は 4 章に書きます。

この 2 つは対になっています。**許可を待たない代わりに、使ったことを隠せない**ようにします。事前に止めるのではなく、事後に必ず分かることで守る、という考え方です。

### 1.2 古い版の削除や守りを外す操作は、原本バケットの側で止める

古い版の削除や守りを外す操作（1 章の表）を止める方法は、大きく 2 つあります。

- **人の側で止める:** 一人ひとりが使う権限から、これらの操作を外す。例えば、MLOps チームが日常の作業で使っている権限セット FullAccess（2 章）から外す。
- **原本バケットの側で止める:** 原本バケットが、BreakGlass 権限以外からのこれらの操作を拒否する。

この提案では、**原本バケットの側で止めます。** 止める仕組みは、原本バケットのバケットポリシーです。

- バケットポリシーは、操作する人やアプリがどんな権限を持っていても効きます。FullAccess を持つ人でも、BreakGlass 権限で入っていなければ拒否されます。
- 一人ひとりの権限セットには手を付けないので、日常の作業は今のままできます。BreakGlass 権限を使うのは、古い版を消すときや、守りの設定を変えるときだけです。
- アプリや、使われていない古いロールなど、人以外の主体は、同じバケットポリシーですでに止めています（2026-10-23〜26 に導入）。人についても同じ仕組みで止めるので、守りの設定が 1 か所にまとまります。
- 例外の CDK の deploy の経路は、組織のポリシー（SCP: Service Control Policy）で、人が使えないようにします（2.2）。

### 1.3 使ってよい場面と、使うときのルール

使ってよい場面:
- 削除や誤操作からの復旧（削除マーカーを消す、古い版から戻す）。
- 意図した大量の削除。ライフサイクルの規則（期限を決めて S3 に消させる設定）を書いて行います。
- 守りの設定の変更（バケットポリシー、バージョニング、ライフサイクル、Object Lock）。
- 定期的な訓練。

使うときのルール:
- 使う前に、決めた Slack のチャンネルに理由を書きます。承認は求めません。
- BreakGlass 権限で入ったら、同じチャンネルに通知が飛びます。BreakGlass 権限を持たない人が、通知の前に理由が書かれているかを確かめます。書かれていなければ、本人に確かめます。
- 認証の情報やセッションを、ほかの人と共有しません。

### 1.4 BreakGlass 権限でないもの

一般には、break-glass は「Okta などの通常の入口が止まったときにも入れる、緊急用の入口」を指すこともあります。この資料の BreakGlass 権限は、その意味の緊急用の入口ではありません。

BreakGlass 権限には、Okta の専用のアプリから入ります。そのため、**Okta が止まっていると使えません。** これは今の FullAccess（Okta → IAM Identity Center）も同じで、BreakGlass 権限を入れても変わりません。Okta が止まったときにも入れる緊急用の入口は、別に CorpIT チームと考えます（5 章）。

## 2. FullAccess はどう変わるか

### 2.1 今の FullAccess

FullAccess は、MLOps チームが日常の作業で使っている権限セットです。

| 項目 | 今の状態 |
|---|---|
| 中身 | AdministratorAccess（AWS のほぼすべての操作ができる）。加えて、td1-raw と tuscenes-raw のオブジェクトの削除（`s3:DeleteObject*`。古い版の削除を含む）を拒否する文を持つ |
| 使われている範囲 | tuscenes-prod のほか、ota など複数のアカウント |
| 持つ人 | tuscenes-prod で 13 名。Okta のグループ「Autonomous Driving Group 3」（Infrastructure Team）と「Autonomous Driving Group 4」（MLOps 1 Team・MLOps 3 Team）の、それぞれ役員・正社員（6 名と 8 名。1 名が両方に入っている）。2026-10-29 に cdk-apps と identity の main で確認 |
| セッションの長さ | 12 時間 |
| 管理の仕組み | 権限セットと割り当ては cdk-apps の `apps/organization-policy`、グループは Okta から同期 |
| 原本バケットの古い版の削除や、守りを外す操作 | **今は、ほぼできる。** 原本バケットのバケットポリシーで、暫定の例外にしているため。ただし td1-raw と tuscenes-raw では、上の削除の拒否が効くので、古い版の削除はできない |

FullAccess は、名前とは違い、今もすべての操作ができるわけではありません。上の削除の拒否のほか、組織のポリシー（SCP）で IAM ユーザーの作成なども止めています。FullAccess は「日常の作業で使う、いちばん強い権限」と読むのが実態に合います。

Control Tower の AWSAdministratorAccess（`Engineers` グループの 1 名。2022 年の古い設定の残り）も、FullAccess と同じく暫定の例外になっています。この資料では、FullAccess と同じ扱いにします。この権限には削除の拒否が無いので、td1-raw と tuscenes-raw の古い版を今消せるのは、この 1 名だけです。

### 2.2 FullAccess でできなくなること

**FullAccess の権限セット（IAM のポリシー）は書き換えません。** 原本バケットのバケットポリシーと、組織のポリシー（SCP）で、FullAccess ではできないようにします。

| # | できなくなること | 方法 |
|---|---|---|
| ① | 原本バケットの古い版の削除や、守りを外す操作（1 章の表） | 原本バケットのバケットポリシーの例外から、FullAccess を外し、BreakGlass 権限（ロール `BreakGlass`）に差し替える |
| ② | CDK の deploy の経路を、人が使うこと | SCP で、CDK の deploy に使うロールを、CI（GitHub Actions）以外から使えないようにする |
| ③ | BreakGlass 権限の仕組みを書き換えること | SCP で、ロール `BreakGlass` と、Okta との SAML（Security Assertion Markup Language）の連携の設定を、deploy の経路以外から変更できないようにする（4.4） |

- ② と ③ は、① の抜け道を塞ぐためのものです。
- ② について: CDK の deploy の経路（CloudFormation が使う実行ロール）は、原本バケットのバケットポリシーを書き換えられます。今は、FullAccess の人が deploy 用のロールを名乗ったり、CloudFormation に実行ロールを渡したり（`iam:PassRole`）すれば、守りを外せます。SCP の具体的な書き方は、これから決めます。
- ③ について: FullAccess は tuscenes-prod の管理者なので、守らないと、ロール `BreakGlass` の信頼の設定を書き換えて自分を足したり、SAML の連携の設定を差し替えたりできます。
- deploy は GitHub Actions に任せる運用なので、② で日常の作業は困らない見込みです。人が手元で `cdk diff` などをするときに使うロールは止めないので、それで困らないかを事前に確かめます。

### 2.3 変わらないもの

- 日常の作業。1 章の表に無い操作は、今までどおり FullAccess でできます。ふつうの削除と上書きも含みます（td1-raw と tuscenes-raw の削除は、今と同じく FullAccess ではできません）。
- 原本バケット以外のバケットと、ほかの AWS のリソース。
- ほかのアカウントでの FullAccess。
- FullAccess の名前、セッションの長さ、ログインの方法。BreakGlass 権限は別の入口から入るので、FullAccess のログインには影響しません。

## 4. BreakGlass 権限の入り方と MFA の実装

この章は、BreakGlass 権限に入るときの本人確認を、どう実装するかの提案です。

### 4.1 全体の形

```
ふだん:      Okta ──(AWS IAM Identity Center のアプリ)──> IAM Identity Center ──> FullAccess
BreakGlass: Okta ──(BreakGlass 専用のアプリ・入るたびにパスキー)──> tuscenes-prod の IAM ──> ロール BreakGlass
```

- BreakGlass 権限には、ふだんとは別の Okta のアプリから入ります。tuscenes-prod の IAM に、SAML で直接つなぎます。
- **Okta の認証ポリシーは、アプリごとに付けられます。** BreakGlass 専用のアプリにだけ、「入るたびに、フィッシングに強い要素で認証し直す」を設定します。朝に FullAccess のためにログインしていても、BreakGlass 権限に入るときには、改めて本人確認を求めます。
- IAM Identity Center の権限セットとして作る形では、これができません。IAM Identity Center は、ID の出どころが Okta のとき、権限セットを選ぶ瞬間に MFA を求める手段を持たないためです（補足 3）。

### 4.2 Okta の設定

| 項目 | 設定 |
|---|---|
| グループ | BreakGlass 権限を持つ人のグループ（例: `APP:AWS BreakGlass`）。identity リポジトリで管理する |
| アプリ | 汎用の SAML 2.0 のアプリ。グループだけに割り当てる。Okta の公式の AWS 用アプリは、ロールの一覧を取るのに IAM ユーザーのアクセスキーを要求するので使わない（この組織は SCP で IAM ユーザーの作成を止めている） |
| アプリが送る属性 | `Role`（ロール `BreakGlass` と SAML の連携の設定の ARN）、`RoleSessionName`（本人のメールアドレス）、`SessionDuration`（3600 秒） |
| 認証ポリシー | このアプリ専用。グループの人に、フィッシングに強い要素（Phishing-resistant）を必須にし、再認証の頻度は「入るたびに」（Every time user signs in to resource）にする |
| 変更の通知 | アプリの割り当てやポリシーの変更を、Okta の System Log から通知する（4.5） |

### 4.3 MFA の要素

社員は全員、個人のスマートフォンを持っているので、それを使います。

| 要素 | フィッシングへの強さ | 使い方 |
|---|---|---|
| **パスキー（FIDO2）を推します** | 強い。偽のサイトでは使えない | スマートフォンに登録する。PC で入るときは、画面の QR コードをスマートフォンで読み、Bluetooth でつながったスマートフォンで認証する |
| Okta FastPass | 強い | ログインする PC 自体に Okta Verify が要る。会社の PC に入っていれば使える |
| 物理のセキュリティキー（予備） | 強い | 1 本 1 万円程度。スマートフォンをなくしたときや、PC でスマートフォンのパスキーが使えないときの予備として、2〜3 本用意する |
| Okta Verify のプッシュ通知、6 桁のコード（TOTP） | 弱い。偽のログイン画面が本物に中継すると破られる | 使わない。認証ポリシーで弾かれる |

- iCloud や Google アカウントで同期されるパスキーも、Okta はフィッシングに強い要素として扱います。ただし、Okta には「同期されるパスキーをブロックする」設定があります。今の値を CorpIT チームに確かめます。
- スマートフォンをなくしたときの、要素の登録し直しの手順も、CorpIT チームと決めます。

### 4.4 AWS の設定

すべて cdk-apps で管理し、tuscenes-prod に deploy します。

| 項目 | 設定 |
|---|---|
| SAML の連携の設定（IAM の SAML プロバイダー） | Okta のアプリのメタデータを登録する。Okta の署名の証明書に期限があるので、更新の時期を記録しておく |
| ロール `BreakGlass` | 中身は AdministratorAccess。セッションの最長は 1 時間 |
| ロールの信頼の設定 | 上の SAML の連携からだけ入れる（`saml:aud`）。さらに、入れる人を 2〜3 名のメールアドレスに固定する（`saml:sub`） |
| SCP での守り（2.2 の ③） | ロール `BreakGlass` の信頼の設定・ポリシーの変更と削除、SAML の連携の設定の作成・変更・削除を、deploy の経路以外から拒否する |

- 信頼の設定で人を固定するので、**名簿は Okta のグループと cdk-apps の 2 か所に持ちます。** 手間は増えますが、これが狙いです。Okta の管理者が自分をアプリに割り当てるだけでは入れず、cdk-apps の PR とレビューも要るようになります。
- 原本バケットのバケットポリシーの例外は、`arn:aws:iam::767397804933:role/BreakGlass` という固定の名前で書けます。
- 不正な利用に気づいたときは、ロールのセッションを AWS のコンソールからすぐに無効にできます（Revoke sessions）。

### 4.5 通知

| 何を | どこから | 注意 |
|---|---|---|
| BreakGlass 権限で入ったこと | tuscenes-prod の CloudTrail の `AssumeRoleWithSAML`（ロール `BreakGlass` あて）を、EventBridge で拾って Slack に送る | この記録は CloudTrail で「読み取りの操作」に分類される。EventBridge のルールは、読み取りの操作も受け取る設定（`ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS`）で作る必要がある。記録されるリージョンは、検証（手順 7）で確かめる |
| BreakGlass 権限での操作 | CloudTrail の記録。セッション名が本人のメールアドレスになる | 通知は入ったときだけにし、操作の中身は後から CloudTrail で追う |
| Okta のアプリの割り当てや、認証ポリシーの変更 | Okta の System Log | 通知の仕組みは CorpIT チームと相談する |

### 4.6 使うときの流れ

1. Slack の決めたチャンネルに、理由を書きます。
2. Okta のダッシュボードで「AWS BreakGlass」のタイルを押します。
3. パスキーなどで認証します（毎回求められます）。
4. ロール `BreakGlass` で AWS のコンソールに入ります。同時に、Slack に通知が飛びます。
5. 作業します。コマンドが要るときは、コンソールから CloudShell を開きます。
6. 1 時間でセッションが切れます。続けるときは、2 からやり直します。

- 手元の PC の CLI からは、当面は使いません。CLI 用の仕組み（okta-aws-cli など）は、Okta のアプリがもう 1 つ要り、設定も複雑になるためです。
- FullAccess と同じブラウザで使うときは、ブラウザの別のプロファイルを使うか、AWS のコンソールの複数のセッションの機能を使います。

## 5. 残るリスク

この提案で、意図して受け入れるリスクです。

- **FullAccess が盗まれると、原本バケット以外は壊せます。** ほかのバケット、EC2、IAM などです。この提案で守るのは、原本バケット 12 本に絞っています。日常の作業の不便を増やさないことを優先しました。
- **Okta が止まっているあいだは、BreakGlass 権限を使えません。** 今の FullAccess も同じで、BreakGlass 権限を入れたことで新しく生じるリスクではありません。原本バケットの守りは止まっているあいだも効き続けるので、データは消えません。復旧などの作業は、Okta が戻るまで待つことになります。待てない場面への備えは、CorpIT チームと決めたいと考えています。
- **BreakGlass 権限に自分を足せる人がいます。** ただし、1 人では足せないようにしています。
  - BreakGlass 権限で入るには、Okta のアプリへの割り当てと、ロール `BreakGlass` の信頼の設定（cdk-apps）の両方に名前が要ります（4.4）。
  - Okta の側は、Okta の管理者が変えられます。記録と通知で補います（4.5）。
  - cdk-apps の側は、PR のレビューを通ります。ただし、cdk-apps の deploy の経路を変えられる人（管理アカウントの管理者など）は、レビューを迂回できる可能性があります。
- **root が残っているあいだは、root で守りを外せます。** root の認証情報の削除は、CorpIT チームに別に依頼しています。
- **手元の PC の CLI からは、BreakGlass 権限を使えません。** 大量の操作は CloudShell で行います（4.6）。

## 補足

### 補足 1. FullAccess を廃止して新しく権限を設計する案を採らなかった理由

FullAccess の扱いには、2 つの案がありました。どちらも、BreakGlass 権限を新しく作る点は同じです。

- 案 A: FullAccess でできることから、BreakGlass 権限にあたる操作を外す。**（採用）**
- 案 B: 新しく権限を設計して割り当て、FullAccess を廃止する。

原本バケットの守りについては、どちらの案でも差はありません。案 B には、2 つの利点があります。

- 「FullAccess」という名前と中身の食い違いを無くせる。
- 日常の権限を絞り直せば、5 章の 1 つ目のリスク（FullAccess が盗まれると、原本バケット以外は壊せる）を小さくできる。

それでも案 A にした理由は、次のとおりです。

- **影響が大きすぎる。** FullAccess は tuscenes-prod だけでなく、複数のアカウントで使われています。また、EKS（`closed-loop-scenario-test`）・`coder`・`skypilot` などのアプリが、FullAccess のロールの名前（`AWSReservedSSO_FullAccess_…`）を直接参照して権限を与えています。廃止すると、これらをすべて移す必要があり、移行のあいだ、日常の作業に影響が出るおそれがあります。
- **名前の食い違いは、今もある。** FullAccess は、今も一部の削除を拒否しています（2.1）。名前の意味は「日常の作業で使う、いちばん強い権限」と説明すれば足ります。
- **案 A なら、守りたいところだけを変えられる。** 変わるのは、原本バケットのバケットポリシーと SCP だけで、FullAccess の権限セットにも、ほかのアカウントにも手を付けません。

権限セットの名前や日常の権限を見直すなら、ほかの権限セットも含めた組織全体の権限設計の中で、改めて考えるのがよいと考えています。

### 補足 2. BreakGlass 権限の中身を S3 の操作に絞る案

BreakGlass 権限の中身は、AdministratorAccess を仮の案にしています（1 章）。対案として、中身を「読み取りの権限（ReadOnlyAccess）＋原本バケットへの S3 の操作」に絞る案があります。

| | AdministratorAccess（仮の案） | S3 の操作に絞る（対案） |
|---|---|---|
| 守りの強さ | 同じ。BreakGlass 権限を持つ人は FullAccess も持っているので、中身を絞っても、その人ができることの合計は変わらない | 同じ |
| 作業のしやすさ | 復旧の途中で、S3 以外の操作（ライフサイクルの確認、CloudTrail の調査、アプリの停止など）が要っても、そのまま続けられる | S3 以外の書き込みが要ると、FullAccess に戻る必要がある |
| 説明のしやすさ | 「なぜ管理者の権限なのか」の説明が要る | 資料の範囲（S3 の保護）と中身が一致する |
| BreakGlass 権限のセッションが盗まれたとき | AWS のほぼすべてを操作される | 原本バケットと読み取りに限られる。ただし、同じ人の FullAccess も同じ方法で盗まれうるので、差は小さい |

いずれは、BreakGlass 権限を S3 以外の強い操作（IAM や組織の設定）にも広げる可能性があります（「この資料の範囲」）。その場合も、AdministratorAccess のほうが扱いやすいと考え、仮の案にしています。

### 補足 3. BreakGlass 権限の入り方の対案

4 章の形（BreakGlass 専用の Okta アプリから、IAM ロールに直接入る）のほかに、2 つの案を比べました。

**案 1: IAM Identity Center の権限セットにし、ログインのときに強い要素を求める**

- BreakGlass 権限を IAM Identity Center の権限セットとして作ります。
- Okta の IAM Identity Center のアプリの認証ポリシーで、BreakGlass のグループの人には、ログインのたびにフィッシングに強い要素を求めます。
- 採らなかった理由: **BreakGlass 権限を選ぶ瞬間には、MFA を求められません。** IAM Identity Center は、ID の出どころが Okta のとき、MFA の機能を持ちません。一度ログインすれば、AWS のアクセスポータルのセッションが続くあいだ（既定で 8 時間）、追加の認証なしに BreakGlass 権限を選べます。朝のログインで済んでしまうので、「入るたびに本人確認をする」ことになりません。

**案 2: BreakGlass 権限の専用の Okta ユーザーを分ける**

- BreakGlass 権限を持つ人に、2 つ目の Okta のユーザー（例: `名前+bg@…`）を用意します。その ID には、BreakGlass 権限の権限セットだけを割り当てます。
- 使うときは、ブラウザの別のプロファイルで、専用の ID でログインし直します。入るたびに MFA を求められます。
- 「特権の ID とふだんの ID を分ける」という一般論（NIST SP 800-53 AC-6(2) など）に合います。
- 採らなかった理由: **毎年かかる手間が大きい。** Okta のユーザーが増え（ライセンスの扱いを CorpIT に確かめる必要がある）、IAM Identity Center にも同期されます。MFA の登録や、退職のときの処理も 2 重になります。4 章の形なら、同じ「入るたびの本人確認」を、Okta のアプリ 1 つと一度きりの設定で実現できます。

参考までに、FullAccess から IAM ロールに切り替える形（assume role）も検討しました。Okta 経由のセッションからの切り替えでは、信頼の設定で MFA を条件にできない（`aws:MultiFactorAuthPresent` が載らない）ため、案 1 と同じ弱点があり、採りませんでした。

### 補足 4. 用語

| 用語 | 説明 |
|---|---|
| SCP（Service Control Policy） | AWS Organizations で、組織の中のアカウントにかける権限の上限です。SCP で拒否した操作は、そのアカウントの中では、管理者の権限を持つ人でもできません。管理アカウントから設定します。 |
| EventBridge | AWS の中で起きた出来事（CloudTrail に記録された操作など）を拾い、条件に合うものを別の処理（Slack への通知など）に流す AWS のサービスです。 |
| CloudShell | AWS のコンソールから開ける、ブラウザの中のターミナルです。コンソールに入ったときの権限のまま、AWS CLI などのコマンドを使えます。 |
| Object Lock | S3 のオブジェクトの版に鍵をかけ、決めた期限まで、誰も消したり上書きしたりできなくする S3 の機能です。一度バケットで有効にすると、無効に戻せません。 |
| SAML（Security Assertion Markup Language） | ログインの結果を、IdP（Okta など、本人確認をするサービス）から別のサービス（AWS など）へ安全に渡すための標準の方式です。この資料では、Okta で本人確認をした人を、AWS の IAM ロールに入れるために使います。 |
| FIDO2 | パスワードを使わずに、端末の中の鍵で本人確認をするための標準です。パスキーは FIDO2 に基づいています。鍵はログイン先のサイトに結び付くので、偽のサイトでは使えず、フィッシングに強いとされます。 |
